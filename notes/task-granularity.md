# 分割しすぎ問題（記事3「チームで使う」用のメモ）

## 主張

タスクを30個以上のサブタスクに割る流儀が広まっている。UIコンポーネント単位、
ロジック単位で1タスク。根拠は「レビューで100行なら読めるが1000行は読めない、疲れる」。

**AI以前ならこの理屈は成り立っていた。いまは成り立たない。**

### レビューで見るものが変わった

いま見るべきなのはコードの美しさではない。

- このPRは、タスクをちゃんと解決しているか
- UXは良いか
- 性能は問題ないか
- 落ちるケースはないか

**これを判断するには「動くもの」が要る。** コンポーネント1個では判断できない。
そしてコードの精読自体は、どのみちAIにやらせる。**人間の仕事は、その指摘を見て
何を直すか決めること。**

### 分割しすぎるとAIを並列で回せない

これが実務上いちばん効く。細かく割ると、

- サブタスク同士が互いの成果物を必要とする
- 並列で走らせると衝突する
- コンフリクト解消と作り直しが増える

**細かく割るほど、並列化できなくなる。** AIを使う前提だと、これは直接コストになる。

### 自分の割り方（推しスキ）

機能まるごとで1タスク。

- `crop`（チェキの切り出し）
- `album`
- 推し会計
- AIチャット
- チェキマップ

**それぞれ単体で動いて、単体で価値がある単位。**

## ⚠️ 書く前に潰すべき反論

この主張には、まだ答えていない正当な反論がある。書くなら先に答えること。

1. **revertしやすさ**：大きいPRは切り戻しが雑になる
2. **git bisect**：大きいコミットは原因の特定が粗くなる
3. **リリース単位**：機能まるごとだと、一部だけ先に出せない
4. **レビュー負荷は本当に消えたのか**：AIに任せるといっても、最終責任は人間

→ 「PRの大きさ」と「コミットの大きさ」を分けて論じると、1と2は両立できるはず。
   PRは機能単位、コミットは小さく、が答えの候補。
