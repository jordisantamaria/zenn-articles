## 1. 画面1つが、30タスクになる

自分も細かく割ります。**問題は「割るかどうか」ではなく、どこまで割るかです。**

多くのチームで見るのはこういう分け方です。画面を1つ作るのに、

- 表示コンポーネント
- そのヘッダー
- 一覧の行
- 状態管理のフック
- API呼び出し
- バリデーション
- スタイル
- テスト

……と並べていくと、**画面1つで30〜50タスクになります。** そして1タスク＝1PRなので、PRも30〜50本出ます。

### 根拠は、レビューの疲労だった

なぜそうするのか。根拠はだいたいこれです。

> 「レビューで100行なら読めるが、1000行は読めない。疲れるし、見落とす」

**これは正しい観察でした。** 人間がコードを1行ずつ追って、命名や書き方の是非を判断していた時代には、割るしかありません。1000行を精読して品質を判断できる人はいません。

**その前提が、いま崩れています。**

## 2. レビューで見るものが変わった

いま自分がPRを見るときに判断しているのは、こういうことです。

- **このPRは、そのタスクをちゃんと解決しているか**
- **UXとして成立しているか**
- **性能は問題ないか**
- **落ちるケースはないか**

**どれも、コードを読んでも分かりません。** 動かさないと分からないし、**機能がまるごと揃っていないと判断できません。**

コンポーネント1個のPRを見て「UXが良いか」は答えられない。「落ちるケースがあるか」も、その部品だけでは分からない。**細かく割ると、いま本当に見るべきことが見られなくなります。**

### コードの精読は、どのみちAIがやる

そしてコード自体のレビューは、結局AIに投げます。命名、型、抜けているエラー処理、使われていない分岐。**人間より速くて、疲れません。**

**人間の仕事は、その指摘を見て「何を直すか」を決めることです。** 直す価値のある指摘か、いま直すべきか、仕様として正しいか。これは判断であって、精読ではありません。

つまり、**「疲れるから割る」の前提が消えています。** 疲れる作業のほうを機械がやるようになったからです。

## 3. 分けすぎると、AIを並列で回せない

ここが実務でいちばん効きます。そしてあまり語られていません。

細かく割ったサブタスクは、**互いの成果物を必要とします。** UI部品のタスクは、その下のロジックのタスクが決めた型を使う。ロジックのタスクは、データ取得のタスクが返す形を前提にする。

順番に1つずつやるなら問題ありません。**並列で走らせた瞬間に壊れます。**

- 相手がまだ書いていない型を前提に書く
- 同じファイルを両方が触ってコンフリクトする
- 片方の設計が変わって、もう片方を作り直す

**細かく割るほど、並列化できなくなります。** そして並列で回せることは、AIを使う上でいちばん大きな利点です。**分割の作法を守った結果、AIの一番の強みを捨てることになります。**

機能まるごとで割れば、この問題は起きません。**チェキとアルバムは、互いの途中経過を必要としないからです。**

## 4. 単位は「単体で判断できる最小の変更」

では、どこで切るのか。基準は1つです。

> **それだけを動かして、良し悪しを判断できるか。**

`AlbumHeader.tsx` は判断できません。動かせないし、単体では何の価値もない。一方「アルバムに写真を追加するシート」なら、**端末で開いて、使ってみて、UXが良いかを言えます。**

機能まるごとである必要もありません。**アルバム機能全体は大きすぎて、逆に判断が雑になります。** 実際、自分のリポジトリでもアルバムは複数のタスクに分かれています。

- 写真を追加するシート
- 写真の詳細表示
- 写真の位置情報
- カメラロールの一括スキャン

**どれも単体で動いて、単体で「これで良いか」を言えます。** そして互いの途中経過を必要としません。

規模でいうと、**1タスクあたり十数〜30ファイル、500〜1,000行**あたりに落ち着いています。「1000行は読めない」の基準からは外れますが、**読んでいるのはコードではなく、動いている画面です。**

1章の分け方と並べるとこうなります。

| | 「アルバムに写真を追加するシート」 |
|---|---|
| よく見る分け方 | コンポーネント、ヘッダー、行、フック、API、バリデーション、スタイル、テスト … **10〜15タスク** |
| 自分 | **1タスク** |

**どちらも「割っている」のは同じです。** 違うのは、割った先が判断できる単位かどうかだけです。

## 5. PRの大きさと、コミットの大きさは別

ここで当然出てくる反論があります。

> 「大きいPRはrevertしづらい」「`git bisect` の解像度が落ちる」

**もっともです。ただ、それはコミットの話であってPRの話ではありません。**

冒頭の表をもう一度見てください。推し活費は**8,576行ですが、34コミットに分かれています。** アルバムは6,275行で28コミット。**1コミットあたり200〜300行です。**

| | 単位 | 目的 |
|---|---|---|
| **コミット** | 小さく | revert、`bisect`、履歴を追う |
| **PR・タスク** | 機能まるごと | 動くものとして判断する |

**この2つを混ぜて考えるから、「大きいPRは危ない」という話になります。** コミットが細かければ、切り戻しも原因特定も細かくできます。PRの大きさとは無関係です。

分けるべきは**履歴**であって、**タスク**ではありません。

## 6. 1タスク＝1セッション＝1worktree

タスクの単位が決まったら、**そのタスクは1つのセッションが最後まで持ちます。** そして、そのセッションは**専用のworktree**で作業します。

多い日で9セッションを同時に動かしています（2026年8月20日）。同じリポジトリに対してです。

### worktreeを分けないと、3つの壊れ方をする

全部、実際に起きたことです。

**1. gitのインデックスは、セッション間で共有されている。**
`git add` してから別の操作を挟んでコミットすると、その隙に**別のセッションが自分のコミットを打ち、こちらがステージしたファイルを巻き込みます。** 2026年8月19日に、メール取り込み機能の約340行が、まったく無関係な `fix(share): ...` の中に入りました。

**2. pre-commitの型チェックは、プロジェクト全体に走る。**
自分のファイルが完璧でも、**別のセッションが書きかけのコードを置いていれば、こちらのコミットが通りません。**

**3. 同じファイルを2つのセッションが触ると、片方の変更が黙って消える。**
警告も出ません。

worktreeを分けると、この3つが同時に消えます。**インデックスも作業ツリーも別になり、型チェックは自分の変更に対して走るからです。**

### そのためのスクリプト

worktreeは便利ですが、手で回すには手数が多い。**関連するスクリプトが6本あります。**

| スクリプト | 何をするか |
|---|---|
| `wt` | worktreeを作り、tmuxのウィンドウを開き、必要なものを揃えるところまで |
| `wtopen` | 既存のworktreeを開き直す |
| `wtworkspace` | 複数のworktreeをまとめて扱う |
| `wt-sync-local-files` | `.env` などgitに入らないファイルを worktree へ運ぶ |
| `wtr` | worktreeを削除する |
| `wtclose` | 全worktreeを閉じ、タイマーを止め、tmuxのウィンドウを片付ける |

**4本目が地味に効きます。** worktreeは新しい作業ツリーなので、gitignoreされているファイル（`.env`、`node_modules` へのリンクなど）が存在しません。**これを毎回手でコピーしていると、そのうちやらなくなります。**

### worktreeでも救えないもの

1つだけあります。**`develop` が壊れているときです。**

worktreeは `develop` から生えるので、`develop` がコンパイルできなければ、**どのworktreeでもコミットできません。** pre-commitがプロジェクト全体を型チェックするからです。

2026年8月20日にこれが起きて、**3セッションが同時に止まりました。** あるコミットが、importしているモジュールと型を置き去りにしたまま入ったせいです。

だから着地させるときのルールが1つあります。**触ったファイルではなく、コンパイルが通る単位でコミットすること。** 新しいファイルや型を足したなら、**それを使う側と同じコミットに入れます。**

## まとめ

- **「細かく割れ」の根拠は、人間がコードを精読していた前提の上にあった。** その作業はもうAIがやります
- **いま人間が見るのは、動くかどうか・UX・性能・壊れ方。** どれも機能がまるごと揃わないと判断できません
- **分けすぎるとAIを並列で回せません。** サブタスク同士が依存し合って、衝突と作り直しが増えます
- **タスクの単位は「それだけを動かして、良し悪しを判断できる最小の変更」**

細かく割りたくなったら、**それはコミットで割ればいい話かどうか**を先に考えてみてください。だいたいそうです。
