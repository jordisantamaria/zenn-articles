「推しスキ」という推し活アプリを個人で作っています。App StoreとGoogle Playに出ていて、**実際のユーザーが毎日使っています。**

そのバックエンドをVercelからFly.ioへ移したとき、いちばん時間をかけたのは移行そのものではなく監視でした。移行は3時間で終わっています。

サーバーレスをやめるということは、**サーバーレスが肩代わりしてくれていた仕事が自分に返ってくる**ということです。その中でいちばん重いのが「落ちても誰も教えてくれない」でした。プラットフォームの問題だったものが、自分の問題になります。

そして一人で開発していると、気づくのはユーザーからの連絡です。**しかも推しスキは現場で開くアプリなので、止まっていることに気づく人がいる時間帯と、僕が寝ている時間帯は重なります。**

ちなみにこの構成を組む過程で、**監視の仕組みがデプロイを落としました**。その話も書きます。

この記事は、そこで組んだ構成をそのまま置いておくものです。**「監視を入れる」と言うとき、実際には性質の違う4つを入れることになる**という話と、それを全部AIエージェントから触れる状態にしておく話。

なぜサーバーに移したのか、料金と機能をどう比較したのかは[別の記事](#)に書きました。

## 1. 監視の全体像——ログ・製品分析・エラー・メール

「監視を入れる」と言うとき、実際には**性質の違う4つ**を入れることになります。ここを混ぜると、どれも中途半端になります。

| 層 | 答える問い | 使っているもの |
|---|---|---|
| **ログ** | いま何が起きた？ なぜ落ちた？ | Axiom（保持30日、無料枠 月500GB） |
| **製品分析** | ユーザーは何をした？ どこで離脱した？ | PostHog（無料枠 月100万イベント） |
| **エラー追跡** | どのコードが、誰に対して壊れた？ | PostHog Error Tracking |
| **人間への通知** | **私はいま動くべきか？** | メール（Resend） |

4つ目が抜けがちです。前3つは「見に行けば分かる」もので、**一人で開発していると見に行きません。** ダッシュボードを毎日開く人はいません。開くのは、ユーザーから「アプリが動きません」と連絡が来た後です。

### ログ：60行の自前トランスポートと、譲れない3つのルール

Vercel Hobbyのログ保持は**1時間**で、障害の翌朝には何も残っていませんでした。Fly.ioの `fly logs` は在庫のない生放送です。だからAxiomに送っています。

SDKは入れず、ingest APIに直接POSTしています。そのとき決めた3つのルールが、結果的にいちばん効きました。

**1. 絶対にアプリを落とさない。** これは思想ではなく、**実際に落としたから**書いています。

最初、`beforeExit` でflushするハンドラを書いていました。このイベントはイベントループが空になったとき、つまりプロセスが終わろうとするときに発火します。そこで `fetch` するとループが復活し、ソケットがリクエストの途中で死んで、undiciが**awaitの外で**未捕捉の例外を投げる。それが `release_command`（`prisma migrate deploy`）を巻き込んで、Flyは「マイグレーション失敗」と判断しました。

**監視の仕組みがアプリを落とす。** これを避けるためのコードがこれです。

```ts
await fetch(url, {
  signal: AbortSignal.timeout(10_000),   // Axiomが遅ければ諦める
}).catch(() => {})   // ← try/catch に「加えて」必要。undici は await の外で投げる
```

そして flush のフックは `beforeExit` ではなく **SIGTERM / SIGINT** に付けました。Fly.ioがマシンを止めるときに送るのはSIGTERMで、そこには猶予があります。

**2. 絶対にブロックしない。** 送信は待たずにキューに積んで、50件か2秒で一括送信。キューには上限（1,000件）を付けます。**上限のないキューは、Axiomが落ちた日にメモリリークになってマシンを殺します**——つまりログの仕組みでサービスが落ちる、また同じ失敗です。

**3. 絶対に個人情報を送らない。** キー名でマスクします（`email` / `token` / `name` / `title`…）。値を見て「これはメールアドレスっぽい」と判定するのは脆く、**偽陰性はユーザーのメールを第三者に送ることを意味します。**

そしてもう一つ、地味にいちばん時間を溶かしたのがこれです。

```ts
// ESC は \u001b と書く。制御文字をソースに直接置くと、コピペや整形で壊れる
const ANSI = /\u001b\[[0-9;]*m/g   // ← これが無いと検索できない
```

consolaやHonoのロガーはステータスコードをANSIで色付けします。それがそのままAxiomに入ると、`200` の前後に色コードが付いた文字列になり、**`200` で検索しても何もヒットしません。** 障害のときにいちばん検索したい文字列が、色コードに埋もれていました。

### いちばん効いたアラートは「エラーが出た」ではなかった

ヘルスチェックはインフラの**内側**で動きます。ネットワークごと死ねば、チェックする側も一緒に消えるので、**失敗の通知すら来ません。**

> 監視対象の内側にある監視は、監視対象と一緒に死にます。

だから最初に作ったアラートはこれです。

```
['fly-logs']
| where _time > ago(15m)
| summarize count()
// → 0 のとき発火
```

**「15分間ログが1行も来ていない」。** 鳴るべき音が消えたことのほうが、エラーの発生より確実に検知できます。エラーが出ないほど静かに死ぬ落ち方が、いちばん怖いので。

### 製品分析とエラー追跡を、1つのツールに寄せる

PostHogを選んだ理由は、**ウェブとアプリで同じプロジェクトに入れられる**ことでした。ランディングページ（`posthog-js`）とReact Nativeアプリ（`posthog-react-native`）が別ツールだと、**「サイトに来た」と「アプリを開いた」の間で計測が切れます。** その断面がいちばん知りたい場所なのに。

エラー追跡も同じ場所に寄せました。Sentryではなく PostHog Error Tracking です。理由は無料枠の中身で、**Sentryの無料枠にはRelease Healthが付きません**（どのリリースからクラッシュが増えたか、が分からない）。

実装で気をつけた点も書いておきます。`posthog-js` は **231KB** あり、ランディングで最大のチャンクでした。動的importにして、`requestIdleCallback`（Safari向けに `setTimeout` のフォールバック付き）で**ページ描画が終わってから**読み込んでいます。分析ツールが分析対象の速度を落とすのは本末転倒なので。

### そして、人間に届ける最後の一手

管理コンソールのキューは静かに溜まります。ユーザーからの不具合報告、「イベントの時間が違う」という指摘、承認待ちの投稿。**全部データベースには存在していますが、誰かが見に行くまで存在しないのと同じです。**

だからキューに何か入った瞬間にメールを送ります。

```ts
export async function notifyAdmin({ kind, subject, details }: AdminAlertInput) {
  const to = process.env.ADMIN_ALERT_EMAIL?.trim()
  if (!to) return          // ← 環境変数が無ければ黙る。local と dev と CI はこれで静か

  try {
    await sendEmail({ to, subject: `[MyApp] ${subject}`, text, html })
  } catch (error) {
    logger.error('[admin-alert] failed to send', error)   // ← 絶対に投げない
  }
}
```

設計の要点は3つです。

- **絶対に投げない。** 呼び出し元はユーザーが送信した内容を保存している最中です。メール基盤が落ちていることが、ユーザーの投稿を失う理由になってはいけません
- **環境変数が無ければ何もしない。** これだけで local / dev / テストが静かになります。「通知先が存在する環境にだけ通知が存在する」
- **即時に送り、まとめない。** 1日1回のダイジェストは、ユーザーを24時間待たせるという意味です。まとめる価値が出るのは量が増えてからで、そのとき変えるのはこの1ファイルだけで済みます

**メールは、4つの層のうち唯一こちらから人間に届く経路**です。他の3つは、こちらが見に行かないと何も起きません。

## 2. 全部を、AIから触れる状態にしておく

ここが、いま構成を選ぶなら足すべきだと思っている基準です。

インフラを組むのは**一度きり**の作業でした。全部で3時間。**運用は毎日です。** そして一人でやっていると、最初に消えるのが運用です。

AxiomにもPostHogにも**MCPサーバー**があります。つまりAIエージェントは、僕がダッシュボードのスクリーンショットを貼るのではなく、**データセットに直接クエリを投げられます。**

```bash
npx @posthog/wizard mcp add     # PostHog（HogQL、エラー、フラグ）
```

Axiom側はAPL（Axiom Processing Language）のクエリ、データセット一覧、モニタの作成・履歴まで触れます。実際に投げているのはこういう依頼です。

- 「直近24時間の5xxをルート別に出して。増えてるものがあれば、いつから増えたかも」
- 「レイテンシのP95が上がってる時間帯があるか見て。あればそのときのログを10件」
- 「このスパイク、ボットか人間か判断して。判断の根拠も」
- 「PostHogで、オンボーディングのどのステップの離脱がいちばん大きいか出して」

これは「見やすくなった」という話ではありません。**そもそも僕が毎日はやらない作業**が、実行されるようになったという話です。

実際、この構成で見つかった問題はほとんどそうやって出てきました。ANSIコードでログが検索できなくなっていたことも、デプロイを落としていた真犯人がログ送信そのものだったことも（画面上はマイグレーション失敗に見えていました）、**気づいたきっかけは両方ともログへのクエリ**です。ダッシュボードを眺めて見つかるものではありません。

### だから、選定基準に1つ足す

> **そのサービスの「状態」は、テキストで問い合わせられるか。**

きれいなダッシュボードは、人間には価値があります。**エージェントにとっては存在しないのと同じです。** 逆に、CLIとAPIとMCPで中身が引き出せるなら、それは毎日見てもらえるインフラになります。

第3章の比較表に「設定の持ち方」という列を入れたのは、そのためです。`fly.toml` がGitに入ること、`fly logs` がテキストを返すこと、AxiomにAPLで問い合わせられること——これらは同じ性質の話です。

「AIに管理させやすいか」がインフラ選定の基準に入るようになったのは、たぶんここ1〜2年のことです。でも一人で開発しているなら、**これは価格と同じくらい実務に効きます。**

### ただし、「何を聞くか」は向こうからは出てきません

正直に書いておきます。**エージェントがくれるのは情報と選択肢までです。**

この記事に出てくる判断は、ほとんどがAIの提案ではありませんでした。

- Proを払わずにサーバーへ移すと決めたこと。数字は両方出ていました。42%を「このプロダクトでは許容できない」と判断したのは、数字ではなくプロダクト側の話です
- **ユーザーが100人に満たない時点でボット対策を入れる**と決めたこと
- オートスケールに2という天井をつけると決めたこと
- 監視を初日から入れると決めたこと

2つ目がいちばん分かりやすい例です。**「まだ誰も使っていないのに、攻撃を心配すべきか？」という質問を、そもそも誰も思いつきません。** 統計的に見れば、この規模で身構えるのは過剰です。

僕がそれを入れたのは、会社で小さなスタートアップのアプリを何本も作って、**攻撃が実際に何度も起きたのを見ているから**です。これは検索して出てくる知識ではなく、**痛い目に遭った記憶**です。

エージェントは、投げた質問には的確に答えます。**投げられなかった質問には、何も答えません。**

> AIが速いのは「調べること」です。「何を調べるべきか」を決めているのは、まだ経験のほうです。

そして経験のいいところは、AIが速くなっても目減りしないことだと思っています。むしろ調べるのが速くなるほど、**正しい問いを持っている人の生産性だけが伸びていきます。**

## 3. まとめ

4層のうち、どれか1つだけ入れるなら**メール通知**です。他の3つは「見に行けば分かる」もので、一人で開発していると見に行かないので。

そして、いま構成を選ぶなら足すべき基準がこれです。

| 層 | 答える問い | 使っているもの | AIから触れるか |
|---|---|---|---|
| ログ | いま何が起きた？ | Axiom | ○ MCP（APL） |
| 製品分析 | ユーザーは何をした？ | PostHog | ○ MCP（HogQL） |
| エラー追跡 | どのコードが壊れた？ | PostHog Error Tracking | ○ MCP |
| 人間への通知 | 私はいま動くべきか？ | メール（Resend） | — |

最後の列が、この記事でいちばん言いたかったことです。**毎日は見に行かない**という前提で組むと、選ぶものが変わります。
