## 2. 最低限これだけ：Claude Codeは、文脈が全部

**Claude Codeを使うために、本当に必要な知識はここだけです。** 逆にここが分かっていないと、あとの章はただの作法に見えます。

### Claudeが知っているのは、文脈に載っているものだけ

Claudeは前回の会話を覚えていません。**毎回ゼロから始まり、その時点で読み込まれたものが全てです。** 「前は分かってくれたのに」は起きません。前回も今回も、載っていたものだけで動いています。

### 文脈は有限で、埋まるほど悪くなる

窓には上限があります。そして**埋まるほどトークンを食い、遅くなり、取り違えも増えます。**

かといって、必要な情報が文脈から消えれば、今度は話の筋を見失います。**入れすぎても、足りなくてもダメ**という両側の問題です。

つまり **Claude Codeを使うというのは、ほぼ文脈を管理することです。** そして管理の方法は、3つあります。

### 管理①：タスクで分ける

よく見るのが「`plan.md` をリポジトリに置いて状況を書き続ける」という方法です。**自分はやっていません。** もっと単純な運用で足ります。

- **タスク1つにつき、セッション1つ。** 別のタスクを始めるときは、よほど近い内容でない限り新しいセッションを開く
- **そのセッションは、終わるまで何日でも使い回す。** 途中で文脈を失いません
- **`/rename` で名前を付ける。** あとで `--resume` から選んで戻れます
- **50%を超えたら、区切りのいいところで `/compact`。** 作業の途中で自動圧縮が走るより、自分で切るほうが安全です

**リポジトリに状態を書き出す必要はありません。セッションそのものが状態だからです。** 書き出す手間が増えるうえに、その文章がまた文脈を食います。

### 管理②：置き場所で分ける

2つ目が、**何をどこに置くかです。** 文脈への載り方は3種類しかありません。

| 種類 | いつ載るか | 例 |
|---|---|---|
| **常時** | 毎回、全部 | `CLAUDE.md`、ルール |
| **必要なときだけ** | 索引から選んで開く | メモリ、スキル |
| **テキストではない** | ツールを呼ぶ瞬間に介入する | 権限、フック |

3つ目が決定的に違います。**上の2つは「お願い」ですが、3つ目は「拒否」です。** モデルの判断を経由しません。

そして同じ内容でも、置く場所で結果が変わります。

- **常時の層** → 毎回載るが、他の全部と競争する
- **必要なときだけの層** → 呼ばれた瞬間、それが主役になる
- **権限・フック** → 競争しない。通らないものは通らない

**この記事の残りは、この②の話です。** 細かい仕様は、1章のガイドに書いてあります。

### 管理③：足りない情報を、取りに行けるようにする

①と②は「載せすぎない」話でした。3つ目は逆で、**必要な情報がちゃんと届いているかの話です。**

**コードを書くのに必要な情報は、コードの中だけにありません。** 自分の場合はここから取っています。

| どこから | 何を |
|---|---|
| コード | 既存の実装と規約 |
| チケット | 何を作るのか |
| Slack | **なぜそう決まったのか** |
| Notion | 仕様と背景 |
| Figma | デザインの実際の値 |
| AWS | 動いている環境の設定 |

**チケットだけ読んで書いたコードは、だいたいどこかが足りません。** 決定の理由はSlackにあり、色や余白の値はFigmaにあり、本番の設定はコンソールにある。人間は当たり前にこれを集めてから書きます。

MCPやCLIを繋ぐというのは、**それをClaudeにもできる状態にする、というだけの話です。** そして貼るのとは違います。**エラーログをコピーして貼れば、それは以後ずっと文脈に残ります。** 1万行貼って、必要だったのは3行かもしれない。繋がっていれば、必要になった時点で取りに行き、**必要なぶんだけ載ります。**

だから「AIから触れるか」は、サービスを選ぶ基準になります。GUIのコンソールしかないサービスは、**結局こちらがスクリーンショットを貼ることになるからです。**

## 3. 全部を作った方法は、ひとつだけ

上の4つの層は、座って設計したものではありません。**全部、何かがうまくいかなかった直後に、その場で足したものです。**

やることは1つだけです。

> **失敗したら、そのセッションのまま「いまのを設定に反映して」と頼む。**

### なぜ「その場」なのか

**そのセッションにしか材料がないからです。**

失敗した直後のセッションには、自分が何を指示して、Claudeがどこを勘違いして、結局どう直したのかが全部残っています。**Claude自身がそれを見ています。** だから「いまのを記憶に書いて」と言えば、何が原因だったのかを自分でまとめられる。

そして、もっと大事なのはこちらです。**その場なら、書いたルールが効くかどうかを確かめられます。** 失敗した本人がそこにいるので、「このルールがあったら、さっきのは防げたか」を実際に当ててみることができる。

翌日にやろうとすると、この2つが両方なくなります。**判断する材料がないまま、自分の記憶を頼りにルールを書くことになる。** それは失敗そのものではなく、失敗の要約に対して書いたルールです。効くかどうかも、次に同じ失敗をするまでわかりません。

ついでに言うと、翌日にやろうとすると大体やりません。

### 厳密にレビューしなくていい

これが続けられる理由です。かかる時間は1〜2分で、**書かれた内容を全部読んで厳密に確認する必要もありません。** ざっと目を通して、方向が合っていればそれでいい。

間違っていたら、次に同じ失敗をしたときにまた直せばいいだけです。**設定は一度で正解にする必要がなくて、失敗のたびに近づいていけばいい。**

### やってはいけないのは、そのまま進むこと

「これ効かないな」と思って、直さずに次の作業に移る。**これだけが本当にまずいやり方です。**

そして、**これが「AIは使えない」の正体だと思っています。**

「Claudeがちゃんと答えてくれない」「AIは信用できない」「結局自分で書いたほうが速い」。よく見る感想ですが、体感では9割以上、原因は同じところにあります。**うまくいかなかったその瞬間に、何も直していないことです。**

うまくいかない → 文句を言う → そのまま次へ。これを繰り返すと、環境は初日のままです。**3ヶ月使っても、初日と同じ精度のClaudeを使い続けることになります。** そして「やっぱりAIはこの程度か」という結論になる。

逆に、失敗のたびに1分だけ使って直していれば、**同じ失敗は二度目で消えます。** AIが賢くなったわけではありません。こちらが同じ説明を二度しなくてよくなっただけです。

不満を持ったまま使い続けるか、その場で1分だけ直すか。**差はそこだけで、この差が5ヶ月で記憶352件とスキル58個になりました。**

そして、直したのに同じ失敗が続くようなら、そのときは腰を据えて設定を読み返す。定期的な見直しは、それくらいの頻度で十分です。

## 4. 忘れることは、記憶に置く

一番効いた層がこれです。

Claudeは会話が終われば全部忘れます。次のセッションでは、また同じ前提から説明することになる。

**こちらがやることは1つだけです。「前も同じ説明をしたな」と思った瞬間に、「これ覚えといて」と言う。** それだけです。

### ファイルは自分で作っていません

置き場所も形式もECCの設定が決めてくれるので、**自分で設計したものではありません。**

- 1ファイル1事実（352件あるのは、細かく切られているから）
- `MEMORY.md` が索引で、1件1行
- プロジェクトごとに独立。モバイルアプリの話が客先の作業に混ざりません

**メモリのファイルを手で書いたことは一度もありません。** 「覚えといて」と言うと、Claudeが置き場所を決めて、索引に足して、関連する記憶へのリンクまで張ります。

つまり、**この層を始めるコストはほぼゼロです。** 難しいのは仕組みのほうではなくて、その場で一言いうことのほうです。

### CLAUDE.mdとは役割が違う

`CLAUDE.md` は3リポジトリに置いていますが、そこに書くのは**自分が決めたルール**です。「mainはJordiがマージする」「作業はworktreeで」のような、そのリポジトリの掟。

記憶に入るのは逆で、**作業中に発見してしまった事実**です。書くのも自分ではなくClaudeです。

### なぜ記憶をCLAUDE.mdに全部書かないのか

352件を1枚のファイルにすると、**毎回そのファイル全部が文脈に載ります。** 今日の作業に関係あるのは3件なのに、残り349件ぶんのトークンを毎回払うことになる。

索引だけを読ませて、関係のあるファイルだけ開かせる。これなら件数が増えても、毎回のコストはほとんど変わりません。

### 実際に入っているもの

たとえばこの2件です。

> **worktreeを分けても、gitのインデックスは共有されている。** だから `git add` して後からコミットすると、別のセッションのコミットに自分のファイルが持っていかれる。コミットは `git commit -- <paths>` で。

> **シンガポールへの236msはバグではない。** DBに日本のリージョンがないので、サーバーとDBを同じ場所に置いた結果。遅いクエリを探し始める前に、まずpingを測る。

どちらも、**知らなければ半日溶ける類の話です。** そして一度溶かした人間しか書けない。ドキュメントに書いてあることは記憶に置きません。リポジトリを読めばわかることも置きません。**置くのは、コードにも履歴にも書いていないことだけです。**

## 5. 繰り返すことは、スキルにする

記憶が「事実」なら、スキルは「手順」です。

58個は、設計して作ったものではありません。**3回目に同じ指示を書いたとき**に作っています。作る基準はそれだけです。

| スキル | 何をするか |
|---|---|
| `/commit` | ステージ済みの差分を読んで、そのリポジトリの言語と形式に合わせたコミットメッセージを3案出す。選ぶだけ |
| `/solve` | チケットから、ブランチを切る→実装→push→Draft PR作成→worktreeの片付けまで通す |
| `/bg` | その `/solve` をバックグラウンドで走らせる。worktreeを先に作ってからサブのClaudeを起動するので、いまの作業を止めない |
| `/review` | PRでもローカルの変更でもレビューする。そのリポジトリの規約に合わせたチェックリストで、他のボットが拾わない「参照はあるのに実装がない」系まで見る |
| `/resolve-bot-review` | ボットのレビューを処理する。指摘ごとに「直す／意図通り／もう古い／間違い」を判定して、直すものだけ直してスレッドに返す |
| `/release-draft` | リリース用のDraft PRの説明文を、新しいコミットぶんだけ追記する。チェック済みのQA項目は絶対に外さない |

コードを書く以外のスキルもあります。この記事も `/zenn-article` を通して書いています。

### スキルにすると、うまくいった条件が残る

指示を毎回書き直していると、**うまくいったときの条件が残りません。** 前回なぜうまくいったのか、何を指定したからなのかは、3週間後には自分でも思い出せない。

スキルはそれを固定します。そして**失敗するたびに追記できるので、使うほど厳しくなります。**

### 実例：`/commit` が `git add` を禁止した理由

同じリポジトリでClaudeのセッションを何個も並行して動かしています。多い日で9個。

**gitのインデックスは、そのセッション全部で共有されています。** つまり `git add` してから別の操作を挟んでコミットすると、その隙に**別のセッションが自分のコミットを打ち、こちらがステージしたファイルを巻き込みます。**

2026年8月19日に実際に起きました。メール取り込み機能の約340行が、まったく関係のない `fix(share): ...` というコミットの中に入りました。コードは無事でしたが、**コミットメッセージが中身の半分を説明していない**状態です。

その場で `/commit` に1行足しました。

```bash
git commit -F - -- path1 path2   # git add してから commit しない
```

`git commit -- <paths>` はインデックスの残りを無視するので、他のセッションがステージしているものに触りません。**この失敗は、それ以来一度も起きていません。**

スキルにしていなければ、この判断は「あのとき何かあったな」で消えていました。

### 道具があることと、使うことは別

正直に書くと、**持っているだけでは効きません。**

Androidのdevビルドは、EASに投げると15分待つことになるのでローカルでやる、と決めています。それでもある日、**習慣でEASに投げました。** ルールがなかったからではなく、単に読まずに手が動いたからです。

そのときもその場で直しました。いまはCLAUDE.mdに書いてあります。

## 6. 守ってほしいことは、お願いせずに強制する

ここが一番大事な層です。

**プロンプトやCLAUDE.mdに「mainにpushしないで」と書くのは、お願いです。** 守られる確率は高い。でも100%ではありません。そして事故というのは、その残りの数%で起きます。

**フックとスクリプトは拒否です。** 通らないものは通りません。

### 3段構えにしている

| 段 | 仕組み | 性質 |
|---|---|---|
| 1 | 権限の拒否リスト | Claudeのツール呼び出しの入口で止める |
| 2 | フック | コマンドの中身を見て、条件つきで止める |
| 3 | リポジトリ側のスクリプト | **Claudeが関係なく動く。人間が手で叩いても止まる** |

3段目が効くのは、**Claudeを信用するかどうかという話から降りられるからです。** リポジトリ側で不正な状態が作れないなら、誰が叩いても同じです。

### 1段目：拒否リスト16個

```
Bash(rm -rf *)
Bash(git push --force*)
Bash(git reset --hard*)
Bash(curl * | bash)
Read(~/.ssh/**)
Read(**/.env)
```

どれも「うっかり」が取り返しのつかないものです。逆に許可リストは73個あって、**毎回聞かれると邪魔なだけの読み取り系はそこに入れています。拒否を厳しくするほど、許可を広くできます。**

### 2段目：フックは条件つきで止められる

| フック | 何をするか |
|---|---|
| `block-prod-merge.sh`（91行） | 本番にデプロイされるリポジトリで、`main` へのマージとpushを拒否する |
| `ask-before-dev-server.sh` | 客先のworktreeで、勝手にdevサーバーを立てる前に確認する |
| `deploy-oshisuki-dev.sh` | `develop` にpushしたら、dev環境へのデプロイを走らせる |

`block-prod-merge.sh` が91行あるのは、**判定が単純ではないからです。** どのリポジトリか、いまどのブランチにいるか、コマンドがどの形か。全部見てから決めます。拒否リストの1行では表現できません。

そして3つ目に注目してほしいのですが、**フックは「禁止」だけの仕組みではありません。** 忘れがちな手順を自動で走らせるのにも使えます。

### 3段目：リポジトリ側のスクリプトが、そもそも不正を許さない

ここが**Claudeの設定より強い**ところです。

**pre-commit で止まるもの：**

- `main` への直接コミット（ブランチ名を見て拒否）
- 型エラーとlintエラー（staged分に `tsc --noEmit` と `eslint`）

型が通らないコードはコミットできません。**Claudeが「たぶん大丈夫」と思っても関係ありません。**

**worktreeを片付けるスクリプト（`worktree-land.sh`）は、12箇所で中断します：**

- worktreeに未コミットの変更が残っていたら、やらない
- rebaseが1つでも衝突したら、その場でrebaseを中止して元に戻す
- マージがfast-forwardにならなかったら、やらない

**「途中まで進んで壊れた状態」が作れない**ようになっています。中断したらworktreeは触る前と同じです。

**post-commit は、リリース用PRの説明文を裏で更新します。** 忘れるからです。

### なぜここまでやるか

並行で何セッションも動かしていると、**全部の出力を自分で見ることは物理的にできません。**

なので、見なくても壊れないようにしています。**レビューで捕まえるのではなく、そもそも不正な状態を作れないようにする。** これはAIに限った話ではなく、CIやpre-commitがずっとやってきたことです。相手がAIになっても考え方は同じで、**効く相手が増えただけです。**

## 7. 設定は、遅くもする

ここまで「足せ」という話をしてきたので、逆の話も書きます。**設定は開発を遅くもします。**

そして遅くなったとき、**犯人はだいたい思っているところにいません。**

### コストは2種類あって、桁が3つ違う

| 種類 | 例 | 実測 |
|---|---|---|
| **1回あたりのコスト** | フックがPythonスクリプトを1本走らせる | **数十ミリ秒** |
| **ターン数のコスト** | ゲートがエージェントをもう1周させる | **1〜2分** |

自分の環境で測った数字です。

- `python3` の起動：**約16ms**
- `git status --porcelain -uall`：**約30ms**
- サブエージェントを1回呼ぶ：**1〜2分**

**桁が3つ違います。** なので「スクリプトが重いのでは」と疑う前に、**1回の依頼で何ターン回っているかを数えるほうが先です。**

### よくある誤診：言語のせい

「フックがPythonだから遅い」は、**まず違います。** 起動は16msです。同じスクリプトをGoで書き直しても、体感は1ミリも変わりません。

言語ではなく、**そのフックが何を起動するか**です。`git status` なら数十ミリ秒ですが、**プロジェクト全体のlintや型チェックを走らせていたら数十秒**になります。同じ「1本のスクリプト」でも中身で桁が変わります。

### 本当に効いてくる4つ

1. **ゲートが強制するターン数。** 「計画を書き終えるまで編集させない」「評価が終わるまで完了させない」のような仕組みは、1回の依頼を4〜5ターンに増やします。**1行の修正でも同じだけ払います**
2. **毎回のツール呼び出しで重い処理を走らせるフック。** 1回2秒でも、50回編集すれば100秒です。しかも分散しているので誰も気づきません
3. **検証そのものが高い。** インクリメンタルでない型チェックは、3行直すたびに全部を検査します。**エージェントは検証を繰り返す前提の道具なので、ここが高いと全部が高くなります**
4. **常時読み込まれる文脈。** ルール、`CLAUDE.md`、使っていないMCPのツール定義。毎ターン払い続けます

### 守りのコストは、仕事の大きさに比例させる

これがいちばん言いたいことです。

**1行の修正と3日がかりのリファクタに、同じ重さの手続きを課すと破綻します。** 小さい仕事の割合のほうが圧倒的に多いので、平均コストは重いほうに引きずられます。

そして本当の問題はその先です。**手続きが重すぎると、人は必ず抜け道を探します。** 止めるために作ったものが、止められないまま使われなくなる。**厳しくしすぎた守りは、緩い守りより弱いです。**

だから、**止める仕組みには必ず「理由を書けば通す」出口を用意しています。** 理由が記録に残るなら監査はできるので、失うものはありません。出口のない禁止は、いずれ設定ごと外されます。

### 疑う前に測る

遅いと感じたら、この順で切り分けます。

1. **1回の依頼で何ターン回っているか。** 増えているなら、そこで終わりです
2. **フックが何を起動しているか。** `time` を付けて実際に測る。想像で犯人を決めない
3. **型チェックやテストが1回いくらか。** インクリメンタルになっているかを確認する
4. **常時載っている文脈の量。** ルールの行数と、繋いでいるMCPの数

**この順番が大事です。** 1番の影響が3桁大きいので、4番から手をつけると何も改善しません。

## 8. よくある誤解：設定は短いほどいい

設定の話でよく見かける「作法」があります。

> 「`CLAUDE.md` は短く。長く書くとAIが読まなくなる」
> 「フォルダ構成をこう分けないと、指示が無視される」
> 「簡潔に書くほど、ちゃんと従ってくれる」

**観測されている症状は本物です。でも、そこから出てくる結論のほうが間違っています。** 自分の環境で測ったうえで、3つに分けて書きます。

### 誤解1：長く書くと読まれない / 分ければ必要な分だけ読まれる

どちらも同じ勘違いから来ています。**長さや分け方では決まりません。決めるのは仕組みです。**

自分の `~/.claude/rules/` は10ファイルに分かれていますが、**10ファイルとも毎回まるごと読み込まれます。** 合計464行。1つの長いファイルだったときと、載る量は完全に同じです。

| | 読み込まれ方 | 増やすと |
|---|---|---|
| `CLAUDE.md`・ルール | **毎回、全部** | 全部が薄まる |
| メモリ・スキル | 索引だけ常時、本体は必要なときだけ | **毎回のコストは変わらない** |

メモリを352件持っていても平気なのは、細かく分けたからではありません。**索引があって、開くものを選べるからです。** 分割しただけでは、この仕組みには乗りません。

#### 気にするべきは長さではなく、置き場所

「mainに直接pushしない」と「文字列はダブルクォートで」を同じファイルに並べると、**モデルから見ればどちらも同じリストの1行です。** 事故と好みを区別する手がかりがありません。

| 置き場所 | いつ届くか | 何を置くか |
|---|---|---|
| **フック・スクリプト** | ツールを呼ぶ瞬間 | 破られたら事故になるもの |
| **`CLAUDE.md`** | 毎回 | 本当に毎回関係することだけ |
| **スキル** | その作業のときだけ | 手順。呼ばれた瞬間、主役になる |
| **メモリ** | 関係するときだけ | 事実 |

**スキルがよく効くのは、呼ばれた瞬間に他の500行と競争していないからです。** 300行のスキルのほうが、`CLAUDE.md` に足した10行より確実に守られます。

`CLAUDE.md` が短くなるのは**結果であって、目的ではありません。**

#### そして、そこは速度に効かない

仮に分割で選択的に読まれたとしても、得られるものは誤差です。**ルール464行はトークンにして1万に届きません。** 一方、ゲートがエージェントをもう1周させれば**1〜2分**（7章）。

| 払うもの | 得るもの |
|---|---|
| 構成を考える時間 | **誤差** |
| 分け方を維持する手間 | **誤差** |
| 腐る場所が10倍 | **誤差** |

**これをオーバーエンジニアリングと呼びます。** コードで同じことをしたらレビューで止まるのに、設定だと通ってしまう。

実際、自分のルールの1つ（`agents.md`）は**存在しないディレクトリのエージェントを10個紹介し続けていました**（9章）。分けるほど、腐る場所は増えます。

### 誤解2：短く簡潔に書くほど効く

もうひとつ、逆になっている話があります。**抽象的なルールを短く書くより、具体例を長く書くほうが効きます。**

たとえば「gitの操作は慎重に」と書いても、何も起きません。実際に書いてあるのはこちらです。

> `git add` してから別の操作を挟んでコミットしない。2026年8月19日に、約340行が無関係なコミットに巻き込まれた。インデックスはセッション間で共有されているため。`git commit -- <paths>` を使う。

**長いです。でもこちらは効きます。** 何が起きたか、なぜ起きたか、代わりに何をするかが全部あるからです。抽象的な一行は、解釈の余地が大きすぎて何も決めません。

**「短く書け」を守って情報を削ると、効かない一行が残ります。**

### 誤解3：長く書くと、維持が大変になる

ここが一番言いたいところです。

上のような記述を、人間が手で書いて維持するのは無理です。**そもそも自分で書いていません。** 失敗した直後に「いまのを覚えといて」と言っただけで、Claudeが状況をまとめて書いています（3章）。

だから「長く書くと大変」という前提自体が成り立ちません。**長さのコストを払っているのは自分ではありません。**

### 情報のほとんどは、自分には関係ない

「〜が効かない」「〜しないと動かない」という記事は無数にあります。そして**多くは、書いた人の環境では本当に起きています。** 嘘ではありません。

問題はそこではありません。**1つの環境で起きたことが、そのツールの仕様として書かれることです。** 読む側には、それが自分に当てはまるのか判断する材料がありません。

自分の環境では、ルールは10ファイルとも毎回読み込まれています（9章で確認済み）。もし「ルールは効かない」という記事を真に受けて設定を組み直していたら、**効いているものを自分で壊していたことになります。**

だから、こうしています。

- **「仕組み」が書いてある記事だけ読む。** どこで何が起きるのかが書いてあれば、自分の環境で確かめられます
- **「こうしないと動かない」という作法は、確かめるまで採用しない**
- **確かめるのは5分で終わります。** ルールが効いているか知りたければ、わざと違反する状況を作って、止まるかどうかを見ればいい

これは正しいか間違っているかの話ではなく、**時間の使い方の話です。** 他人の環境の話を10本読む時間で、**自分の環境を1回測ったほうが、確実な答えが手に入ります。**

そして測った結果は、そのままメモリに入れておけます（4章）。**次に同じ話が流れてきたときには、もう答えを持っている状態になります。**

### 本当の損失は、自分の設定ができないこと

失う時間の話をしましたが、**いちばんの損失はそこではありません。**

作法を追いかけて設定を組み替えていると、あとに残るのは、**他人の環境で起きた問題への対策の寄せ集め**です。自分が毎日どこで詰まっているかとは、何の関係もありません。

そして自分で作っていないので、**中身が分かりません。** 効いているのかも判断できないし、おかしくなっても直せない。9章に書いた `agents.md` のように、**壊れていることにすら気づけません。**

自分のメモリ352件に意味があるのは、件数ではありません。**全部、自分が実際にやらかしたことだからです。** 他人の352件をそのまま持ってきても、自分は一度も助かりません。

**記事を読んで設定を組み替えている時間があれば、今日うまくいかなかったことを1つ直したほうがいい。** それが3章の話で、この記事で一番言いたいことです。

## 9. 設定は、静かに古くなる

この記事を書くために自分の設定を見直して、**壊れているものが見つかりました。**

`~/.claude/rules/common/agents.md` に、10個のエージェントの表が書いてあります。「複雑な機能は planner を使え」「コードを書いたら code-reviewer を使え」と。置き場所は `~/.claude/agents/` と書いてある。

**そのディレクトリは存在しません。** いつ消えたのかも分かりません。実際に使えるエージェントはプラグイン側にあって、名前も違います。**globalのルールが、空の場所を指し続けていた**わけです。

**壊れたコードはエラーを出しますが、壊れたルールは何も言いません。** 静かに効かなくなって、こちらは効いているつもりで使い続ける。しかも消えずに残るので、**他のルールを薄め続けます**（8章）。

対策は、**参照を書くときは実在を確かめること**、そして時々読み返すことだけです。この記事を書いたのが、その読み返しになりました。

### 絶対に守らせたいものを、ルールに書かない

**「守ってほしい」ものはルールでいい。「守られないと事故になる」ものは、ルールに書いてはいけません。** それはフックかスクリプトの仕事です（6章）。

ルールに書いた禁止事項は**561行のうちの1行**ですが、フックは1行でも拒否は拒否です。**ルールを増やして守らせようとするのは、効かない層に仕事を積むことになります。**

## 10. 設定は、GitHubに置く。ただしコピーで置くと古くなる

ここまでの設定は全部、**1台のPCの`~/.claude/`というフォルダの中**にしかありません。5ヶ月ぶんの試行錯誤が、ディスクが飛んだら消えます。

なので自分は、dotfilesのリポジトリに入れています。`shell/`や`nvim/`や`tmux/`と並べて`claude/`を置いて、`install.sh`で新しいマシンに展開する。ここまでは普通の話です。

**問題はバックアップの有無ではなく、どう繋いでいるかでした。**

自分の`install.sh`は、`.zshrc`も`.gitconfig`も`nvim/`も`tmux.conf`も**シンボリックリンク**で繋いでいます。編集した瞬間にリポジトリのファイルが変わるので、ズレようがありません。ところが`~/.claude/`だけは`mkdir -p`で、**中身は実体のコピー**でした。

この記事を書きながら差分を取って、それがどうなっていたか分かりました。

| | リポジトリ | 実際に動いているもの |
|---|---|---|
| `settings.json` | 4月5日 | 9月5日 |
| deny（禁止コマンド） | 12個 | 16個 |
| フック | 4個 | **7個** |
| スキル | 58個 | 71個 |

**6章で「これだけは絶対に譲れない層」と書いたフックが、バックアップには半分も入っていませんでした。** 5ヶ月かけて足したものが、全部あとから足したものだからです。

スキルも2つズレていて、片方は**実際に動いているほうにだけ44行**ありました。1ヶ月ぶん直した内容が、一度もリポジトリに戻っていなかったわけです。

### 古いバックアップは、無いより悪いことがある

もう片方のスキルは、もっと厄介でした。

リポジトリ側には、**開発用DBを親ブランチからリセットする手順**が残っていました。実際に動いているほうでは、その手順は消してあります。8月28日に本番DBが別サービスへ移って、リセット元が「本番ではない、その日で凍ったスナップショット」になったからです。いま実行すると、**開発用DBが黙って過去に巻き戻ります。**

つまり新しいマシンでこのリポジトリを展開していたら、復元されるのは古い設定ではありません。**DBを壊す手順書が復元されて、Claudeはそれに従います。**

**バックアップが古いというのは、単に整理されていないという意味ではありません。** 間違った指示が、正しい指示の顔をして戻ってくるということです。

### だからコピーではなくリンクにする

原因ははっきりしています。**コピーで置いたものは、自分が「リポジトリに戻す」のを覚えていることに依存しています。**

そして3章で書いたとおり、設定を直すのは**うまくいかなかったその瞬間**です。その瞬間に考えているのは目の前の失敗のことで、dotfilesリポジトリのことではありません。**思い出すことに頼る仕組みは、いずれ必ず外れます。**

`~/.claude/`の中で、リンクにして困らないものはリンクにする。`settings.json`、`CLAUDE.md`、`skills/`、`commands/` — 全部そうです。

置かないものもはっきりしています。

- **トークンや認証情報**（MCPの接続情報は`~/.claude.json`にあります。これは絶対に入れない）
- **セッションの履歴やキャッシュ**（`projects/`、`history.jsonl`、`shell-snapshots/` など。移植性がない）
- **プラグイン経由で入れたスキル**（マーケットプレイスから入れ直せます。自分の71個のうち13個がこれです）

**残るのは、自分が書いたものだけです。** そしてそれが、消えたら二度と戻ってこない唯一の部分でもあります。

## まとめ

- **設定は、日々の失敗から1つずつ作る。** 座って設計するものではありません。自分がどこで詰まるかは、詰まるまで分からないからです
- **層に分けるのは、優先度をつけるため。** 事故になるものはフックへ。手順はスキルへ。事実はメモリへ。全部を`CLAUDE.md`に積むと、全部が同じ重さになります
- **近道はありません。** 「これをコピーすれば全部解決する設定」は存在しません。他人の設定は、他人の失敗への対策だからです

**自分の環境を直せるのは、自分だけです。** うまくいかなかったその瞬間に、1分だけ使って直す。それを習慣にするだけです。

自分はそれで、**月100コミットから月270コミットになりました。** 賢くなったわけではなく、同じ説明を二度しなくてよくなっただけです。
