## この記事で、何ができるようになるか

Claude Codeを6ヶ月、毎日使って分かったことを1本にまとめたものです。**コピーして使う設定集ではありません。** むしろ逆で、他人の設定は効かない、という話をします。

読んで、そのとおりにやると、**同じClaude Codeがこう変わります。**

- **返ってくる答えの精度が上がります。** Claude Codeが何を覚えていて何を忘れるのかが分かると、必要な情報の渡し方が決まるからです
- **出した指示が、守られるようになります。** 同じ一行でも、`CLAUDE.md`に書くかフックにするかで守られる確率が変わります
- **同じ失敗が、二度目で消えます。** 詰まった瞬間に1〜2分だけ使って、設定に変える。続けるのはそれだけです
- **Claudeが間違えても、事故になりません。** 本番DBを消す、自分の名前でSlackに投稿する——取り返しのつかない操作は、お願いではなく仕組みで止めます

**そして、ここまでできるようになります。**

「このJiraのチケットをやっておいて」と投げるだけで、**Claudeが裏で最後まで走ります。** 必要な文脈を自分で取りに行けるタスクなら、**やりとりは一度も発生しません。** 追加の指示も、途中の軌道修正も、「そこはそうじゃない」もなし。ブランチが切られ、実装が入り、**そのままでマージできるPRが上がっています。** こちらがやるのは、中身を確認してapproveを押すことだけです。

モデルが賢いからではありません。**そこに必要な情報が全部揃っている状態を、設定として先に作ってあるからです。**

### 記事の構成

**前半が使い方、後半が守り方です。** 1章だけでも役に立ちます。

- **1〜2章**：コンテキストの仕組みと、何をどこに置くか。そして設定を1〜2分で足す手順
- **3〜4章**：事故を止める3段構えと、6ヶ月ぶんの設定を消さずに置く方法

### なぜこれが書けるのか

Claude Codeの設定を触り始めて、6ヶ月。**GitHubのコミットが、月100から月881——8.8倍になりました。**

![GitHubのコントリビューショングラフ。設定を触り始めた春から急に濃くなっている](/images/github-contributions-2026.png)

モデルが賢くなったからではありません。**同じ説明を二度しなくてよくなっただけです。** 手元にあるのはこれです。

| 層 | いまの数 |
|---|---|
| 記憶（メモリ） | **358件**（15プロジェクトぶん） |
| スキル | **72個**（うち59個は自作） |
| ルール | **10個** |
| MCPサーバー | **10個** |
| フック | **5つ** |
| 権限ルール | **95個**（許可79 / 拒否16） |

**座って設計したものは、ひとつもありません。** ただ、ゼロから始めたわけでもありません。

出発点にしたのは[ECC](https://github.com/affaan-m/ECC)です。スキル292個・エージェント・ルールを丸ごと1式にしたOSSで、**GitHubで25万スター**。作者はAnthropic共催のハッカソン優勝者です。

**価値があったのは、コードよりガイドのほうでした。** Claude Codeの使い方を深いところまで説明したガイドが3本ついていて（**日本語訳あり**）、書いてあるのは「何が書けるか」ではなく「**なぜそう書くのか**」です——フックをどこで使い、スキルをどの粒度で切り、権限をどこまで開けるか。その判断の理由がここまでまとまっているものは、他に見当たりませんでした。

そのあとは、記事も動画も追いかけるのをやめました。**自分がどこで詰まるかは、自分のリポジトリにしか出てこないからです。** いまECCは外していて、スキル72個のうちECC由来は**0個**。**土台は要ります。要らないのは、土台に住み続けることのほうです。**

## 1. 最低限これだけ：Claude Codeは、文脈が全部

**本当に必要な知識はここだけです。** ここが分かっていないと、あとの章はただの作法に見えます。

### 前提は2つ

**1. Claudeが知っているのは、文脈（コンテキスト）に載っているものだけ。**

前回の会話は覚えていません。毎回ゼロから始まります。「前は分かってくれたのに」は起きません。

ここから、**コードはできるだけClaudeに書かせてください**という結論が出ます。自分で手を入れたファイルは、Claudeの文脈に載っていません。**本人は、さっき自分が書いた状態のままだと思っています。** その前提の上に次の変更が積まれるので、噛み合わなくなります。

手で直したなら、**会話を再開する前にそれを伝えます。** 手で書いたコード、別のターミナルで叩いたコマンド、GitHubの画面から消したブランチ——**Claudeを通さずにやったことは、言わなければ存在しません。**

**2. 文脈は有限で、埋まるほど悪くなる。**

文脈に載るものは、すべて**トークン**という単位で数えられます。文章を細かく区切ったもので、日本語なら1文字が1トークン前後です。**Claudeが一度に読める量にも、契約プランで使える量にも、このトークンで上限があります。**

埋まっていくと、3つ起きます。

- トークンを多く使うので、**プランの上限に早く届いて、しばらく使えなくなる**
- 読む量が増えるので、**返事が遅くなる**
- 大事な指示が埋もれて、**`CLAUDE.md`に書いたことを守らなくなる。** 前に言ったことも取り違える

3つ目がいちばん厄介です。エラーが出るわけではないので、**設定が効かなくなったことに気づけません。**

かといって必要な情報が消えれば、今度は筋を見失います。**入れすぎても、足りなくてもダメです。**

**どれだけ埋まったかは、画面の下に出せます。**

![ステータスラインに、作業ディレクトリ・ブランチ・モデル名と、文脈の使用率がctx:13%と表示されている](/images/statusline-context.png)

`ctx:13%`は、**読める上限のうち13%が埋まっているという意味です。** 50%を超えると黄色、80%を超えると赤にしてあるので、上の3つが効き始める前に気づけます。**最初から出ているものではなく、設定で足すものです**（4章のリポジトリに入れてあります）。

つまり**Claude Codeを使うとは、ほぼ文脈を管理することです。** 方法は3つ。

---

### 管理①：タスクで分ける

`plan.md`をリポジトリに置いて状況を書き続ける方法をよく見ます。**自分は書いていません。セッションそのものが状態だからです。**

やっているのは**タスク1つにつき、セッション1つ**。それだけです。

- **別の用事は新しいセッションで、終わっていないタスクは同じセッションで。** 混ぜると、さっきまで直していたバグの話とこれから書く機能の話が同じ文脈に並び、**Claudeにはどちらも「いま関係のある話」に見えます。** 逆に途中で開き直せば、何を試して何がダメだったかが消えて、また一から説明することになります
- **`/rename`で名前を付けておく。** あとで`claude --resume`を叩くと名前の付いた一覧が出るので、そこから選べばその会話に戻れます。付けていないと、どれがどれだか分かりません
- **`/compact`は、自分から走らせる。** 会話を要約して圧縮するコマンドです。放っておくと**作業の真っ最中に自動で走って、いま一番必要な情報から消えます。** **`ctx`が黄色（50%）になったあたりで区切りを探し、** コミットを切った直後などに自分で走らせます

そして、**セッションは1つとは限りません。** Claudeが考えている数分間、こちらは待つだけになります。その時間に別のタスクのセッションを開けば、2つが同時に進みます。多い日で9個動かしています。

ただし、同じ作業ディレクトリで並行させると**お互いのファイルを踏みます。** `git worktree`でディレクトリごと分けるのが前提です。**並列そのものの回し方は、それだけで1本になるので別記事で書きます。**

---

### 管理②：置き場所で分ける

同じ一行でも、**どこに置くかで守られ方が変わります。** 置き場所は6つ。**強い順**に並べます。

| 置き場所 | どこまで守られるか | 何を置くか |
|---|---|---|
| 権限 | **通らない。** ファイルを読む・コマンドを走らせる、その入口で弾かれる | 通す／通さないの線引き。`deny`の道具は**そもそも見えない** |
| フック | **必ず走る。** 条件が合えば、モデルの都合と無関係に | 止めたい操作。忘れると困る手順 |
| スキル | 呼ばれた瞬間、**それが主役になる** | 繰り返す**手順**。3回目に同じ指示を書いたら、これ |
| 記憶（メモリ） | 関係するときだけ開かれ、**その場では効く** | 一度ハマって分かった**事実**。「このDBの236msは仕様」 |
| ルール | 毎回載るが、**他の全部と競争する** | 分野ごとの決まりごと |
| `CLAUDE.md` | 毎回載るが、**他の全部と競争する** | 自分が決めた掟。**本当に毎回関係することだけ** |

ここで、**「全部`CLAUDE.md`に書いておけば毎回読んでくれる」と思いたくなります。** 毎回載るのは本当です。でも、**載ることと守られることは別です。** 500行の中の1行は、500分の1の重さになります。**300行のスキルのほうが、`CLAUDE.md`に足した10行より確実に守られます。**

上2つだけが、性質からして違います。

> 上の2つは**拒否**。下の4つは**お願い**。

だから、**破られたら事故になることは、いちばん上の2つに置きます**（3章）。

そして**この6つを、自分で書くことはありません。** 全部Claudeが書きます。自分がやるのは「いまのを設定に入れて」と言うことだけで、**どこに置くかもClaudeが決めます。**

つまり覚えることは、**こういう置き場所がある**ということだけです。あとは頼めば作ってくれますし、**出てきたものが妥当かどうかは、この6つを知っていれば判断できます。**

---

### 管理③：足りない情報を、取りに行けるようにする

①②は「載せすぎない」話でした。ここは逆です。**コードを書くのに必要な情報は、コードの中だけにありません。**

**MCPやCLI経由で読ませるもの：**

- **コード**：既存の実装と規約
- **チケット**：何を作るのか
- **Slack**：**なぜそう決まったのか**
- **Notion**：仕様と背景
- **Figma**：デザインの実際の値
- **AWS**：動いている環境の設定

**チケットだけ読んで書いたコードは、だいたいどこかが足りません。**

ここまでは全部ドキュメントです。**書かれていない事実のほうが、実は多い。** それは、動かさないと出てきません。

**動かして取りに行かせるもの：**

- **Chrome**：ブラウザを操作させて、実際の表示・コンソールのエラー・通信の中身を見せる
- **iOSシミュレータ・Androidエミュレータ・実機**：ビルドを入れて、アプリが本当にどう動くかとログを読ませる
- **スクリプト**：本番のデータ件数やAPIの返りを、自分で叩いて確かめさせる

効くのは、**壊れていてもエラーが出ない類のバグがあるからです。** 顔認識のベクトルが壊れていたとき、**例外は1つも出ませんでした。** 型は通り、テストも通り、ログも静か。おかしいと分かったのは、実機で数字を測ったときだけでした。

> コードを読んで分かることは、コードに書いてあります。**書いていないことは、動かさないと出てきません。**

繋ぐのと、結果を貼るのは違います。**ログを貼れば1万行が以後ずっと文脈に残りますが、繋いでおけば必要になった時点で、必要なぶんだけ載ります。**

だから「AIから触れるか」は、サービス選びの基準になります。**GUIしかないサービスは、結局こちらがスクリーンショットを貼ることになるからです。**

---

### 足りないのは、言い方ではなく情報です

**うまくいかないとき、足りないのは言い方ではなく情報です。** 言い換えを10回試すより、足りない1つを渡すほうが速い。

渡し方で一番手軽なのが**スクリーンショットと動画**です。**ずれたUI、エラー画面、期待と違う表示は、文章で説明するより貼るほうが速くて正確です。** 「ボタンが少し下にずれている」を文章で伝えるのは、意外と難しい。そして**動きが関わるものは、静止画1枚では足りません。** アニメーションや遷移がおかしいときは、画面を録って渡すほうが早く伝わります。

そして**書かせる前に、相談に使うこと。** いきなり実装させると、方針の間違いをコードの形で受け取ることになります。

### 新しい画面は、実装の前に3〜5案を並べさせる

画面を新しく作るときに一番高くつくのは、**1案に数時間かけてから作り直すこと**です。

なので先に、**案を3〜5つ並べたHTMLを1枚作らせます。** artifactとして出てくるので、ブラウザで開けば**それぞれの画面が実際の見た目のまま横に並びます。** 実装ではないので数分で出てきますし、並べて見れば「これは違う」が一瞬で分かる。決まってから、はじめて実装に入ります。

**選ぶのは実物を見てから、というだけの話です。** 頭の中で比べるのと、並べて見るのとでは精度が違います。

## 2. 作り方は、ひとつだけ

この記事に出てくる設定は、**全部、失敗した直後にその場で足したものです。**

やることは1つ。

> 失敗したら、**そのセッションのまま**「いまのを設定に反映して」と頼む。

実例です。同じリポジトリで複数のセッションを動かしていたら、**お互いの変更を踏むようになりました。** 2つのセッションが同じファイルを書けば、**エラーも出ないまま片方が消えます。**

そのセッションのまま「これを防ぐ設定を入れて」と頼んで出てきたのが、**worktreeの外でコードを書こうとした瞬間に止まるフック**です。`CLAUDE.md`に「worktreeで作業する」と書くのでは足りません。だいたい守られますが、**事故はその残りの数%で起きます**（3章）。

**それ以来、同じ壊れ方はしていません。**

---

### なぜ「その場」なのか

その理由は3つです。

- **材料が、そこにしかないからです。** 自分が何を指示したか、Claudeがどこを勘違いしたか、結局どう直したか——全部そのセッションに残っていて、**Claude自身がそれを見ています。** 翌日に手元にあるのは失敗ではなく、**失敗の要約**です
- **書いたルールが効くかどうか、その場で試せます。** 「これがあったら、さっきのは防げたか」を実際に当てられます
- **翌日にやろうとすると、大体やりません。**

---

### 厳密に読まなくていい

これが続く理由です。

- かかる時間は**1〜2分**
- 読み方は、**ざっと見て方向が合っていればいい**
- 間違っていたら、**次に同じ失敗をしたとき直す**

**一度で正解にしなくていい。** 失敗のたびに近づけばいい。

---

### やってはいけないのは、そのまま進むこと

「これ効かないな」と思って、直さずに次へ行く。**まずいのはこれだけです。**

そして、これが「AIは使えない」の正体だと思っています。

> 「ちゃんと答えてくれない」
> 「AIは信用できない」
> 「結局、自分で書いたほうが速い」

体感で9割以上、原因は同じところにあります。**うまくいかなかったその瞬間に、何も直していないことです。**

- **直さないと**、3ヶ月後も**初日と同じ精度**のClaudeを使っています
- **毎回1分直すと**、同じ失敗が**二度目で消えます**

この差が、6ヶ月で記憶358件とスキル59個になりました。

直したのに同じ失敗が続くなら、そのときだけ腰を据えて読み返す。**定期的な棚卸しは、それくらいの頻度で十分です。**

## 3. セキュリティ：守ってほしいことは、お願いせずに強制する

Claudeには、ほぼ全部つないであります。Slack、Notion、Gmail、Jira、AWS、**本番のデータベース。** しかも読むだけでなく、**書ける状態で**です。

そうしていられるのは、**6ヶ月で一度も、取り返しのつかないことが起きていないから**です。データベースは消えていません。リポジトリも、Notionのページも、ファイルも消えていません。

小さいことなら、何度もありました。**頼んでいないSlackスレッドへの返信や、Notionへのコメント。** そのたびに消して、同じことが起きないように設定を足しています。**起きていないのは、取り返しのつかないほうだけです。**

最初から安全だったわけではありません。**入口はECCに入っていた設定で、そのあとは事故が起きるたびに1つずつ足しています。** この章は、その中身です。

### まず、危ない道具は渡さない

設定を書く前に、**そもそも渡さないのが一番強い**です。道具が来なければ、事故のしようがありません。

- **本番DBは、読み取り専用のロールでつなぐ**
- **書き込みが要らないサービスは、読み取り専用のトークンで作る**
- **使っていないサービスは、そもそもつながない**

**権限は、あとから足すほうが簡単です。** 足りなければすぐ気づきますが、**余っていることには気づきません。**

とはいえ、**書き込みが要るものもあります。** Notionにはページを書いてほしいし、Slackの下書きも作ってほしい。**そこは渡したうえで、次の段で絞ります。**

---

### 残りは、3段構えで止める

渡した道具を止める仕組みは、3段に分けています。

#### 1段目：拒否リスト

Claudeがコマンドを走らせる、ファイルを読む、書く——こうした操作は`Bash`や`Read`といった**ツール**の呼び出しとして実行されます。`settings.json`の`deny`に形を並べておくと、**その呼び出しが実行前に弾かれます。**

```json
"deny": [
  "Bash(rm -rf *)",
  "Bash(git push --force*)",
  "Read(**/.env)"
]
```

どれも「うっかり」が取り返しのつかないものです。**書いた形に当たれば、必ず止まります。** 「今回は大丈夫」とClaudeが判断する余地はありません。

> Permission rules are enforced by Claude Code, not by the model.

公式ドキュメントの一文です。**止めているのはモデルではなく、Claude Code自身。** だから`CLAUDE.md`に「消さないで」と書くのとは、効き方が違います。

自分の環境では拒否が16個、許可が79個。**拒否を厳しくするほど、許可は広くできます。**

#### 2段目：フック

拒否リストが見られるのは「コマンドの形」だけです。**フックなら、状況を見て判断できます。**

フックは、**決まったタイミングで自動的に走るスクリプト**です。呼び出しの中身がJSONで渡ってきて、**返した内容で通るか止まるかが決まります。**

| いつ走るか | よくある使い方 |
|---|---|
| `PreToolUse` | ツールを呼ぶ**直前**。危ない操作を止める |
| `PostToolUse` | ツールが終わった**直後**。書き換えたファイルを自動で整形する |
| `UserPromptSubmit` | こちらが入力を送った直後。毎回の前提を足す |
| `SessionStart` | セッション開始時。いまの状態を読み込ませる |
| `SessionEnd` | セッション終了時。その日の成果を保存する |

止めるのに使うのは`PreToolUse`です。

```bash
# 「Bashツールを呼ぶ直前（PreToolUse）に走らせる」と settings.json に登録したスクリプト
#
# Claudeが「git push origin main」を実行しようとすると、こう渡ってくる：
#   {"tool_name":"Bash","tool_input":{"command":"git push origin main"}}

input=$(cat)
cmd=$(printf '%s' "$input" | jq -r '.tool_input.command')   # ← "git push origin main"

# いま main にいて、そこへ push しようとしていたら止める
if [[ "$cmd" == *"git push"* && "$(git branch --show-current)" == "main" ]]; then
  jq -nc '{hookSpecificOutput:{hookEventName:"PreToolUse",
           permissionDecision:"deny",
           permissionDecisionReason:"mainは本番。マージは人間がやる"}}'
fi
```

**止めた理由は、そのままClaudeに返ります。** だから別の抜け道を探すのではなく、なぜ止まったかを踏まえて次へ進みます。見ているのは、**どのリポジトリか・いまどのブランチか・コマンドがどの形か**です。

そして**フックは、止めるだけの仕組みではありません。** 条件が合えば必ず走るので、**忘れると困る手順**も任せられます。自分はセッションが終わるたびに、その日増えた記憶をリポジトリへコピーさせています（4章）。**頼んでいないので、書き忘れが起きません。**

#### 3段目：リポジトリ側のスクリプト

gitが持っている仕組みです。コミットの直前に`.husky/pre-commit`が走り、**0以外を返せばコミットは作られません。**

```bash
# .husky/pre-commit
BRANCH=$(git rev-parse --abbrev-ref HEAD)
if [[ $BRANCH =~ ^(main|master) ]]; then
  echo ">> mainへの直接コミットは禁止"
  exit 1                      # 0以外を返すとコミットが中止される
fi
npx lint-staged               # 型エラーとlintエラーもここで止まる
```

上の2段との違いは、**これがClaude Codeの設定ではないこと**です。走らせているのはgitなので、**人間が手で叩いても同じように止まります。**

つまり、**Claudeを信用するかどうかという話から降りられます。**

### 外のサービスは、つないだ瞬間に書ける

MCPは、読むためにつないだつもりでも**書く道具と消す道具が一緒に来ます。** 自分の環境で数えたら、**書き込み・削除できる道具が94個**ありました。Neonの`delete_project`はプロジェクトごと消せますし、Slackの`conversations_add_message`は**自分の名前でメッセージが飛ぶ**ということです。

渡した道具は、`settings.json`で2通りに絞ります。

- **`deny`で消す。** 名前を書いた道具は**Claudeの文脈から消えます。** ブロックされるのではなく、最初から見えない
- **`ask`で毎回聞かせる。** **自動承認モードでも必ず止まります**——`allow`に入れてあっても`ask`が勝ちます

```json
"deny": ["mcp__neon__delete_project", "mcp__claude_ai_Google_Drive__share_file"],
"ask":  ["mcp__neon__run_sql", "mcp__slack__conversations_add_message"]
```

**ハマりどころがひとつ。** `mcp__`のルールに括弧を書いて引数で絞ろうとすると、**そのルールは黙って読み飛ばされます。** 名前で止めるものだと思っておくのが安全です。

#### 鍵は渡さない。通り道だけ渡す

本番のデータは見たい。**でも「見られる」と「書ける」が同じ権限で来るのが嫌でした。** そこでスクリプトを1本挟んでいます。

```bash
bash scripts/prod-sql.sh "SELECT count(*) FROM community_event;"
```

**接続情報はスクリプトが持ち、認証情報のファイルは`deny`で読めなくします。** 使えるが、見えない。そしてクエリは`BEGIN READ ONLY`の中で走るので、**INSERTもDDLもPostgres自身が拒否します。** 書き方を変えても抜けられません。

地味に大事なのが、**この安全な道が`allow`に入っていて、確認なしで通ること**です。**安全なほうが面倒だと、人もAIも結局それを避けます。**

#### 順番は、逆から考える

「何を止めるか」から入ると際限がありません。**「これが起きたら本当に困る」を数えるほうが速い。** 本番のデータが消える。自分の名前で外に何かが送られる。共有ドキュメントが書き換わる。**この3つは、だいたい誰でも同じです。** そこだけ`deny`と`ask`で塞いで、残りは動かしながら足していけばいい。

並行で何セッションも動かしていると、**全部の出力を自分で見ることは物理的にできません。** レビューで捕まえるのではなく、**そもそも不正な状態を作れないようにする。** CIやpre-commitがずっとやってきたことと同じで、**効く相手が増えただけです。**

## 4. 設定は、GitHubに置く。ただしコピーではなくリンクで

ここまでの設定は全部、**1台のPCの`~/.claude/`の中**にしかありません。ディスクが飛べば6ヶ月が消えます。なのでdotfilesのリポジトリに入れています。

**置き方はコピーではなく、シンボリックリンクです。**

```bash
ln -sfn ~/dotfiles/claude/settings.json ~/.claude/settings.json
```

実体は自分のリポジトリ側にあって、`~/.claude/`からリンクを張るだけ。**設定は自分の好きな場所に並びますし、直した瞬間にリポジトリのファイルが変わります。** コピーだと、戻すのを忘れた時点で古くなります。

例外は**記憶**です。`memory/`はClaude Codeがそのプロジェクトを初めて触ったときに自分で作るので、まだ無いディレクトリにはリンクを張れません。ここだけはセッション終了時のフックにコピーさせています。

そして**トークンと認証情報は、絶対に入れません。**

### 出発点として使えるものを置きました

自分のdotfilesは仕事のものが混ざっているので公開できません。**汎用の部分だけ切り出したものを置いてあります。**

https://github.com/jordisantamaria/claude-code-starter

- **`claude/settings.json`**：権限（許可68／拒否16）、フック、ステータスライン
- **`claude/hooks/`**：本当に止まるフック3つ
- **`claude/skills/`**：git・PR まわりのスキル4つ
- **`install.sh`**：`~/.claude`に**リンクで**展開する

**これをそのまま使っても、自分の設定にはなりません。** 入れたら、まず壊してください。使わないスキルを消して、合わないルールを書き換える。そして**うまくいかなかったその瞬間に、その場で直す**（2章）。**それだけが本体で、ファイルはそれが溜まる場所です。**

## 5. あえて書かなかったこと

設定の話でよく見かけるのに、**この記事で扱わなかったものがあります。効果が小さいからです。**

- **「AIに効く言い方」を覚えること。** 呪文集のようなプロンプト集が出回っていますが、**普通の日本語で、同僚に頼むように書けば通じます。** キーワードも言い回しも、覚えるものはありません
- **どのモデルを使うか。** いちばん強い最新のものを使ってください。コードの品質が変わります。上位モデルの中でタスクごとに選び分けても、差はほとんど出ません。**ただし、トークンを節約しようと安いモデルに落とすのは別の話で、そこははっきり落ちます。** そのうえ切り替えは**元に戻すのを忘れる**ので、手間だけが残ります
- **`.claude/`のフォルダ構成をどう分けるか。** 自分のルールは10ファイルに分かれていますが、**10ファイルとも毎回まるごと読み込まれます。** 1つの長いファイルだったときと、載る量は同じです
- **設定を短く整えること。** 長くて構いません。まずいのは、短くしようとするほうです。削れば必要な情報まで一緒に落ちて、**返ってくるものが悪くなります。** 設定はClaudeに全部書かせて、こちらは中身が合っているかを見るだけ。整える作業に時間を使う価値はありません
- **フックを何の言語で書くか。** 手元で測ると`python3`の起動は約**10ms**です。Goで書き直しても体感は変わりません

**時間をかけるべきは、1〜4章のほうです。**

## まとめ

- **Claude Codeを使うとは、ほぼコンテキストの管理です。** 何をどこに置くかで、同じ内容でも効いたり効かなかったりします
- **設定は、うまくいかなかったその瞬間に足す。** 座って設計するものではありません。自分がどこで詰まるかは、詰まるまで分からないからです
- **層に分けるのは、優先度をつけるため。** 事故はフックへ。手順はスキルへ。事実は記憶へ。全部を`CLAUDE.md`に積むと、全部が同じ重さになります
- **近道はありません。** 他人の設定は、他人の失敗への対策だからです
