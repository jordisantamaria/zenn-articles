## 2. 全部を作った方法は、ひとつだけ

上の4つの層は、座って設計したものではありません。**全部、何かがうまくいかなかった直後に、その場で足したものです。**

やることは1つだけです。

> **失敗したら、そのセッションのまま「いまのを設定に反映して」と頼む。**

### なぜ「その場」なのか

**そのセッションにしか材料がないからです。**

失敗した直後のセッションには、自分が何を指示して、Claudeがどこを勘違いして、結局どう直したのかが全部残っています。**Claude自身がそれを見ています。** だから「いまのを記憶に書いて」と言えば、何が原因だったのかを自分でまとめられる。

そして、もっと大事なのはこちらです。**その場なら、書いたルールが効くかどうかを確かめられます。** 失敗した本人がそこにいるので、「このルールがあったら、さっきのは防げたか」を実際に当ててみることができる。

翌日にやろうとすると、この2つが両方なくなります。**判断する材料がないまま、自分の記憶を頼りにルールを書くことになる。** それは失敗そのものではなく、失敗の要約に対して書いたルールです。効くかどうかも、次に同じ失敗をするまでわかりません。

ついでに言うと、翌日にやろうとすると大体やりません。

### 厳密にレビューしなくていい

これが続けられる理由です。かかる時間は1〜2分で、**書かれた内容を全部読んで厳密に確認する必要もありません。** ざっと目を通して、方向が合っていればそれでいい。

間違っていたら、次に同じ失敗をしたときにまた直せばいいだけです。**設定は一度で正解にする必要がなくて、失敗のたびに近づいていけばいい。**

### やってはいけないのは、そのまま進むこと

「これ効かないな」と思って、直さずに次の作業に移る。**これだけが本当にまずいやり方です。**

そして、**これが「AIは使えない」の正体だと思っています。**

「Claudeがちゃんと答えてくれない」「AIは信用できない」「結局自分で書いたほうが速い」。よく見る感想ですが、体感では9割以上、原因は同じところにあります。**うまくいかなかったその瞬間に、何も直していないことです。**

うまくいかない → 文句を言う → そのまま次へ。これを繰り返すと、環境は初日のままです。**3ヶ月使っても、初日と同じ精度のClaudeを使い続けることになります。** そして「やっぱりAIはこの程度か」という結論になる。

逆に、失敗のたびに1分だけ使って直していれば、**同じ失敗は二度目で消えます。** AIが賢くなったわけではありません。こちらが同じ説明を二度しなくてよくなっただけです。

不満を持ったまま使い続けるか、その場で1分だけ直すか。**差はそこだけで、この差が5ヶ月で記憶352件とスキル71個になりました。**

そして、直したのに同じ失敗が続くようなら、そのときは腰を据えて設定を読み返す。定期的な見直しは、それくらいの頻度で十分です。

## 3. 忘れることは、記憶に置く

一番効いた層がこれです。

Claudeは会話が終われば全部忘れます。次のセッションでは、また同じ前提から説明することになる。

**こちらがやることは1つだけです。「前も同じ説明をしたな」と思った瞬間に、「これ覚えといて」と言う。** それだけです。

### ファイルは自分で作っていません

置き場所も形式もECCの設定が決めてくれるので、**自分で設計したものではありません。**

- 1ファイル1事実（352件あるのは、細かく切られているから）
- `MEMORY.md` が索引で、1件1行
- プロジェクトごとに独立。モバイルアプリの話が客先の作業に混ざりません

**メモリのファイルを手で書いたことは一度もありません。** 「覚えといて」と言うと、Claudeが置き場所を決めて、索引に足して、関連する記憶へのリンクまで張ります。

つまり、**この層を始めるコストはほぼゼロです。** 難しいのは仕組みのほうではなくて、その場で一言いうことのほうです。

### CLAUDE.mdとは役割が違う

`CLAUDE.md` は3リポジトリに置いていますが、そこに書くのは**自分が決めたルール**です。「mainはJordiがマージする」「作業はworktreeで」のような、そのリポジトリの掟。

記憶に入るのは逆で、**作業中に発見してしまった事実**です。書くのも自分ではなくClaudeです。

### なぜ記憶をCLAUDE.mdに全部書かないのか

352件を1枚のファイルにすると、**毎回そのファイル全部が文脈に載ります。** 今日の作業に関係あるのは3件なのに、残り349件ぶんのトークンを毎回払うことになる。

索引だけを読ませて、関係のあるファイルだけ開かせる。これなら件数が増えても、毎回のコストはほとんど変わりません。

### 実際に入っているもの

たとえばこの2件です。

> **worktreeを分けても、gitのインデックスは共有されている。** だから `git add` して後からコミットすると、別のセッションのコミットに自分のファイルが持っていかれる。コミットは `git commit -- <paths>` で。

> **シンガポールへの236msはバグではない。** DBに日本のリージョンがないので、サーバーとDBを同じ場所に置いた結果。遅いクエリを探し始める前に、まずpingを測る。

どちらも、**知らなければ半日溶ける類の話です。** そして一度溶かした人間しか書けない。ドキュメントに書いてあることは記憶に置きません。リポジトリを読めばわかることも置きません。**置くのは、コードにも履歴にも書いていないことだけです。**

## 4. 繰り返すことは、スキルにする

記憶が「事実」なら、スキルは「手順」です。

71個は、設計して作ったものではありません。**3回目に同じ指示を書いたとき**に作っています。作る基準はそれだけです。

| スキル | 何をするか |
|---|---|
| `/commit` | ステージ済みの差分を読んで、そのリポジトリの言語と形式に合わせたコミットメッセージを3案出す。選ぶだけ |
| `/solve` | チケットから、ブランチを切る→実装→push→Draft PR作成→worktreeの片付けまで通す |
| `/bg` | その `/solve` をバックグラウンドで走らせる。worktreeを先に作ってからサブのClaudeを起動するので、いまの作業を止めない |
| `/review` | PRでもローカルの変更でもレビューする。そのリポジトリの規約に合わせたチェックリストで、他のボットが拾わない「参照はあるのに実装がない」系まで見る |
| `/resolve-bot-review` | ボットのレビューを処理する。指摘ごとに「直す／意図通り／もう古い／間違い」を判定して、直すものだけ直してスレッドに返す |
| `/release-draft` | リリース用のDraft PRの説明文を、新しいコミットぶんだけ追記する。チェック済みのQA項目は絶対に外さない |

コードを書く以外のスキルもあります。この記事も `/zenn-article` を通して書いています。

### スキルにすると、うまくいった条件が残る

指示を毎回書き直していると、**うまくいったときの条件が残りません。** 前回なぜうまくいったのか、何を指定したからなのかは、3週間後には自分でも思い出せない。

スキルはそれを固定します。そして**失敗するたびに追記できるので、使うほど厳しくなります。**

### 実例：`/commit` が `git add` を禁止した理由

同じリポジトリでClaudeのセッションを何個も並行して動かしています。多い日で9個。

**gitのインデックスは、そのセッション全部で共有されています。** つまり `git add` してから別の操作を挟んでコミットすると、その隙に**別のセッションが自分のコミットを打ち、こちらがステージしたファイルを巻き込みます。**

2026年8月19日に実際に起きました。メール取り込み機能の約340行が、まったく関係のない `fix(share): ...` というコミットの中に入りました。コードは無事でしたが、**コミットメッセージが中身の半分を説明していない**状態です。

その場で `/commit` に1行足しました。

```bash
git commit -F - -- path1 path2   # git add してから commit しない
```

`git commit -- <paths>` はインデックスの残りを無視するので、他のセッションがステージしているものに触りません。**この失敗は、それ以来一度も起きていません。**

スキルにしていなければ、この判断は「あのとき何かあったな」で消えていました。

### 道具があることと、使うことは別

正直に書くと、**持っているだけでは効きません。**

Androidのdevビルドは、EASに投げると15分待つことになるのでローカルでやる、と決めています。それでもある日、**習慣でEASに投げました。** ルールがなかったからではなく、単に読まずに手が動いたからです。

そのときもその場で直しました。いまはCLAUDE.mdに書いてあります。

## 5. 外のサービスは、MCPでつなぐ

いま10個つないでいます。

| MCP | 何のために |
|---|---|
| **Neon** | 本番のDBに直接クエリを投げる。データを見ながら原因を追う |
| **PostHog** | エラーとイベントを、ダッシュボードを開かずに聞く |
| **Axiom** | ログとモニター |
| **Chrome** | 実際に画面を触らせて、コンソールとネットワークを読ませる |
| **Notion** | 仕様やタスクのページを読ませる。毎回コピペしない |
| **Figma** | デザインの値を直接取る。色を目視で写さない |
| **Slack** | 過去のやりとりを検索させる |
| **Gmail / カレンダー / ドライブ** | 予定と資料 |

### 何が変わるか：こちらが持っていかなくてよくなる

MCPがないと、**調べるのは全部こちらの仕事です。** 本番でエラーが出たら、自分でPostHogを開いて、スタックトレースをコピーして、貼り付けて、ついでにDBも見て、それも貼り付ける。Claudeは貼られたものしか見られません。

MCPがあると、**「本番でこのエラーが出ている、原因を調べて」で終わります。** ログを引いて、DBに当たって、必要ならブラウザで再現するところまで自分でやる。こちらがコンソールを開く回数が、はっきり減りました。

### 選ぶ基準は「AIから触れるか」

前の記事にも書きましたが、サービスを選ぶときの基準がひとつ増えました。

CLIやAPIやMCPがあるサービスは、調べるところまで任せられます。**GUIのコンソールしかないサービスは、結局こちらが画面を開いてスクリーンショットを貼ることになる。** 同じ機能でも、任せられる範囲がまったく違います。

### MCPとCLI、どちらでも動く。選べるならMCP

同じことはCLIでもできます。実際、GitHubは `gh` のCLIで済ませていて、MCPは入れていません。**両方使えるなら、基本はMCPを選びます。**

理由は精度です。

- **MCPのツールには型付きの定義がついてきます。** どんな引数があるかが最初から分かっているので、**存在しないオプションを推測で書いて失敗する、ということが起きません。** マイナーなCLIほどこれが効きます
- **返ってくるのが構造化されたデータです。** CLIの出力はテキストなので、パースの段階で取り違える余地があります
- 失敗したときに、何が起きたのかがエラーとして返ってきます

逆に、**CLIのほうがいい場面もあります。**

- パイプで繋いだり `jq` で加工したり、**組み合わせて使うとき**
- MCPサーバーが公開していない操作が必要なとき。CLIはそのサービスの全部が触れます
- MCPは繋いだ時点で定義が文脈に載りますが、**CLIは使うまで何も載りません**

なので実際は「MCPがあればMCP、細かい作業はCLI」の併用になっています。

### つなぐ前に、権限を絞る

ここが一番大事なところです。

**MCPは、自分の権限をそのままClaudeに渡します。** 本番のDBを消せるトークンを渡せば、Claudeも消せます。「AIが暴走したら」ではなく、**渡した時点でできる状態になっている**、という話です。

やっていることは3つです。

- **トークンは用途ごとに発行して、読むだけでいいものは読み取り専用にする。** ログや分析は読めれば十分なので、書き込みを持たせません
- **書き込みが必要なものは、分かったうえで開ける。** 自分のNeonは書き込みを有効にしていますが、その代わり破壊的な操作は必ず確認を挟む設定にしています。開けるなら、開けたと自覚して開ける
- **CLIも同じ**。`gh` や各種CLIのトークンも、必要なスコープだけにする

そして見落としやすいのがこれです。**権限の拒否リストと、MCPの権限は別の入口です。**

自分の拒否リストに書いてあるのは `Bash(rm -rf *)` のようなシェルとファイルの話で、**MCP経由の操作はそこを通りません。** シェルを固く閉じても、DBのMCPに書き込みトークンを渡していれば、そちらからは通ります。**層ごとに閉じる必要があります。**

ECCには `the-security-guide.md` という4,000語のガイドがあります。**何を許して何を止めるかは、ここで一通り学びました。** MCPを増やす前に読むものとしては、いちばん実用的だと思います。

### ただし、繋ぎすぎない

MCPは1つ繋ぐごとに、そのツールの定義が文脈に載ります。**関係ないMCPを10個繋いでおくのは、毎回使わない道具の説明書を持ち歩くのと同じです。**

いま繋いでいる10個は、どれも実際に週1回以上使うものだけです。試して使わなかったものは外しました。

## 6. 守ってほしいことは、お願いせずに強制する

ここが一番大事な層です。

**プロンプトやCLAUDE.mdに「mainにpushしないで」と書くのは、お願いです。** 守られる確率は高い。でも100%ではありません。そして事故というのは、その残りの数%で起きます。

**フックとスクリプトは拒否です。** 通らないものは通りません。

### 3段構えにしている

| 段 | 仕組み | 性質 |
|---|---|---|
| 1 | 権限の拒否リスト | Claudeのツール呼び出しの入口で止める |
| 2 | フック | コマンドの中身を見て、条件つきで止める |
| 3 | リポジトリ側のスクリプト | **Claudeが関係なく動く。人間が手で叩いても止まる** |

3段目が効くのは、**Claudeを信用するかどうかという話から降りられるからです。** リポジトリ側で不正な状態が作れないなら、誰が叩いても同じです。

### 1段目：拒否リスト16個

```
Bash(rm -rf *)
Bash(git push --force*)
Bash(git reset --hard*)
Bash(curl * | bash)
Read(~/.ssh/**)
Read(**/.env)
```

どれも「うっかり」が取り返しのつかないものです。逆に許可リストは73個あって、**毎回聞かれると邪魔なだけの読み取り系はそこに入れています。拒否を厳しくするほど、許可を広くできます。**

### 2段目：フックは条件つきで止められる

| フック | 何をするか |
|---|---|
| `block-prod-merge.sh`（91行） | 本番にデプロイされるリポジトリで、`main` へのマージとpushを拒否する |
| `ask-before-dev-server.sh` | 客先のworktreeで、勝手にdevサーバーを立てる前に確認する |
| `deploy-oshisuki-dev.sh` | `develop` にpushしたら、dev環境へのデプロイを走らせる |

`block-prod-merge.sh` が91行あるのは、**判定が単純ではないからです。** どのリポジトリか、いまどのブランチにいるか、コマンドがどの形か。全部見てから決めます。拒否リストの1行では表現できません。

そして3つ目に注目してほしいのですが、**フックは「禁止」だけの仕組みではありません。** 忘れがちな手順を自動で走らせるのにも使えます。

### 3段目：リポジトリ側のスクリプトが、そもそも不正を許さない

ここが**Claudeの設定より強い**ところです。

**pre-commit で止まるもの：**

- `main` への直接コミット（ブランチ名を見て拒否）
- 型エラーとlintエラー（staged分に `tsc --noEmit` と `eslint`）

型が通らないコードはコミットできません。**Claudeが「たぶん大丈夫」と思っても関係ありません。**

**worktreeを片付けるスクリプト（`worktree-land.sh`）は、12箇所で中断します：**

- worktreeに未コミットの変更が残っていたら、やらない
- rebaseが1つでも衝突したら、その場でrebaseを中止して元に戻す
- マージがfast-forwardにならなかったら、やらない

**「途中まで進んで壊れた状態」が作れない**ようになっています。中断したらworktreeは触る前と同じです。

**post-commit は、リリース用PRの説明文を裏で更新します。** 忘れるからです。

### なぜここまでやるか

並行で何セッションも動かしていると、**全部の出力を自分で見ることは物理的にできません。**

なので、見なくても壊れないようにしています。**レビューで捕まえるのではなく、そもそも不正な状態を作れないようにする。** これはAIに限った話ではなく、CIやpre-commitがずっとやってきたことです。相手がAIになっても考え方は同じで、**効く相手が増えただけです。**

## 7. そのままコピーして使える設定

`~/.claude/settings.json` から、**環境に依存しない部分だけ**抜き出しました。パスや客先の情報が入っているところは外してあります。

```json
{
  "permissions": {
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force*)",
      "Bash(git reset --hard*)",
      "Bash(curl * | bash)",
      "Bash(scp *)",
      "Bash(nc *)",
      "Read(~/.ssh/**)",
      "Read(~/.aws/**)",
      "Read(**/.env)",
      "Read(**/.env.*.local)",
      "Read(**/.env.production)",
      "Edit(~/.ssh/**)",
      "Edit(~/.aws/**)"
    ],
    "allow": [
      "Read", "Glob", "Grep", "Edit", "Write",
      "Bash(git status*)", "Bash(git diff*)", "Bash(git log*)",
      "Bash(git show*)", "Bash(git branch*)", "Bash(git fetch*)",
      "Bash(pnpm *)", "Bash(npx *)", "Bash(tsc*)"
    ]
  },
  "attribution": { "commit": "", "pr": "" },
  "env": {
    "MAX_THINKING_TOKENS": "10000",
    "CLAUDE_AUTOCOMPACT_PCT_OVERRIDE": "50"
  }
}
```

それぞれの意味です。

| 設定 | 何のため |
|---|---|
| `deny` | 取り返しがつかない操作と、鍵や `.env` を読ませないため |
| `allow` | 読み取り系とプロジェクトのコマンドは、毎回聞かれても邪魔なだけなので通す |
| `attribution` | コミットとPRに入る「Generated with Claude」の署名を空にする |
| `MAX_THINKING_TOKENS` | 思考に使うトークンの上限 |
| `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` | 文脈が50%になったら自動で圧縮する。埋まりきってから慌てない |

**`deny` から先に書くのがおすすめです。** ここが固いほど `allow` を広くできて、結果として確認のプロンプトが減ります。逆に `deny` が空のまま `allow` を広げると、ただ危ないだけになります。

### フックはこの形

`settings.json` に置きます。`PreToolUse` は、ツールが実行される**前**に走ります。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "bash ~/.claude/hooks/block-prod-merge.sh" }
        ]
      }
    ]
  }
}
```

スクリプト側は、標準入力でツールの引数を受け取って、**終了コードで通すか止めるかを返すだけです。** シェルが書ければ書けます。

そして実際のところ、**このスクリプトも自分では書いていません。** 止めたい状況が起きたときに、そのセッションで「これをフックで止めて」と言って書いてもらったものです。3章と同じやり方です。

## 8. チームで共有する設定と、手元に置く設定

設定を育てると、次に出てくるのが「これ、リポジトリに入れてチームで共有していいのか」です。

判断の基準はひとつです。

> **それはプロジェクトについての事実か、自分についての事実か。**

プロジェクトについての事実なら、リポジトリに入れます。誰が触っても同じように成り立つからです。自分についての事実なら、手元に置きます。

### 実際の分け方

モバイルアプリのリポジトリで、gitに入っているのはこの3つだけです。

| 入れているもの | なぜ |
|---|---|
| `CLAUDE.md` | このリポジトリの掟。「mainは人がマージする」「作業はworktreeで」 |
| `.claude/settings.json` | プロジェクト用の権限とフック |
| `.claude/skills/ux-gate/SKILL.md` | このプロジェクトの画面を作ったら通す確認手順 |

そして `.claude/settings.local.json` は**gitignoreに入れています。** 個人の権限設定はここに書く前提です。

### 手元に置いておくもの

- **メモリ**。自分がどこでハマったかの記録なので、他の人の環境ではそのまま当てはまりません
- **個人用のスキル**。`/copy` は `wl-copy` を叩くのでWayland専用です。macOSの人に配ったら壊れます
- **MCPの接続情報**。**トークンが絡むものは、そもそも共有する対象ではありません**
- ステータスライン、通知、応答の言語のような**好みの設定**

### 共有するときに、必ず見るところ

`.claude/` をコミットする前に見るのはこの3つです。

- **絶対パスが入っていないか**（`/home/自分の名前/...` は他の人の環境で動きません）
- **トークンや接続文字列が入っていないか**
- **社内の情報が入っていないか。** 環境を説明するための設定には、ドメイン名や本番の識別子、シークレットの名前が入りうる。ここはコミット前に必ず読む

### いちばん効くのは `CLAUDE.md` を共有すること

順番をつけるなら、**まず `CLAUDE.md` です。**

チームで一番もったいないのは、**全員が同じ前提をそれぞれのセッションで説明し直していることです。** 「このリポジトリはこう動く」を1回書いて共有すれば、その説明は全員ぶん消えます。

ただし、**長くしすぎると9章の話になります。** 全部が毎回読み込まれて、全部が薄くなる。守らせたい掟は短く書いて、事故になるものはフックとスクリプトに落とす。

## 9. 設定は、遅くもする

ここまで「足せ」という話をしてきたので、逆の話も書きます。**設定は開発を遅くもします。**

そして遅くなったとき、**犯人はだいたい思っているところにいません。**

### コストは2種類あって、桁が3つ違う

| 種類 | 例 | 実測 |
|---|---|---|
| **1回あたりのコスト** | フックがPythonスクリプトを1本走らせる | **数十ミリ秒** |
| **ターン数のコスト** | ゲートがエージェントをもう1周させる | **1〜2分** |

自分の環境で測った数字です。

- `python3` の起動：**約16ms**
- `git status --porcelain -uall`：**約30ms**
- サブエージェントを1回呼ぶ：**1〜2分**

**桁が3つ違います。** なので「スクリプトが重いのでは」と疑う前に、**1回の依頼で何ターン回っているかを数えるほうが先です。**

### よくある誤診：言語のせい

「フックがPythonだから遅い」は、**まず違います。** 起動は16msです。同じスクリプトをGoで書き直しても、体感は1ミリも変わりません。

言語ではなく、**そのフックが何を起動するか**です。`git status` なら数十ミリ秒ですが、**プロジェクト全体のlintや型チェックを走らせていたら数十秒**になります。同じ「1本のスクリプト」でも中身で桁が変わります。

### 本当に効いてくる4つ

1. **ゲートが強制するターン数。** 「計画を書き終えるまで編集させない」「評価が終わるまで完了させない」のような仕組みは、1回の依頼を4〜5ターンに増やします。**1行の修正でも同じだけ払います**
2. **毎回のツール呼び出しで重い処理を走らせるフック。** 1回2秒でも、50回編集すれば100秒です。しかも分散しているので誰も気づきません
3. **検証そのものが高い。** インクリメンタルでない型チェックは、3行直すたびに全部を検査します。**エージェントは検証を繰り返す前提の道具なので、ここが高いと全部が高くなります**
4. **常時読み込まれる文脈。** ルール、`CLAUDE.md`、使っていないMCPのツール定義。毎ターン払い続けます

### 守りのコストは、仕事の大きさに比例させる

これがいちばん言いたいことです。

**1行の修正と3日がかりのリファクタに、同じ重さの手続きを課すと破綻します。** 小さい仕事の割合のほうが圧倒的に多いので、平均コストは重いほうに引きずられます。

そして本当の問題はその先です。**手続きが重すぎると、人は必ず抜け道を探します。** 止めるために作ったものが、止められないまま使われなくなる。**厳しくしすぎた守りは、緩い守りより弱いです。**

だから、**止める仕組みには必ず「理由を書けば通す」出口を用意しています。** 理由が記録に残るなら監査はできるので、失うものはありません。出口のない禁止は、いずれ設定ごと外されます。

### 疑う前に測る

遅いと感じたら、この順で切り分けます。

1. **1回の依頼で何ターン回っているか。** 増えているなら、そこで終わりです
2. **フックが何を起動しているか。** `time` を付けて実際に測る。想像で犯人を決めない
3. **型チェックやテストが1回いくらか。** インクリメンタルになっているかを確認する
4. **常時載っている文脈の量。** ルールの行数と、繋いでいるMCPの数

**この順番が大事です。** 1番の影響が3桁大きいので、4番から手をつけると何も改善しません。

## 10. よくある誤解：設定は短いほどいい

設定の話でよく見かける「作法」があります。

> 「`CLAUDE.md` は短く。長く書くとAIが読まなくなる」
> 「フォルダ構成をこう分けないと、指示が無視される」
> 「簡潔に書くほど、ちゃんと従ってくれる」

**観測されている症状は本物です。でも、そこから出てくる結論のほうが間違っています。** 自分の環境で測ったうえで、3つに分けて書きます。

### 誤解1：長く書くと、AIが読まなくなる

**文脈の窓は十分に大きいので、入るものは入ります。** 「◯行を超えたら読まなくなる」という線はありません。9章と11章で見たとおり、`CLAUDE.md` もルールも**毎回まるごと載っています。**

なので、気にするべきなのは長さではありません。

> **それは `CLAUDE.md` に書くべきことなのか。**

#### 全部を`CLAUDE.md`に入れると、全部が同じ重さになる

これが本当の問題です。

「mainに直接pushしない」と「文字列はダブルクォートで」を同じファイルに並べたとき、**モデルから見れば、どちらも同じリストの1行です。** 片方は事故で、片方は好みなのに、**どちらが重いのかを示す手がかりがありません。**

そして毎回載るものが増えるほど、その1行が占める割合は小さくなります。**大事な1行を守りたくて書き足した20行が、その1行を薄めます。**

#### 分けるのは、容量ではなく「優先度」と「届くタイミング」

| 置き場所 | いつ届くか | 何を置くか |
|---|---|---|
| **フック・スクリプト** | ツールを呼ぶ瞬間 | **破られたら事故になるもの**（テキストですらない） |
| **`CLAUDE.md`** | 毎回 | **本当に毎回関係すること**だけ |
| **スキル** | その作業をするときだけ | 手順。呼ばれた瞬間、それが主役になる |
| **メモリ** | 関係するときだけ | 事実 |

**スキルがよく効くのは、呼ばれた瞬間に他の500行と競争していないからです。** 300行のスキルのほうが、`CLAUDE.md` に足した10行よりも確実に守られます。メモリを352件持っていても毎回のコストが変わらないのも同じ理由です。**載っているのは索引だけで、開くのは関係する数件だけ。**

だから、**`CLAUDE.md` が短くなるのは結果であって、目的ではありません。** 毎回関係することだけを残せば、勝手に短くなります。逆に「短くしよう」から始めると、**行き場を決めないまま情報を捨てることになります。**

### 誤解2：ファイルを分ければ、必要なものだけ読まれる

言われているのはこうです。

> 「1つの長いファイルより、小さく分けたほうがいい。**必要なファイルだけ読まれる**ので、文脈がきれいになって応答も速くなる」

**分けたかどうかでは決まりません。決めるのは、載っている仕組みのほうです。**

自分の `~/.claude/rules/` は10ファイルに分かれています。git、テスト、セキュリティ、コードレビュー……。きれいに整理されています。そして**10ファイルとも、毎回まるごと読み込まれます。** 合計464行。**1つの長いファイルに書いてあったときと、載る量は完全に同じです。**

「必要なときだけ開く」が成り立つのは、**索引があって選べる仕組みに載っている場合だけ**です（メモリやスキル）。ファイルを分割しただけでは、その仕組みには乗りません。

#### そして、そこは速度にほとんど効かない

仮に選択的に読まれたとしても、**得られるものは小さいです。**

9章のコストの表を思い出してください。**ルール464行はトークンにすれば1万にも届きません。** 毎ターンの体感差にすると誤差です。一方で、**ゲートがエージェントをもう1周させれば1〜2分**かかります。

**桁が3つ違うほうを放置して、フォルダ構成で悩むのは割に合いません。** 分け方をどれだけ工夫しても、取り返せるのは誤差のほうです。

分割していい理由は、**人間が読みやすいから**で十分です。それ以上の効果を期待して時間を使う必要はありません。

#### 分けるほど、腐る場所が増える

そして分割にはコストもあります。

自分のルールのうち1つ（`agents.md`）は、**存在しないディレクトリのエージェントを10個も紹介し続けていました**（11章）。1ファイルなら目に入ったかもしれませんが、10個に分かれていると、**どれが死んでいるか気づきにくくなります。**

#### つまり、これはオーバーエンジニアリングです

整理すると、フォルダ構成に凝ることで払っているのはこれです。

| 払うもの | 得るもの |
|---|---|
| 構成を考える時間 | **誤差** |
| 分け方を維持する手間 | **誤差** |
| 腐る場所が10倍 | **誤差** |

**効果が誤差の場所に、時間と維持コストを払っている。** これをオーバーエンジニアリングと呼びます。コードで同じことをしたらレビューで止まるはずですが、設定だと通ってしまう。

**フォルダ構成に正解はありません。** 「この構成にしないと効かない」という作法を見かけたら、**その構成が「必要なときだけ開く」仕組みに載っているのか**だけ確認すれば十分です。載っていないなら、どう置いても結果は同じです。

そして、そこで浮いた時間で**今日うまくいかなかったことを1つ直すほうが、確実に効きます。**

### 誤解3：短く簡潔に書くほど効く

もうひとつ、逆になっている話があります。**抽象的なルールを短く書くより、具体例を長く書くほうが効きます。**

たとえば「gitの操作は慎重に」と書いても、何も起きません。実際に書いてあるのはこちらです。

> `git add` してから別の操作を挟んでコミットしない。2026年8月19日に、約340行が無関係なコミットに巻き込まれた。インデックスはセッション間で共有されているため。`git commit -- <paths>` を使う。

**長いです。でもこちらは効きます。** 何が起きたか、なぜ起きたか、代わりに何をするかが全部あるからです。抽象的な一行は、解釈の余地が大きすぎて何も決めません。

**「短く書け」を守って情報を削ると、効かない一行が残ります。**

### 誤解4：長く書くと、維持が大変になる

ここが一番言いたいところです。

上のような記述を、人間が手で書いて維持するのは無理です。**そもそも自分で書いていません。** 失敗した直後に「いまのを覚えといて」と言っただけで、Claudeが状況をまとめて書いています（2章）。

だから「長く書くと大変」という前提自体が成り立ちません。**長さのコストを払っているのは自分ではありません。**

### 情報のほとんどは、自分には関係ない

「〜が効かない」「〜しないと動かない」という記事は無数にあります。そして**多くは、書いた人の環境では本当に起きています。** 嘘ではありません。

問題はそこではありません。**1つの環境で起きたことが、そのツールの仕様として書かれることです。** 読む側には、それが自分に当てはまるのか判断する材料がありません。

自分の環境では、ルールは10ファイルとも毎回読み込まれています（11章で確認済み）。もし「ルールは効かない」という記事を真に受けて設定を組み直していたら、**効いているものを自分で壊していたことになります。**

だから、こうしています。

- **「仕組み」が書いてある記事だけ読む。** どこで何が起きるのかが書いてあれば、自分の環境で確かめられます
- **「こうしないと動かない」という作法は、確かめるまで採用しない**
- **確かめるのは5分で終わります。** ルールが効いているか知りたければ、わざと違反する状況を作って、止まるかどうかを見ればいい

これは正しいか間違っているかの話ではなく、**時間の使い方の話です。** 他人の環境の話を10本読む時間で、**自分の環境を1回測ったほうが、確実な答えが手に入ります。**

そして測った結果は、そのままメモリに入れておけます（3章）。**次に同じ話が流れてきたときには、もう答えを持っている状態になります。**

### 本当の損失は、自分の設定ができないこと

失う時間の話をしましたが、**いちばんの損失はそこではありません。**

作法を追いかけて設定を組み替えていると、手元に残るのは**「他人の環境で起きた問題への対策」の寄せ集め**です。自分が毎日どこで詰まっているかとは、何の関係もありません。

そして自分で作っていないので、**中身が分かりません。** 効いているのかも判断できないし、おかしくなっても直せない。11章に書いた `agents.md` のように、**壊れていることにすら気づけません。**

自分のメモリ352件に意味があるのは、件数ではありません。**全部、自分が実際にやらかしたことだからです。** 他人の352件をそのまま持ってきても、自分は一度も助かりません。

**記事を読んで設定を組み替えている時間があれば、今日うまくいかなかったことを1つ直したほうがいい。** それが2章の話で、この記事で一番言いたいことです。

## 11. 設定は、静かに古くなる

この記事を書くために自分の設定を見直して、**壊れているものが見つかりました。**

`~/.claude/rules/common/agents.md` に、10個のエージェントの表が書いてあります。「複雑な機能は planner を使え」「コードを書いたら code-reviewer を使え」と。置き場所は `~/.claude/agents/` と書いてある。

**そのディレクトリは存在しません。**

いつ消えたのかもわかりません。実際に使えるエージェントはプラグイン側にあって、名前も違います。つまり、**globalのルールが、空の場所を指し続けていた**わけです。

これが設定を育てるときの本当の落とし穴です。壊れたコードはエラーを出しますが、**壊れたルールは何も言いません。** ただ静かに効かなくなって、こちらは効いているつもりで使い続ける。

対策は単純で、**参照を書くときは実在を確かめる、そして時々ルールを読み返す**しかありません。この記事を書いたことがその読み返しになりました。

### ルールは「読まれない」のではなく、薄まる

もうひとつ、よく聞く症状があります。「`.claude/rules` に書いたのに、読まれていない気がする」。

自分の環境を確認したら、**ルールは毎回まるごと読み込まれていました。** `CLAUDE.md` の97行と `rules/` 配下の464行、**合計561行が、どのセッションでも最初から入っています。**

つまり「読み込まれていない」わけではありません。**入ってはいるけれど、他の560行と一緒に入っている**、というだけです。

ここがメモリとの決定的な違いです。

| | 読み込まれ方 |
|---|---|
| メモリ | 索引だけ常時。**必要なものだけ開く** |
| ルール・`CLAUDE.md` | **毎回、全部** |

だからルールは、**増やすほど1本あたりが薄くなります。** 20本書けば、大事な1本も20本ぶんに薄まる。そして古くなった1本は、消えるのではなく**残って場所を取り続けます。**

### 絶対に守らせたいものを、ルールに書かない

ここが6章と繋がります。

**「守ってほしい」ものはルールでいい。「守られないと事故になる」ものは、ルールに書いてはいけません。** それはフックかスクリプトの仕事です。

ルールに書いた禁止事項は、**561行のうちの1行**です。フックは1行でも拒否は拒否です。

ルールを増やして守らせようとするのは、**効かない層に仕事を積んでいることになります。** 減らないなら、その分だけ全部が薄くなる。

## 12. まとめ：どこに何を置くか

| 層 | 置くもの | 作るきっかけ |
|---|---|---|
| **記憶** | コードにも履歴にも書いていない事実 | 「前も説明した」と思ったとき |
| **スキル** | 繰り返す手順 | 同じ指示を3回書いたとき |
| **MCP** | 外のサービスへの接続 | コピペで渡しているものがあるとき |
| **権限・フック・スクリプト** | 破られたら事故になること | 一度ヒヤッとしたとき |

**この4つは全部「あとから足したもの」です。** 最初に完璧な設定を作る必要はありません。というより、作れません。**自分がどこで失敗するかは、失敗するまで分からないからです。**

同じ説明を二度したら記憶に。同じ指示を三度書いたらスキルに。一度ヒヤッとしたらフックに。

そして一番大事なのは、**それをその場でやることです。** 「あとでまとめて設定を整理しよう」という日は来ません。うまくいかなかった直後の、文脈が全部残っている1分。**そこで直すかどうかだけで、AIが間違える回数は確実に減っていきます。**

### 近道はありません

「これを入れれば全部解決する設定」を探している人は多いと思います。**自分もそこから始めました。** ただ、5ヶ月やってみて分かったのは、**そんなものはない**ということです。

理由は単純で、**自分の環境で何が壊れるかは、自分にしか観測できないからです。** 他人の設定は、他人の失敗への対策です。よくできていても、自分の詰まりどころには当たりません。

記憶352件も、スキル71個も、**中身が価値なのではありません。** 全部が「自分が実際にやらかしたこと」に対応している、という事実のほうが価値です。同じ数を他所から持ってきても、一度も助かりません。

### この記事も、そのまま真に受けないでください

ここまで書いておいて何ですが、**この記事も誰かの環境の話です。**

書いてある数字は自分の環境で測ったものですし、そのつもりで書きましたが、**あなたの環境で同じとは限りません。** ルールが読み込まれているかどうかも、フックが何ミリ秒かかるかも、**5分あれば自分で測れます。**

だから、この記事の使い方はこうです。

- **仕組みの部分（何がいつ読み込まれるか）は、自分の環境で確かめる**
- **設定そのものは、コピーする前に「自分はこれで困ったことがあるか」を考える**
- **やり方の部分（失敗したその場で直す）だけは、今日から試せます**

読んで設定を組み替えるより、**今日うまくいかなかったことを1つ直すほうが、確実に前に進みます。** 環境を良くできるのは、その環境で失敗している人だけです。
