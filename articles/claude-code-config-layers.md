## 2. 最低限これだけ：Claude Codeは、文脈が全部

**本当に必要な知識はここだけです。** ここが分かっていないと、あとの章はただの作法に見えます。

### 前提は2つ

**1. Claudeが知っているのは、文脈に載っているものだけ。**

前回の会話は覚えていません。毎回ゼロから始まります。「前は分かってくれたのに」は起きません。

**2. 文脈は有限で、埋まるほど悪くなる。**

- トークンを食う
- 遅くなる
- 取り違えが増える

かといって必要な情報が消えれば、今度は筋を見失います。**入れすぎても、足りなくてもダメです。**

つまり**Claude Codeを使うとは、ほぼ文脈を管理することです。** 方法は3つ。

---

### 管理①：タスクで分ける

よく見るのが「`plan.md`をリポジトリに置いて状況を書き続ける」方法です。**やっていません。**

| やること | なぜ |
|---|---|
| タスク1つ＝セッション1つ | 混ざらない |
| 終わるまで使い回す | 途中で文脈を失わない |
| `/rename`で名前を付ける | `--resume`で戻れる |
| 50%を超えたら`/compact` | 自動圧縮が作業中に走るより安全 |

**状態を書き出す必要はありません。セッションそのものが状態です。** 手間が増えるうえに、その文章がまた文脈を食います。

---

### 管理②：置き場所で分ける

文脈への載り方は、3種類しかありません。

| 種類 | いつ載るか | 例 |
|---|---|---|
| **常時** | 毎回、全部 | `CLAUDE.md`、ルール |
| **必要なときだけ** | 索引から選んで開く | メモリ、スキル |
| **テキストではない** | ツールを呼ぶ瞬間に介入 | 権限、フック |

3つ目が決定的に違います。

> 上の2つは**お願い**。3つ目は**拒否**。

同じ内容でも、置き場所で結果が変わります。

- **常時** → 毎回載るが、他の全部と競争する
- **必要なときだけ** → 呼ばれた瞬間、それが主役になる
- **権限・フック** → 競争しない

**この記事の残りは、②の話です。**

---

### 管理③：足りない情報を、取りに行けるようにする

①②は「載せすぎない」話でした。3つ目は逆です。

**コードを書くのに必要な情報は、コードの中だけにありません。**

| どこから | 何を |
|---|---|
| コード | 既存の実装と規約 |
| チケット | 何を作るのか |
| Slack | **なぜそう決まったのか** |
| Notion | 仕様と背景 |
| Figma | デザインの実際の値 |
| AWS | 動いている環境の設定 |

**チケットだけ読んで書いたコードは、だいたいどこかが足りません。**

MCPやCLIを繋ぐのは、これをClaudeにもできる状態にする、というだけの話です。

貼るのとは違います。

| | 文脈への載り方 |
|---|---|
| ログを貼る | 1万行が、以後ずっと残る |
| 繋いでおく | 必要になった時点で、必要なぶんだけ |

だから「AIから触れるか」はサービス選びの基準になります。GUIしかないサービスは、**結局こちらがスクリーンショットを貼ることになるからです。**

### 話し方に、コツはありません

先に誤解をひとつ。**「AIに効く言い方」を覚える必要はありません。** 呪文集のようなプロンプト集が出回っていますが、普通の日本語で、同僚に頼むように書けば通じます。

**うまくいかないとき、足りないのは言い方ではなく情報です。** 言い換えを10回試すより、足りない1つを渡すほうが速い。

渡し方で一番手軽なのがスクリーンショットです。**ずれたUI、エラー画面、期待と違う表示は、文章で説明するより貼るほうが速くて正確です。** 「ボタンが少し下にずれている」を文章で伝えるのは、意外と難しい。

そして**書かせる前に、相談に使うこと。** いきなり実装させると、方針の間違いをコードの形で受け取ることになります。

### 探索は、作る前に並べさせる

画面を新しく作るときに一番高くつくのは、**1案に数時間かけてから作り直すこと**です。

なので先に、**artifactで案を3〜5つ並べて出してもらいます。** 実装ではないので数分で出てきて、横に並べて見れば「これは違う」が一瞬で分かる。決まってから、はじめて実装に入ります。

**選ぶのは実物を見てから、というだけの話です。** 頭の中で比べるのと、並べて見るのとでは精度が違います。

## 3. 作り方は、ひとつだけ

4つの層は、座って設計したものではありません。**全部、失敗した直後にその場で足したものです。**

やることは1つ。

> 失敗したら、**そのセッションのまま**「いまのを設定に反映して」と頼む。

---

### なぜ「その場」なのか

材料がそこにしかないからです。

- 自分が何を指示したか
- Claudeがどこを勘違いしたか
- 結局どう直したか

全部そのセッションに残っていて、**Claude自身がそれを見ています。**

もう1つ、こっちのほうが大事です。**その場なら、書いたルールが効くか試せます。** 「これがあったら、さっきのは防げたか」を実際に当てられる。

翌日だと両方消えます。手元にあるのは失敗ではなく、**失敗の要約**です。

そして翌日にやろうとすると、大体やりません。

---

### 厳密に読まなくていい

これが続く理由です。

| | |
|---|---|
| かかる時間 | 1〜2分 |
| 読み方 | ざっと見て、方向が合っていればいい |
| 間違っていたら | 次に同じ失敗をしたとき直す |

**一度で正解にしなくていい。** 失敗のたびに近づけばいい。

---

### やってはいけないのは、そのまま進むこと

「これ効かないな」と思って、直さずに次へ行く。**まずいのはこれだけです。**

そして、これが「AIは使えない」の正体だと思っています。

> 「ちゃんと答えてくれない」
> 「AIは信用できない」
> 「結局、自分で書いたほうが速い」

体感で9割以上、原因は同じところにあります。**うまくいかなかったその瞬間に、何も直していないことです。**

| | 3ヶ月後 |
|---|---|
| 直さない | **初日と同じ精度**のClaudeを使い続ける |
| 毎回1分直す | 同じ失敗が**二度目で消える** |

AIが賢くなったわけではありません。**同じ説明を二度しなくてよくなっただけです。**

この差が、5ヶ月で記憶352件とスキル58個になりました。

直したのに同じ失敗が続くなら、そのときだけ腰を据えて読み返す。**定期的な棚卸しは、それくらいの頻度で十分です。**

## 4. 忘れることは、記憶に置く

一番効いた層がこれです。

Claudeは会話が終われば全部忘れます。次のセッションでは、また同じ前提から説明することになる。

やることは1つ。

> 「前も同じ説明をしたな」と思った瞬間に、**「これ覚えといて」**と言う。

---

### ファイルは自分で作っていません

置き場所も形式もECCの設定が決めてくれます。

- 1ファイル1事実（352件あるのは、細かく切られているから）
- `MEMORY.md`が索引で、1件1行
- プロジェクトごとに独立。モバイルの話が客先の作業に混ざらない

**メモリのファイルを手で書いたことは一度もありません。** 「覚えといて」と言えば、Claudeが置き場所を決めて、索引に足して、関連する記憶へのリンクまで張ります。

**始めるコストはほぼゼロです。** 難しいのは仕組みではなく、その場で一言いうことのほう。

---

### CLAUDE.mdとは役割が違う

| | 書く内容 | 書く人 |
|---|---|---|
| `CLAUDE.md` | 自分が決めた掟（「mainは人がマージする」） | 自分 |
| 記憶 | 作業中に発見してしまった事実 | Claude |

**なぜ記憶を`CLAUDE.md`に全部書かないのか。**

352件を1枚にすると、毎回そのファイル全部が文脈に載ります。今日必要なのは3件なのに、**残り349件ぶんのトークンを毎回払う**ことになる。

索引だけ読ませて、関係するファイルだけ開かせる。これなら件数が増えても、毎回のコストは変わりません。

---

### 実際に入っているもの

> **worktreeを分けても、gitのインデックスは共有されている。** `git add`して後からコミットすると、別のセッションのコミットに自分のファイルが持っていかれる。コミットは`git commit -- <paths>`で。

> **シンガポールへの236msはバグではない。** DBに日本のリージョンがないので、サーバーとDBを同じ場所に置いた結果。遅いクエリを探す前に、まずpingを測る。

どちらも**知らなければ半日溶ける**類の話で、一度溶かした人間しか書けません。

置かないものもはっきりしています。

- ドキュメントに書いてあること
- リポジトリを読めばわかること

**置くのは、コードにも履歴にも残らないことだけです。**

## 5. 繰り返すことは、スキルにする

記憶が「事実」なら、スキルは「手順」です。

58個は設計して作ったものではありません。**3回目に同じ指示を書いたとき**に作っています。基準はそれだけ。

| スキル | 何をするか |
|---|---|
| `/commit` | 差分を読んで、そのリポジトリの言語と形式でメッセージを3案出す。選ぶだけ |
| `/solve` | チケットから、ブランチ→実装→push→Draft PR→worktree片付けまで通す |
| `/bg` | その`/solve`を裏で走らせる。いまの作業が止まらない |
| `/review` | PRでもローカル変更でも。他のボットが拾わない「参照はあるのに実装がない」系まで見る |
| `/resolve-bot-review` | ボットの指摘ごとに「直す／意図通り／もう古い／間違い」を判定して返す |
| `/release-draft` | リリースPRの説明文を追記する。チェック済みのQA項目は絶対に外さない |

この記事も`/zenn-article`を通して書いています。

---

### スキルにすると、うまくいった条件が残る

指示を毎回書き直していると、**うまくいったときの条件が残りません。** 前回なぜうまくいったのかは、3週間後には自分でも思い出せない。

スキルはそれを固定します。そして**失敗するたびに追記できるので、使うほど厳しくなります。**

---

### 実例：`/commit`が`git add`を禁止した理由

同じリポジトリでセッションを何個も並行させています。多い日で9個。

**gitのインデックスは、その全部で共有されています。**

2026年8月19日に何が起きたか。

1. メール取り込み機能の約340行を`git add`した
2. コミットする前に、別のセッションがコミットを打った
3. その340行が、無関係な`fix(share): ...`の中に入った

コードは無事です。壊れたのは**コミットメッセージが中身の半分を説明していない**ことのほう。

その場で`/commit`に1行足しました。

```bash
git commit -F - -- path1 path2   # git add してから commit しない
```

`git commit -- <paths>`はインデックスの残りを無視します。**この失敗は、それ以来一度も起きていません。**

スキルにしていなければ、この判断は「あのとき何かあったな」で消えていました。

---

### 道具があることと、使うことは別

正直に書くと、**持っているだけでは効きません。**

Androidのdevビルドは、EASに投げると15分待つのでローカルでやると決めています。それでもある日、**習慣でEASに投げました。**

ルールがなかったからではありません。読まずに手が動いただけです。

そのときもその場で直しました。いまは`CLAUDE.md`に書いてあります。

## 6. 守ってほしいことは、お願いせずに強制する

ここが一番大事な層です。

| 書く場所 | 性質 | 守られる確率 |
|---|---|---|
| プロンプト、`CLAUDE.md` | **お願い** | 高い。でも100%ではない |
| フック、スクリプト | **拒否** | 通らないものは通らない |

事故は、その残りの数%で起きます。

---

### 3段構えにしている

| 段 | 仕組み | 性質 |
|---|---|---|
| 1 | 権限の拒否リスト | ツール呼び出しの入口で止める |
| 2 | フック | コマンドの中身を見て、条件つきで止める |
| 3 | リポジトリ側のスクリプト | **人間が手で叩いても止まる** |

3段目が効く理由は1つ。**Claudeを信用するかどうかという話から、降りられるからです。**

---

### 1段目：拒否リスト16個

```
Bash(rm -rf *)
Bash(git push --force*)
Bash(git reset --hard*)
Bash(curl * | bash)
Read(~/.ssh/**)
Read(**/.env)
```

どれも「うっかり」が取り返しのつかないものです。

一方、許可リストは73個。読み取り系は全部そこに入れています。**拒否を厳しくするほど、許可を広くできます。**

---

### 2段目：フックは条件つきで止められる

| フック | 何をするか |
|---|---|
| `block-prod-merge.sh`（91行） | 本番に出るリポジトリで、`main`へのマージとpushを拒否 |
| `ask-before-dev-server.sh` | 客先のworktreeで、devサーバーを立てる前に確認 |
| `deploy-oshisuki-dev.sh` | `develop`にpushしたら、dev環境へデプロイ |

91行あるのは、**判定が単純ではないからです。**

- どのリポジトリか
- いまどのブランチにいるか
- コマンドがどの形か

拒否リストの1行では表現できません。

そして3つ目を見てください。**フックは「禁止」だけの仕組みではありません。** 忘れがちな手順を自動で走らせるのにも使えます。

---

### 3段目：リポジトリ側のスクリプト

ここが**Claudeの設定より強い**ところです。

**pre-commitで止まるもの：**

- `main`への直接コミット
- 型エラーとlintエラー（staged分に`tsc --noEmit`と`eslint`）

型が通らないコードはコミットできません。**Claudeが「たぶん大丈夫」と思っても関係ありません。**

**`worktree-land.sh`は、12箇所で中断します：**

- 未コミットの変更が残っていたら、やらない
- rebaseが1つでも衝突したら、その場で中止して元に戻す
- マージがfast-forwardにならなかったら、やらない

**「途中まで進んで壊れた状態」が作れません。** 中断したら、触る前と同じです。

post-commitはリリースPRの説明文を裏で更新します。忘れるからです。

### 外のサービスは、つないだ瞬間に書ける

ここまでは自分のリポジトリの話でした。**MCPをつなぐと、話が repo の外に出ます。**

読むためにつないだつもりでも、書く道具と消す道具が一緒に来ます。自分の環境で数えたら、こうなっていました。

| サーバー | 書き込み・削除できる道具 |
|---|---|
| Neon（本番DB） | 29 |
| Gmail | 15 |
| Notion | 12 |
| Axiom | 10 |
| Slack | 9 |
| Figma | 9 |
| Drive | 5 |
| Google Calendar | 4 |
| **合計** | **94** |

中身を見ると、Neonの29個には`delete_project`と`run_sql`が入っています。**プロジェクトごと消せるし、任意のSQLが流せます。** Slackの`conversations_add_message`は、**自分の名前でメッセージが飛ぶ**ということです。Notionにはページを書き換える道具が、Driveには`share_file`——つまり外部共有——があります。

つないだ覚えはありました。**何が一緒に来たかを見た覚えは、ありませんでした。**

#### 「消さないで」と書いても、それは制御ではない

ここが6章の全部です。公式ドキュメントの一文がそのまま答えになっています。

> Permission rules are enforced by Claude Code, not by the model.

`CLAUDE.md`に書いた禁止事項は、モデルの動機を変えるだけです。**通す／通さないを決めているのは設定ファイルのほうで、そこは日本語の説得が効く場所ではありません。**

#### 元栓・deny・ask の3段階

**1段目、元栓を締める。** これが一番強い。道具が来なければ事故のしようがありません。DBは読み取り専用のロールでつなぐ、Notionのインテグレーションは`Read content`だけで作ってもらう、Slackのトークンに投稿の権限を入れない。**権限は、あとで足すほうが簡単です。**

**2段目、`deny`で消す。** 名前を書いた道具は**Claudeの文脈から消えます**。ブロックされるのではなく、最初から見えない。副産物として、そのぶんのトークンも払わなくて済みます（7章）。

**3段目、`ask`で毎回聞かせる。** 使うけれど、勝手には使わせないもの。**`ask`は自動承認モードでも必ず止まります**——ここが大事で、`allow`に入れてあっても`ask`が勝ちます。

```json
{
  "permissions": {
    "deny": [
      "mcp__neon__delete_project",
      "mcp__neon__reset_from_parent",
      "mcp__claude_ai_Google_Drive__share_file"
    ],
    "ask": [
      "mcp__neon__run_sql",
      "mcp__slack__conversations_add_message",
      "mcp__claude_ai_Gmail__send_message",
      "mcp__notion__notion-update-page"
    ]
  }
}
```

評価の順番は`deny` → `ask` → `allow`で、**最初に当たったものがそのまま決まります。** だから広い`deny`に例外は作れません。書き方は3通り：

| 書き方 | 意味 |
|---|---|
| `mcp__slack` | そのサーバーの道具ぜんぶ |
| `mcp__neon__delete_*` | 名前が前方一致するものぜんぶ（`deny`と`ask`のみ） |
| `mcp__neon__run_sql` | その道具ひとつ |

**ハマりどころがひとつ。** `mcp__`のルールに括弧を書くと——`mcp__neon__run_sql(...)`のように引数で絞ろうとすると——**そのルールは黙って読み飛ばされます。** 起動時の警告には出ますが、書いた本人は効いているつもりでいます。MCPの道具は、引数ではなく名前で止めるものだと思っておくのが安全です。

#### 鍵は渡さない。通り道だけ渡す

`deny`と`ask`は、道具の単位で決める話でした。**もうひとつ上のやり方があって、こっちのほうが強い。**

本番のデータをどうしても見たいことがあります。何件あるのか、どのくらい埋まっているのか。**でも「見られる」と「書ける」が同じ権限として来るのが嫌でした。**

やったのは、スクリプトを1本挟むことです。

```bash
bash scripts/prod-sql.sh "SELECT count(*) FROM community_event;"
```

中身は短くて、効いているのは3つです。

**1. 接続情報はスクリプトが持ちます。** そして認証情報のファイルそのものは、`deny`で読めなくしておく。**使えるが、見えない。** ここが境界線で、持ち出せないものは漏れません。

ここに落とし穴があります。**`Read(**/.env)`は、名前がちょうど`.env`のファイルにしか当たりません。** `.env.db-prod`のような名前を作った瞬間、スクリプトで隠したはずの鍵が、そのまま読める場所に戻っています。塞いだつもりの穴が一番危ないので、**パターンを書いたら、実際にあるファイル名と突き合わせて確認してください。**

**2. 読み取り専用を保証しているのはPostgres自身です。** クエリは`BEGIN READ ONLY`の中で走ります。

```sql
BEGIN READ ONLY;
<クエリ>
COMMIT;
```

INSERTもUPDATEもDELETEもDDLも、**サーバー側が拒否します。** 文字列で危ないSQLを弾く方式だと、書き方を変えれば抜けられます。これは抜けられません。**判定しているのが、こちら側ではないからです。**

**3. 拒否されたら、スクリプトごと失敗します。** `ON_ERROR_STOP=1`を付けてあるので、途中まで実行された中途半端な出力が、答えのような顔をして返ってくることがありません。

そして地味に大事なのが、**この安全な道が`allow`に入っていて、確認なしで通ること**です。安全なやり方のほうが面倒だと、人もAIも結局そっちを避けます。**通りやすい道を安全なほうにしておく**、というだけの設計です。

同じ考えで、**触る前に「どこに繋いだか」を必ず名乗らせています。** クローラーのスクリプトは最初のクエリの前にホスト名を出します。「本番を触ったつもり」と「本番を触った」を区別できる唯一の材料が、それだからです。

正直に書いておくと、**これは本命ではありません。** 本命はサーバー側に読み取り専用のロールを作ることで、スクリプトはそれが無い間、事故の大きさをゼロに抑えるための当て木です。スクリプトの先頭にも、そう書いてあります。**当て木だと分かって使うぶんには、当て木で十分です。**

#### 順番は、逆から考える

「何を止めるか」から入ると、際限がありません。**「これが起きたら本当に困る」を数えるほうが速い。**

本番のデータが消える。自分の名前で外に何かが送られる。共有ドキュメントが書き換わる。**この3つは、だいたい誰でも同じです。** そこだけ`deny`と`ask`で塞いで、残りは動かしながら足していけばいい。

### なぜここまでやるか

並行で何セッションも動かしていると、**全部の出力を自分で見ることは物理的にできません。**

なので、見なくても壊れないようにしています。**レビューで捕まえるのではなく、そもそも不正な状態を作れないようにする。** これはAIに限った話ではなく、CIやpre-commitがずっとやってきたことです。相手がAIになっても考え方は同じで、**効く相手が増えただけです。**

## 7. 設定は、遅くもする

ここまで「足せ」という話でした。逆も書きます。**設定は開発を遅くもします。**

そして遅くなったとき、**犯人はだいたい思っているところにいません。**

---

### コストは2種類あって、桁が3つ違う

| 種類 | 例 | 実測 |
|---|---|---|
| **1回あたり** | フックがスクリプトを1本走らせる | **数十ミリ秒** |
| **ターン数** | ゲートがエージェントをもう1周させる | **1〜2分** |

自分の環境で測った数字です。

| | |
|---|---|
| `python3`の起動 | 約**16ms** |
| `git status --porcelain -uall` | 約**30ms** |
| サブエージェントを1回呼ぶ | **1〜2分** |

**桁が3つ違います。**

「スクリプトが重いのでは」と疑う前に、**1回の依頼で何ターン回っているかを数えるほうが先です。**

---

### よくある誤診：言語のせい

「フックがPythonだから遅い」は、**まず違います。** 起動は16ms。Goで書き直しても体感は変わりません。

問題は言語ではなく、**そのフックが何を起動するか**です。

| フックの中身 | かかる時間 |
|---|---|
| `git status` | 数十ミリ秒 |
| プロジェクト全体のlintや型チェック | **数十秒** |

同じ「1本のスクリプト」でも、中身で桁が変わります。

---

### 本当に効いてくる4つ

1. **ゲートが強制するターン数。** 「計画を書き終えるまで編集させない」のような仕組みは、1回の依頼を4〜5ターンにします。**1行の修正でも同じだけ払います**
2. **毎回のツール呼び出しで走る重い処理。** 1回2秒でも、50回編集すれば100秒。分散しているので誰も気づきません
3. **検証そのものが高い。** インクリメンタルでない型チェックは、3行直すたびに全部を検査します。**エージェントは検証を繰り返す道具なので、ここが高いと全部が高くなります**
4. **常時読み込まれる文脈。** ルール、`CLAUDE.md`、使っていないMCPのツール定義

---

### 守りのコストは、仕事の大きさに比例させる

これがいちばん言いたいことです。

**1行の修正と3日がかりのリファクタに、同じ重さの手続きを課すと破綻します。** 小さい仕事のほうが圧倒的に多いので、平均は重いほうに引きずられます。

本当の問題はその先。

> **手続きが重すぎると、人は必ず抜け道を探します。**

止めるために作ったものが、止められないまま使われなくなる。**厳しくしすぎた守りは、緩い守りより弱いです。**

だから止める仕組みには、必ず**「理由を書けば通す」出口**を用意しています。理由が記録に残るなら監査はできるので、失うものはありません。

出口のない禁止は、いずれ設定ごと外されます。

---

### 疑う前に測る

遅いと感じたら、この順です。

1. **1回の依頼で何ターン回っているか。** 増えているなら、そこで終わり
2. **フックが何を起動しているか。** `time`を付けて実際に測る
3. **型チェックやテストが1回いくらか。** インクリメンタルか
4. **常時載っている文脈の量。** ルールの行数と、MCPの数

**この順番が大事です。** 1番の影響が3桁大きいので、4番から手をつけても何も変わりません。

## 8. よくある誤解：設定は短いほどいい

設定の話でよく見かける「作法」があります。

> 「`CLAUDE.md`は短く。長く書くとAIが読まなくなる」
> 「フォルダ構成をこう分けないと、指示が無視される」
> 「簡潔に書くほど、ちゃんと従ってくれる」

**症状は本物です。間違っているのは、そこから出てくる結論のほうです。**

自分の環境で測ったうえで、3つに分けて書きます。

---

### 誤解1：長く書くと読まれない / 分ければ必要な分だけ読まれる

**長さや分け方では決まりません。決めるのは仕組みです。**

自分の`~/.claude/rules/`は10ファイルに分かれています。**10ファイルとも毎回まるごと読み込まれます。** 合計464行。1つの長いファイルだったときと、載る量は同じです。

| | 読み込まれ方 | 増やすと |
|---|---|---|
| `CLAUDE.md`・ルール | **毎回、全部** | 全部が薄まる |
| メモリ・スキル | 索引だけ常時、本体は必要なときだけ | **毎回のコストは変わらない** |

メモリを352件持っていても平気なのは、細かく分けたからではありません。**索引があって、開くものを選べるからです。**

分割しただけでは、この仕組みには乗りません。

#### 気にするべきは長さではなく、置き場所

「mainに直接pushしない」と「文字列はダブルクォートで」を同じファイルに並べる。**モデルから見れば、どちらも同じリストの1行です。**

事故と好みを区別する手がかりがありません。

| 置き場所 | いつ届くか | 何を置くか |
|---|---|---|
| **フック・スクリプト** | ツールを呼ぶ瞬間 | 破られたら事故になるもの |
| **`CLAUDE.md`** | 毎回 | 本当に毎回関係することだけ |
| **スキル** | その作業のときだけ | 手順 |
| **メモリ** | 関係するときだけ | 事実 |

**スキルが効くのは、呼ばれた瞬間に他の500行と競争していないからです。** 300行のスキルのほうが、`CLAUDE.md`に足した10行より確実に守られます。

`CLAUDE.md`が短くなるのは**結果であって、目的ではありません。**

#### そして、そこは速度に効かない

仮に分割で選択的に読まれたとしても、得られるのは誤差です。

| | |
|---|---|
| ルール464行 | トークンにして**1万に届かない** |
| ゲートがもう1周 | **1〜2分**（7章） |

| 払うもの | 得るもの |
|---|---|
| 構成を考える時間 | 誤差 |
| 分け方を維持する手間 | 誤差 |
| 腐る場所が10倍 | 誤差 |

**これをオーバーエンジニアリングと呼びます。** コードで同じことをすればレビューで止まるのに、設定だと通ってしまう。

実際、自分のルールの1つは**存在しないディレクトリのエージェントを10個紹介し続けていました**（9章）。

---

### 誤解2：短く簡潔に書くほど効く

逆です。**抽象的なルールを短く書くより、具体例を長く書くほうが効きます。**

「gitの操作は慎重に」と書いても、何も起きません。実際に書いてあるのはこちら。

> `git add`してから別の操作を挟んでコミットしない。2026年8月19日に、約340行が無関係なコミットに巻き込まれた。インデックスはセッション間で共有されているため。`git commit -- <paths>`を使う。

長いです。**でもこちらは効きます。**

- 何が起きたか
- なぜ起きたか
- 代わりに何をするか

抽象的な一行は、解釈の余地が大きすぎて何も決めません。

**「短く書け」を守って情報を削ると、効かない一行が残ります。**

---

### 誤解3：長く書くと、維持が大変になる

こういう記述を人間が手で書いて維持するのは、確かに無理です。

**そもそも自分で書いていません。** 失敗した直後に「いまのを覚えといて」と言っただけです（3章）。

**長さのコストを払っているのは、自分ではありません。**

---

### 情報のほとんどは、自分には関係ない

「〜が効かない」という記事は無数にあります。そして多くは、**書いた人の環境では本当に起きています。** 嘘ではありません。

問題はそこではなく、**1つの環境で起きたことが、ツールの仕様として書かれること**です。

自分の環境では、ルールは10ファイルとも毎回読み込まれています（9章で確認済み）。「ルールは効かない」を真に受けて組み直していたら、**効いているものを自分で壊していました。**

なので、こうしています。

- **「仕組み」が書いてある記事だけ読む。** 自分の環境で確かめられるから
- **「こうしないと動かない」という作法は、確かめるまで採用しない**
- **確かめるのは5分。** わざと違反する状況を作って、止まるか見ればいい

正しいか間違っているかの話ではなく、**時間の使い方の話です。**

> 他人の環境の話を10本読む時間で、自分の環境を1回測ったほうが、確実な答えが手に入ります。

測った結果は、そのままメモリに入ります（4章）。次に同じ話が流れてきたときには、もう答えを持っている状態です。

---

### 本当の損失は、自分の設定ができないこと

いちばんの損失は、時間ではありません。

作法を追いかけて組み替えていると、あとに残るのは**他人の環境で起きた問題への対策の寄せ集め**です。自分が毎日どこで詰まるかとは、何の関係もありません。

そして自分で作っていないので、**中身が分かりません。**

- 効いているのか判断できない
- おかしくなっても直せない
- **壊れていることにすら気づけない**（9章）

メモリ352件に意味があるのは、件数ではありません。**全部、自分が実際にやらかしたことだからです。**

**記事を読んで設定を組み替えている時間があれば、今日うまくいかなかったことを1つ直したほうがいい。**

## 9. 設定は、静かに古くなる

この記事を書くために設定を見直して、**壊れているものが見つかりました。**

`~/.claude/rules/common/agents.md`に、エージェント10個の表があります。「複雑な機能はplannerを使え」と。置き場所は`~/.claude/agents/`と書いてある。

**そのディレクトリは存在しません。**

いつ消えたのかも分かりません。**globalのルールが、空の場所を指し続けていました。**

> 壊れたコードはエラーを出す。**壊れたルールは何も言わない。**

静かに効かなくなって、こちらは効いているつもりで使い続ける。しかも消えずに残るので、**他のルールを薄め続けます**（8章）。

対策は2つだけです。

- 参照を書くときは、実在を確かめる
- 時々読み返す

この記事を書いたのが、その読み返しになりました。

### 絶対に守らせたいものを、ルールに書かない

**「守ってほしい」ものはルールでいい。「守られないと事故になる」ものは、ルールに書いてはいけません。** それはフックかスクリプトの仕事です（6章）。

ルールに書いた禁止事項は**561行のうちの1行**ですが、フックは1行でも拒否は拒否です。**ルールを増やして守らせようとするのは、効かない層に仕事を積むことになります。**

## 10. 設定は、GitHubに置く。ただしコピーで置くと古くなる

ここまでの設定は全部、**1台のPCの`~/.claude/`の中**にしかありません。ディスクが飛んだら、5ヶ月が消えます。

なのでdotfilesのリポジトリに入れています。`shell/`や`nvim/`と並べて`claude/`を置く。ここまでは普通の話です。

**問題はバックアップの有無ではなく、どう繋いでいるかでした。**

| 対象 | 繋ぎ方 | ズレるか |
|---|---|---|
| `.zshrc`、`.gitconfig`、`nvim/`、`tmux.conf` | **シンボリックリンク** | ズレようがない |
| `~/.claude/` | `mkdir -p`で**実体のコピー** | ズレる |

この記事を書きながら差分を取ったら、こうなっていました。

| | リポジトリ | 実際に動いているもの |
|---|---|---|
| `settings.json` | **4月5日** | 9月5日 |
| deny（禁止コマンド） | 12個 | 16個 |
| フック | **4個** | **7個** |
| スキル | 58個 | 71個 |

**6章で「絶対に譲れない層」と書いたフックが、バックアップには半分も入っていませんでした。**

スキルも2つズレていて、片方は**動いているほうにだけ44行**。1ヶ月ぶん直した内容が、一度もリポジトリに戻っていませんでした。

---

### 古いバックアップは、無いより悪いことがある

もう片方のスキルは、もっと厄介でした。

- リポジトリ側に、**開発用DBを親ブランチからリセットする手順**が残っていた
- 動いているほうでは、その手順は消してある
- 8月28日に本番DBが移って、リセット元が**その日で凍ったスナップショット**になったから

いま実行すると、**開発用DBが黙って過去に巻き戻ります。**

新しいマシンでこのリポジトリを展開したら、復元されるのは古い設定ではありません。**DBを壊す手順書が復元されて、Claudeはそれに従います。**

> バックアップが古いというのは、整理されていないという意味ではありません。**間違った指示が、正しい指示の顔をして戻ってくる**ということです。

---

### だからコピーではなくリンクにする

**コピーで置いたものは、「リポジトリに戻す」のを自分が覚えていることに依存します。**

そして設定を直すのは、うまくいかなかったその瞬間です（3章）。その瞬間に考えているのは目の前の失敗で、dotfilesのことではありません。

**思い出すことに頼る仕組みは、いずれ必ず外れます。**

リンクにするもの：`settings.json`、`CLAUDE.md`、`skills/`、`commands/`。

置かないもの：

| | なぜ |
|---|---|
| トークン・認証情報 | 絶対に入れない |
| セッション履歴・キャッシュ | 移植性がない |
| プラグイン経由のスキル | 入れ直せる（71個中13個） |

**残るのは、自分が書いたものだけです。** そしてそれが、消えたら二度と戻ってこない唯一の部分です。

## まとめ

- **設定は、日々の失敗から1つずつ作る。** 座って設計するものではありません。自分がどこで詰まるかは、詰まるまで分からないからです
- **層に分けるのは、優先度をつけるため。** 事故はフックへ。手順はスキルへ。事実はメモリへ。全部を`CLAUDE.md`に積むと、全部が同じ重さになります
- **近道はありません。** 他人の設定は、他人の失敗への対策だからです

**自分の環境を直せるのは、自分だけです。**

うまくいかなかったその瞬間に、1分だけ使って直す。それを習慣にするだけです。

自分はそれで、**月100コミットから月270コミットになりました。** 賢くなったわけではなく、同じ説明を二度しなくてよくなっただけです。
