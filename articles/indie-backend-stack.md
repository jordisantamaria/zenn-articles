個人開発のバックエンドを **Vercel（サーバーレス）から Fly.io（サーバー）へ移し、その6日後にデータベースも東京へ移したら、同じエンドポイントが1.9秒から60〜85msになりました。20倍以上**です。月額は$20から$8.3、作業はそれぞれ3時間と2時間でした。

| | 移行前（Vercel） | サーバー移行後 | **いま**（DBも東京） |
|---|---|---|---|
| DBクエリ | 1,541ms | 35ms | **6ms** |
| `/api/health`（日本から） | 約1.9s | 約0.35s | **60〜85ms** |
| コールドスタート | 42.3% | 0 | **0** |
| コスト | Pro $20/月の下限 | 約$3.5/月 | **約$8.3/月** |
| ログ保持 | 1時間 | 30日 | **30日** |

ただ、この記事で伝えたいのは移行の武勇伝でも、**「無料でどこまでやれるか」でもありません。**

**これから何かを作る人が、最初の1時間で決めてしまう部分**の話です。そこを勘で決めた結果が、3週間後の障害寸前でした。

そして選定の基準は安さではなく、**「小さく始めて、大きくなったときに作り直さなくていいか」**——この一点でした。結果として月$8.3になりましたが、それは今の規模に正しく合わせた結果であって、**同じ構成のままプランを上げるだけで10倍・100倍に対応できる**ことのほうが重要でした。最後にその道筋も書きます。

### この記事に書いてあること

- **サーバーレスとサーバーの決め方** — 好みではなく、3つの数字で決まります（測り方も書きます）
- **ホスティングの比較** — Vercel / Cloudflare / Render / Railway / Fly.io / AWS。料金・常時起動・リージョン・設定の持ち方の4軸で
- **データベースの選び方** — Neon / PlanetScale / Supabase / Fly Postgres / AWS RDS。性能・料金・**バックアップ**・AIから触れるかの4軸で
- **リージョンの決め方** — ユーザーの近くに置くのは**間違い**でした
- **無料プランが常時起動と噛み合わない話** — 公開6日前に無料枠が尽きて、DBを引っ越すことになりました
- **そのまま貼れる `fly.toml`** と、サーバーを持つと戻ってくる4つの仕事
- **監視5層の組み方** — ログ / 製品分析 / エラー / 死活監視 / 人間への通知。各層とも無料枠で比較しています
- **AIエージェントから全部触れる状態にしておく** — いま選定基準に足すべきだと思っている項目

**前提を1つ置きます。この記事は最初から最後まで、VCの資金を入れずに自己資金で伸ばすプロダクトの話です。** 半年で100倍を狙う前提なら、判断はまったく変わります。

**そして、ここに書いていないこと。** すでに数十万ユーザーがいて、決済が動いていて、SLAを約束しているなら、この記事の判断はほぼ当てはまりません。扱うのは**リリース直後から3年目くらいまで**の、規模が小さいからこそ踏む落とし穴です。

### 誰に向けて書いているか

AIエージェントでコードが書けるようになって、**動くプロダクトを作るハードルはこの1〜2年で劇的に下がりました。** それ自体はいいことだと思っています。僕もインフラの作業はほとんどClaude Codeに任せています。

でも、下がったのは**実装**のハードルだけです。

- どこで動かすか
- どのデータベースを使うか
- 壊したとき、どこまで戻せるか
- 落ちたとき、誰が気づくか

**この4つは、コードを書く前に決まってしまいます。** そして決めた覚えがなくても、決まります——デフォルト値という形で。僕のリージョンが `iad1`（ワシントンDC）だったのが、まさにそれです。

そして正直に書くと、**これらをAIが代わりに決めてくれることはありません。** 聞けば的確に答えますが、**聞かなかった質問には何も答えない**からです（最後の章で詳しく書きます）。

だからこの記事は、**「コードは動いている。でもこの辺を決めた覚えがない」という人**に向けて書いています。判断そのものより、**判断するための測り方**を残すつもりで書きました。

数字はすべて本番環境の実測か、公式の価格ページからの引用です。推測は推測と書きます。そして「Vercelが高い」という話ではないことは、最後に公平に書きます。

### きっかけ：無料枠の警告メール

「推しスキ」という推し活アプリを個人で作っています。App StoreとGoogle Playに出していて、**実際のユーザーが毎日使っています。**

本番に出して3週間が経ったころ、Vercelから「無料枠の75%を使いました」というメールが届きました。

![Vercelから届いた無料枠の警告メール](/images/vercel-free-tier-warning.png)
*8月21日 19:46。「無料枠を超えると、プロジェクトは自動的に一時停止されます」*

翌朝ダッシュボードを開いたら、そこにあった数字は**96%**。メールが届いてから、わずか**11時間**です。

無料枠を使い切ると、Vercelはチーム内の**全プロジェクトを停止します**。ログインも、共有カタログも、写真のアップロードも止まる。**すでにユーザーがいるアプリが、その日から使えなくなる**ということです。

そして、月のリクエスト数は**約14,500回**でした。ほぼ無風です。

調べたら、無料枠は成功して尽きたのではありませんでした。**トラフィックが少なすぎるせいで尽きていました。**

ここから、全部を測り直すことになります。

## 1. サーバーレスかサーバーかは、好みではなく3つの数字で決まる

この選択は思想の問題ではありません。**測れば決まります。** 必要なのは3つの数字だけです。

### ① コールドスタート率

いちばん効きます。僕の実測は **42.3%** でした。

サーバーレスが明確に勝つのは、**アクセスが同じ時間帯に集中しているとき**です。理由は2つあります。

- アクセスが密なのでインスタンスが温まったまま再利用され、コールドスタートがほぼ起きない
- 使っていない時間帯は課金されない。サーバーは24時間ぶん払います

B2Bの業務アプリのように「平日9時〜18時に一気に来て、夜は誰もいない」形なら、サーバーレスは速くて安い。これは疑いようがありません。

推しスキは逆でした。ユーザーは少なく、アクセスは1日中まばらに散っている。インスタンスは温まらず、42%が起動待ちになる。

> サーバーレスのデメリット（コールドスタート）を全部払って、メリット（密なアクセスでの効率）を一度も使えていなかった。

**トラフィックが少ないことは、サーバーレスにとって有利ではありません。不利です。** ここが直感と逆で、僕も測るまで分かっていませんでした。

**目安：コールドスタート率が20%を超えたら、サーバーを検討する。**

### ② 1リクエストあたりのCPU時間

実測は **Active CPU P75 = 593ms**。処理時間ではありません。ほとんどが **Next.js + Prisma + better-auth を起動し直している時間**です。

サーバーレスの課金はここに乗ります。**フレームワークの起動が重いほど、1リクエストが高くなる。** Next.js + ORM + 認証ライブラリは、起動が重い側の代表です。

逆に、依存が薄いAPI（Honoだけ、といった構成）ならこの数字は小さく、サーバーレスの不利は消えます。**選択はフレームワークにも依存します。**

**目安：起動込みのCPUが300msを超えるなら、常時起動のほうが安い。**

この593msが積み上がった結果が、無料枠の消費です。Vercelのダッシュボードで日次の内訳を見ると、こうなっていました。

![Fluid Active CPUの日次消費。8月22日を境に推しスキの消費が消えている](/images/vercel-fluid-cpu-drop.png)
*チーム全体で 3h36m / 4h。そのうち推しスキだけで2時間40分、74.1%です。緑の棒が推しスキで、8月22日を境に消えているのが移行した日*

チームには3つプロジェクトが載っていますが、**無料枠を食べていたのは実質1つ**でした。そして移行後、その1つが消費表からいなくなっています。

### ③ 1リクエストあたりのDB往復回数

Prismaなら測り方はこれだけです。

```ts
const prisma = new PrismaClient({
  log: [{ emit: 'event', level: 'query' }],
})

let count = 0
prisma.$on('query', (e) => {
  count++
  console.log(`[q${count}] ${e.duration}ms  ${e.query.slice(0, 80)}`)
})
```

いちばん重い画面を1回開いて、`count` がいくつになるか見る。

この数字は2か所で効きます。**サーバーレスかどうか**（この章）と、**サーバーをどこに置くか**（第4章）です。

まずこの章のほう。クエリを投げる前には、TCPハンドシェイク・TLS・Postgresの認証という往復が要ります。常時起動ならこれは最初の1回だけで、あとはコネクションプールに残ったものを使い回せます。**サーバーレスはリクエストごとに起動するので、プールを持ち続けられません。** 冷えたリクエストは、1クエリ目の前にこの往復をもう一度払います。

移行前の `/api/health` は、`SELECT 1` ひとつに1,541msかかっていました。**その大半はSQLの実行ではなく、プールの張り直し**です。**この数字が大きいほど、プールを維持できる常時起動が有利になります。**

もう一方の効き方は単純で、`count` がそのまま**倍率**になります。ユーザー↔サーバーの往復はリクエストにつき1回で固定なのに、サーバー↔DBの往復はクエリの数だけ増えるからです。第4章はこの掛け算の話になります。

ここでN+1が見つかることもよくあります。**往復を減らすのは、引っ越しより先にできる最適化**です。

---

ついでに、測ったから分かったことをもう一つ。ルート別の内訳がこれでした。

```
/api/[[...rest]]   140回
/_not-found         38回   ← ボット
/                   27回
/robots.txt         10回   ← ボット
/admin               6回
/login               6回
```

**実行回数の約20%が、脆弱性を探して回っているボット**でした。トラフィックのないプロジェクトほど、ボットのノイズがコストに占める割合は大きくなります。無料枠の見積もりでは、ここを忘れないほうがいい。

## 2. 落とし穴：「サーバー」を選んでも、寝るサーバーなら同じことが起きる

比較記事であまり書かれない部分です。「じゃあサーバーにしよう」と無料プランを選ぶと、**サーバーレスより悪いコールドスタート**を踏みます。

Renderの公式ドキュメントにこうあります。

> Render **spins down** a Free web service that goes 15 minutes without receiving any inbound traffic.
> A Free web service spins back up whenever it next receives an HTTP request... **This process takes about one minute.**
> — [Render Docs, Free Instance Types](https://render.com/docs/free)

**15分で寝て、起きるのに約1分。** Vercelのコールドスタートが593msだったので、**100倍遅い**ことになります。まばらなアクセスのプロダクトなら、ほぼ全員が1分待つ計算です。

つまり、本当の軸は「サーバーレスかサーバーか」ではありません。

> 本当の軸は **scale-to-zero か always-on か**。ゼロまで落ちるものは、名前が何であれコールドスタートを持ちます。

| | ゼロまで落ちるか | 復帰時間 |
|---|---|---|
| Vercel Functions | 落ちる | 実測 P75 593ms（起動込みCPU） |
| Cloudflare Workers | 落ちる（ただし極小） | 数ms |
| Render Free | **15分で落ちる** | **約1分** |
| Render Starter 以上 | 落ちない | — |
| Railway | 落ちない（従量課金） | — |
| Fly.io（`min_machines_running = 1`） | **落ちない** | — |

**無料の常時起動は、基本的に存在しません。** 月$3〜5は、コールドスタートを買い取る金額だと考えたほうが正確です。

## 3. 料金と機能の比較

少トラフィックのプロダクトを常時起動で置く前提で並べます。数字はすべて公式の価格ページ、2026年8月時点です。

DBと同じく、**いま**と**3年目**（月170万リクエスト）の2列で見ます。3年目はCPU 100ms/リクエスト、東京リージョン、常時1〜2インスタンス相当で計算しました。

料金の列は、**本番として成立する最小のプラン**で揃えます。無料プランは載せません——この記事の冒頭が、まさに**Vercelの無料枠が87人で尽きた話**だからです。

なお **Cloudflare Workersは表から外しました。** 両方の列で最安（$5→$8）になるのですが、**Next.js + Prisma + 認証は載らない**からです（無料枠のCPU制限が10ms/リクエストであることが、その重さを示しています）。軽いAPIを書くなら最有力ですが、この記事の構成では選択肢に入りません。

| | 常時起動できるか | **いま**（本番の最小） | **3年目**（月170万req） | 東京 | 設定の持ち方 |
|---|---|---|---|---|---|
| **Vercel** | **不可**（関数のみ） | **Pro $20**（Hobbyは3週間で枯渇） | **約$27** | ○ `hnd1` | ダッシュボード |
| **Render** | Starter以上（**Freeは15分で停止**） | 〜**$7**（Starter） | 2台で〜**$14** | **✗ なし** | `render.yaml` |
| **Railway** | 可（従量） | **$5**（クレジット込み） | **約$30** | **✗ なし** | ダッシュボード |
| **Fly.io** | 可（`min_machines_running = 1`） | **$3.32** | **約$12**（1GB×2台） | **○ `nrt`** | **`fly.toml`** |
| **AWS ECS（Fargate）+ ALB** | 可 | **約$27** | **約$55** | ○ | Terraform / CDK |

**無料プランが1つも残らないことが、この表の最初の結論です。** 常時起動には最低ラインの費用がある——**月$3〜5は、コールドスタートを買い取る金額**です。

2列目も見ておくと、**AWS以外の4社は$12〜$30に収まります。** この規模で「スケールするか」を心配する必要はほぼありません。**差が出るのは金額ではなく、左右の列のほうです。**

- **RenderとRailwayは日本リージョンが無い** ため、第4章の問題が最初から解けません
- **Vercelは、常時起動できないまま最も高い。** しかも東京が最も高いリージョンで、Active CPUは `iad1` $0.128/時に対し `hnd1` $0.202/時（**+58%**）。速くしようとするほど高くなります
- **AWSは、コンテナを1つも動かさない状態で月$17.74。** ALBの時間課金（東京 $0.0243/時）がトラフィックゼロでも走るからです。最小のFargateタスクを足して**約$27＝Fly.ioの8倍**が入場料でした。EC2起動タイプにしても下がりません——インスタンスを24時間ぶん払ったうえで、ALBは同じだけかかります

### なぜFly.ioが勝つのか

上の表で**常時起動・東京あり・月$5未満**を全部満たすのはFly.ioだけでした。ただ、$2や$3の差は本音を言えば決め手ではありません。決め手は最後の列です。

**設定が1つのTOMLにあって、操作が全部CLIで、出力がテキストで返ってくる。**

一人で開発していて、インフラはAIエージェントに任せています。GUIのコンソールを何画面もクリックして回る構成は、自分でやるぶんには問題なくても、エージェントに任せると破綻します。**「何を選んだか」がどこにも残らない**からです。`fly.toml` はGitに入ります。

**大きなクラウドを選ばない理由も、価格ではありません。** ECS + ALB + RDS + IAM + VPC を一人で見るのと、コンテナ1つを動かすのとでは、**障害が起きたときに原因までたどり着く時間**が違います。オーバーキルの本当のコストは金額ではなく複雑さです。

## 4. リージョンは、ユーザーではなくDBに合わせる

### サーバーにした瞬間、DBの無料枠は成立しなくなった

この章はデータベースの選び方から始まる予定でした。**その予定が、公開日の朝に壊れました。**

![Neonから届いた「無料枠の80%を使った」という警告メール](/images/neon-80-percent-warning.png)
*8月28日 6:00。100 CU-hoursのうち80.2を使った、という通知*

**ユーザーは93人。この6日で6人増えただけです。** 増えたのはトラフィックではありませんでした。

Neonの無料プランが配るのは「100 CU-hours」。0.25 CUの構成なら、**「DBが起きている時間」を月に400時間ぶん**もらえる計算です。ひと月は730時間あります。

> **無料プランは、DBが月の45%眠っている前提で設計されています。**

そしてNeonは5分間アクセスが無いと**サスペンドします**。眠るための条件はそれだけです。ところが第5章で足すヘルスチェックは、`/api/health` を **30秒おき**に叩き、その中身は `SELECT 1` です。

**DBに5分の空きが一生訪れません。**

Neon APIで確認したら、本番のコンピュートは `2026-08-22T00:17:01Z` から一度も止まっていませんでした。**Fly.ioへ移行した、まさにその時刻**です。

| | 起きていた時間 | 月換算 |
|---|---|---|
| 移行前（Vercel、8/1〜8/22） | 1日6.7時間（**28%**） | 約52 CU-h ✅ |
| 移行後（常時起動、8/22〜） | 1日24時間 | **約182 CU-h** ❌ |

**第5章のヘルスチェックが、第4章の前提を壊していました。** 同じ記事の中で、隣り合った章が矛盾していたわけです。

### 条件は1つだけ——壊したときに戻せるか

では、どう選べばよかったのか。**このあとのリージョンの話は、ここで決まったことの結果**でしかないので、選び方から書きます。

**SQLかNoSQLかの議論はしません**（始めると記事が終わらないうえ、この規模ならどちらでも動きます）。比べたのは**マネージドPostgresを6つ**、条件は1つだけ——**壊したときに戻せること**です。バックアップも復旧手段も無いプランは、いくら安くても本番の選択肢に入りません。**安さは条件に入れていません。**

料金は**いま**と**3年目**の2時点で見ます。3年目の中身は、いまの実測から伸ばしました。

| | **いま** | **3年目**（1万人） |
|---|---|---|
| 登録ユーザー | 93人 | **10,000人** |
| リクエスト | 月14,500 | **月約170万** |
| DBサイズ | 34MB | **約3.8GB**（余裕を見て10GBで計算） |

1万人は予測ではありません。**「ここまで来ても構成が壊れないか」を確かめるための数字**で、**いまの100倍のトラフィック**と読み替えても同じです。**下振れで困る構成は誰も作りませんが、上振れで詰む構成はよくある**ので、上限側で見ます。

DBは以下、「メモリ2GB相当を常時起動、ストレージ10GB」で計算しています。

| | いま | **3年目**（1万人） | 日本から最も近いリージョン | **バックアップ** | 備考 |
|---|---|---|---|---|---|
| ~~**Neon**~~ | **$19**（Launch・常時起動） | **約$42** | シンガポール（実測 **73ms**） | PITR 1日 | 起きている時間で課金。**無料枠は月17日で尽きます** |

| Railway Postgres | アプリと同じ$5の枠内 | **約$27** | シンガポール | 他より弱い | アプリもRailwayに寄せるなら |

（内訳の例：RailwayはRAM $10/GB＋CPU $20/vCPU＋ボリューム $0.15/GBなので、2GB＋0.25vCPU＋10GBで約$27。PlanetScaleの価格はus-east-1基準で、東京はやや上がります。AWSはすべて東京の実価格）

> **コストに追われて先に決めるより、収益が出てから一日かけて移すほうが安い。** 先回りして払うのは、未来の自分の問題を今の自分の財布で解決しているだけです。

大事なのは、**その一日で済む設計になっているか**のほうです。

表に載せなかった軸が1つあります。**AIから触れるかは、もう差になりません**——6つとも公式MCPがあります（PlanetScaleとRailwayも2026年に追加）。**AWSだけは壁がMCPの手前**にあって、RDSは既定でVPCの中にいて外から届きません。DBが1つできるまでにVPC・サブネットグループ・SGが要る。設計としては正しいのですが、**一人で小さく始めるには面積が広い**——ECS + ALBを避けたのと同じ判断です。

### ユーザーの近くではなく、DBの近くに置いた

ここがいちばん意外だった部分です。**ユーザーは全員日本にいるのに、サーバーはシンガポールに置きました。**

理由はデータベースです。Neonの公式ドキュメントに載っているリージョンは、**US×3 / Frankfurt / London / Singapore / Sydney / São Paulo** の8つ。**日本はありません。** しかも、

> You cannot change the region for an existing project.
> — [Neon Docs, Regions](https://neon.com/docs/introduction/regions)

**後から変更できません。** 作り直してデータを移すしかない。あとで直せる設定ではなく、最初に決めきる項目です。

そして同じページには「アプリケーションサーバーに近いリージョンを選べ」と書いてあります。正しいアドバイスですが、日本にサーバーを置きたい人には実行不可能です。**だから逆をやります。DBを動かせないなら、サーバーのほうを動かす。**

### 往復の回数を数えると、直感と逆の答えが出る

- ユーザー ↔ サーバー：**1往復**（リクエストにつき1回で固定）
- サーバー ↔ DB：**クエリの数だけ往復**

ここが非対称です。日本からシンガポールまでのRTTは実測 **73ms**（TCPハンドシェイクで7回、中央値）。

```
サーバーが東京：
  ユーザー ↔ 東京          8ms × 1        =   8ms
  東京 ↔ シンガポール    73ms × 3クエリ  = 219ms
                                    合計 ≈ 227ms

サーバーがシンガポール（DBの隣）：
  ユーザー ↔ シンガポール  73ms × 1       =  73ms
  シンガポール ↔ DB        ~1ms × 3クエリ =   3ms
                                    合計 ≈  76ms
```

DBの隣に置くと**掛け算が消えて**、太平洋を渡る往復がリクエストにつき1回だけ残ります。**画面が重いほどこの選択が効きます。**

実測はこうなりました。

| | 移行前（`iad1`） | 移行後（`sin`） |
|---|---|---|
| DBクエリ | **1,541ms** | **35ms** |

40倍。Fly.ioが速いからではなく、**クエリが太平洋を渡るのをやめたから**です。

> 重要なのはユーザーからサーバーまでの距離ではなく、サーバーから**いちばんおしゃべりな依存先**までの距離 × そのおしゃべりさ。

移行前の構成は `iad1`（ワシントンDC）でした。**誰も選んだ覚えのないデフォルト値**です。日本のユーザーのリクエストがワシントンで処理され、クエリがシンガポールへ飛んでいた。サーバーレスの「設定を書かなくていい」という美点の裏側がここで、**書かなかった設定にもデフォルト値は入ります。**

逆に、東京に置くのが正しいのは **1リクエストあたりのクエリが1回以下のとき**です。キャッシュが効いてDBにほとんど触らないAPIなら東京でいい。数えてから決めてください。

### だから、DBを東京に移しました

移行先はPlanetScale Postgres。決め手は価格ではなく、**課金の単位がインスタンスであること**、そして**東京があること**でした。

| | いま | 移行後 |
|---|---|---|
| DB | Neon シンガポール | **PlanetScale 東京** |
| 課金 | 起きている時間 | **インスタンス** |
| 料金 | 無料枠（**月17日で尽きる**） | **$5** |
| バックアップ | PITR 6時間 | 12時間ごと + PITR **2日** |
| 日本からのRTT | 73ms | **8ms** |

作業は2時間弱でした。11MBのダンプとリストアが15秒、あとは接続文字列の差し替えと、**サーバーを `nrt` へ動かすこと**です。

そう、**第4章の結論はそのまま生きています。** ルールは「サーバーはDBの隣」で、変わったのはDBが動けるようになったことだけ。8月22日はDBが動けなかったからサーバーがシンガポールへ行き、8月28日はDBが東京へ行けたのでサーバーがついていきました。**同じルールで、逆の答えです。**

そして最後に、いちばん恥ずかしいものが出てきました。

### 常時起動にしたのに、コネクションプールが無かった

東京同士になったのに、`/api/health` の `SELECT 1` が **50〜64ms** かかっていました。ネットワークは実測4ms、PlanetScaleの管理画面が出すサーバー側のp50は**0.19ms**。50msが説明できません。

犯人はこれでした。

```ts
function getPrismaClient(): PrismaClient {
  if (globalThis.prisma) return globalThis.prisma

  const client = prismaClientSingleton()

  if (process.env.NODE_ENV !== 'production') {
    globalThis.prisma = client        // ← 本番ではキャッシュしない
  }

  return client
}
```

Next.jsでよく見る書き方です。あちらでキャッシュがdev限定なのは、**ホットリロードを生き延びるためだけ**の仕掛けで、本番はモジュールが一度しか評価されないからモジュールスコープの `const` で足りるからです。

ところがこのコードでは `db` がProxyで、**プロパティに触るたびにこの関数を呼びます。** つまり本番では、クエリ1回ごとに新しいPrismaClientと新しいプールと新しいコネクションが生まれていました。**毎回、TCPハンドシェイクとTLSとPostgresの認証から。**

1行直した結果です。

| | 修正前 | 修正後 |
|---|---|---|
| `SELECT 1` | 50〜64ms | **6ms** |
| リクエスト全体（日本から） | 117〜147ms | **58ms** |

**プールを維持できることを理由に常時起動へ移って、プールを維持していませんでした。** ずっとです——Neonの時代も含めて。第4章で「シンガポールが遠いから」と説明していた遅さの一部は、これでした。

> 移行の価値の半分は、**普段見ないところを全部見ることになる**ことだと思います。3つ壊れているのが見つかった、と第9章に書きました。これで4つ目です。

## 5. そのまま貼れる `fly.toml` と、サーバーを持つと戻ってくる4つの仕事

サーバーレスをやめるということは、**サーバーレスが肩代わりしてくれていた仕事が自分に返ってくる**ということです。4つあり、うち3つの手当てがこのファイルに入っています。

```toml
app = "my-app"
primary_region = "nrt"   # ← DBの隣（第4章）。いまは東京にDBがあるので東京

[deploy]
  # ② デプロイのたびに止まる、への対処
  strategy = "bluegreen"
  release_command = "sh -c 'cd /migrate && node node_modules/prisma/build/index.js migrate deploy'"

[http_service]
  internal_port = 3000
  force_https = true
  auto_stop_machines   = "stop"   # 余った台だけ止める
  auto_start_machines  = true
  min_machines_running = 1        # ← コールドスタートを消す1行
  max_machines_running = 2        # ① リソースの天井（ハードキャップ）

[http_service.concurrency]
  type = "requests"
  soft_limit = 80    # ここを超えたら2台目が起きる
  hard_limit = 120

[[http_service.checks]]
  path = "/api/health"   # SELECT 1 を打つ。DBに届かなければ503
  interval = "30s"
  timeout  = "10s"
  grace_period = "20s"

[[vm]]
  size   = "shared-cpu-1x"
  memory = "512mb"   # Vercelでの実測平均が294MBだったので
  cpus   = 1
```

`min_machines_running = 1` が問題を解いている1行です。`auto_stop_machines` を切るのではなく、**最低1台を保証する**のがポイント。余った台は止まって構わないので。

### ① リソースには天井がある

サーバーレスならCPUもメモリも勝手に増えます。サーバーは増えません。天井に当たった時点でユーザーはアプリを使えなくなります。

→ **オートスケール、ただし上限2台。** 上限なしにするとボットの波がそのまま請求額になります。弾力性より封じ込めを選ぶ、技術ではなくリスクの判断です。

ただ、理由はそれだけではありません。**そもそも台数を増やしても速くなりません。**

| | 値 |
|---|---|
| DBのCPU | **1/16 vCPU 固定**（PS-5） |
| `max_connections`（直結） | **25** |
| プーラー経由（PgBouncer） | 400 |

アプリを何台に増やしても、この1/16 vCPUは1ミリも増えません。しかも各インスタンスは自分のプールを持つので、**台数×プールが、増えない枠を取り合います。** キャパシティが上がる前に、コネクションの奪い合いが先に起きる。

そして直結は**25本しかありません。** 2台なら足ります（Prismaの既定プールは `shared-cpu-1x` で3本前後）が、`bluegreen` は新旧2バージョンが同時に生きる瞬間があるので、そこが一番きわどい。**台数を増やすならプーラー経由に変える**——そしてPrismaはトランザクションモードのプーラーに対して `?pgbouncer=true` を付けないと、prepared statementで妙な壊れ方をします。

> 横に並べる前に、「一緒にスケールしてくれないのはどれか」を数える。たいていそれは、状態を持っている側です。

だから2台目は、速くするためではなく**止まらないための2台目**です。

### ② デプロイのたびに止まる

サーバーではデプロイ＝プロセスの再起動です。デフォルトの `rolling` は、マシンが1台だと「古いのを止めてから新しいのを起動する」——ただの再起動になります。

うまくいって30秒。ただし新しいほうが起動に失敗したら（マイグレーションがこけた、環境変数が1つ足りない）**古いほうはもう止めた後**です。しかも、いちばん失敗しやすい日といちばん止まると困る日は同じです。大きな変更を出す日なので。

→ **`strategy = "bluegreen"`。** 古いのを止める前に新しいのを隣に立て、ヘルスチェックが通ってから切り替える。通らなければ古いほうが働き続けます。2台目はデプロイ中しか存在しないので、費用は1デプロイ数セントです。

「正常」の定義も大事で、プロセスが起動しただけでは正常ではありません。`/api/health` は `SELECT 1` を打っていて、アプリが生きていてもDBに届かなければ503を返します。**アプリは生きているのにDBに届いていない、が実際の落ち方**なので。

### ③ 攻撃は、規模に関係なく来る

会社で小さなスタートアップのアプリを何本も作りましたが、攻撃は数え切れないほど起きました。有名である必要はありません。公開されたIPとポートがあれば十分です。

| | 攻撃を受けたとき |
|---|---|
| サーバーレス | 請求書が跳ね上がる |
| サーバー | 落ちる |

→ **CloudflareをプロキシモードにしてWAFをサーバーの前に置く。** 無料で、トラフィックが自分のサーバーに届く前に止まります。コスト側の蓋は①の上限2台が兼ねています。

### ④ 落ちても、誰も教えてくれない

サーバーレスなら、落ちているかどうかはプラットフォームの問題です。サーバーでは自分の問題になります。そして一人で開発していると、気づくのはユーザーからの連絡です。

これは設定1行では終わらないので、章を分けます。

## 6. 監視の全体像——ログ・製品分析・エラー・メール

「監視を入れる」と言うとき、実際には**性質の違う4つ**を入れることになります。ここを混ぜると、どれも中途半端になります。

| 層 | 答える問い | どこで動くか | 使っているもの |
|---|---|---|---|
| **死活監視** | そもそも生きているか？ | **完全に外** | Better Stack |
| **ログ** | いま何が起きた？ なぜ落ちた？ | 外 | Axiom |
| **製品分析** | ユーザーは何をした？ どこで離脱した？ | 外 | PostHog |
| **エラー追跡** | どのコードが、誰に対して壊れた？ | 外 | PostHog Error Tracking |
| **人間への通知** | **私はいま動くべきか？** | 外 | メール |

「どこで動くか」の列が効いてきます。ヘルスチェックはインフラの**内側**で動くので、ネットワークごと死ねば**チェックする側も一緒に消えて、失敗の通知すら来ません。**

> 監視対象の内側にある監視は、監視対象と一緒に死にます。

だから5つとも外に置いています。そして最後の1つが抜けがちです。上の4つは「見に行けば分かる」もので、**一人で開発していると見に行きません。** ダッシュボードを毎日開く人はいません。開くのは、ユーザーから「アプリが動きません」と連絡が来た後です。

**そして、1ツールで全部やろうとしないのが結論でした。** 層ごとに無料枠の形がまったく違うので、得意なところを使い分けたほうが安く済みます。

### 死活監視：`fly.toml` のヘルスチェックとは別に、外から叩く

`fly.toml` に書いた `[[http_service.checks]]` は、Fly.ioが自分のネットワークの中から叩くものです。**デプロイの安全装置としては必須ですが、死活監視ではありません。** Fly.ioのリージョンごと落ちたら、チェックする側も一緒に落ちるので。

だから、まったく別の会社のサーバーから `/api/health` を叩いてもらいます。ここも無料枠で比べました。

| | 無料枠 | チェック間隔（無料） | **3年目**（監視対象8つ） | 有料 |
|---|---|---|---|---|
| **Better Stack** | モニタ10 + **ハートビート10** + ステータスページ | 3分 | **無料のまま** | 30秒チェック、50モニタ追加で$25/月 |
| UptimeRobot | モニタ**50** | 5分 | **無料のまま** | $9/月で60秒 |

**この層だけは、ユーザー数で増えません。** 増えるのは**監視対象の数**です。いまはAPIとランディングの2つですが、3年目には管理画面、ブログ、クローラーやリマインダーのcron（ハートビート）が加わって、**8つ前後**でしょう。それでも10枠に収まります。

> **ユーザーが100倍になっても、監視すべきものは100倍にはなりません。** だからここは、最初からちゃんと入れておいても後で困りません。

**モニタの数はUptimeRobotが5倍多い**（50対10）。間隔は3分対5分で、正直そこまで差はありません。プロダクトが1つなら10モニタで足りるので、数は決め手になりませんでした。

決め手は**ハートビート**のほうです。これはこちらから「動いた」と定期的に報告して、**来なくなったら鳴る**仕組みで、cronやバッチ処理のための監視です。定期実行が「エラーを出す」のではなく「**そもそも走らなかった**」という落ち方は、ログをいくら見ても気づけません。**無いものは表示されない**ので。

これも実例が出ました。毎朝9時にチケット締切のリマインダーを送るcronがあるのですが、**8月25日と26日、動いていませんでした。**

> The job was not started because recent account payments have failed or **your spending limit needs to be increased**.

GitHub Actionsの無料枠を使い切っていたのです。ジョブは**起動すらしていない**ので、赤いrunもログの1行も残りません。気づいたのは、3日後に履歴を手で遡ったときでした。**2日ぶんのリマインダーが、誰にも届いていませんでした。**

考え方は前の章と同じです。

> 鳴るべき音が消えたことを検知する。

そして、ここでも1ツールに寄せる必要はありません。**ログはAxiom、死活監視はBetter Stack**——Better Stackにもログ機能はありますが、無料枠が月3GB・保持3日なので使っていません。**層ごとに得意なところを使えば、両方とも無料のままです。**

### ログ：60行の自前トランスポートと、譲れない3つのルール

まず、**プラットフォーム標準のログはどれも障害調査には足りません。** Vercel Hobbyの保持は**1時間**で、障害の翌朝には何も残っていませんでした。Fly.ioの `fly logs` は在庫のない生放送で、見ていなかったぶんは消えます。だからどこかに送る必要があります。

送り先を無料枠で比べると、こうでした（2026年8月時点、各社の価格ページより）。

ここは**3年目でも無料枠に収まります。** 発生量はいま月15MB、1万ユーザーに伸ばしても**月1.7GB**の計算です。

| | 無料枠 | **保持** | 3年目（月1.7GB）の使用率 |
|---|---|---|---|
| **Axiom** | 月500GB | **30日** | **0.3%** |
| Grafana Cloud | 月50GB | 14日 | 3.4% |
| Better Stack Telemetry | 月3GB | **3日** | **56%** |
| Vercel Hobby（標準） | — | **1時間** | — |

**つまりログは、容量ではなく保持で選ぶ層です。** 3つとも容量は足りていて、差が出るのは保持のほうだけ。障害を調べるのはたいてい翌朝なので、**保持が3日を切ると使いものになりません。**

とはいえ余裕も無視できません。Better Stackは3年目に無料枠の**半分以上**を使う計算で、そこから先は有料（Nano $45/月）。Axiomは0.3%なので、**この層は当面ゼロ円で回り続けます。**

SDKは入れず、ingest APIに直接POSTしています。そのとき決めた3つのルールが、結果的にいちばん効きました。

**1. 絶対にアプリを落とさない。** これは思想ではなく、**実際に落としたから**書いています。

最初、`beforeExit` でflushするハンドラを書いていました。このイベントはイベントループが空になったとき、つまりプロセスが終わろうとするときに発火します。そこで `fetch` するとループが復活し、ソケットがリクエストの途中で死んで、undiciが**awaitの外で**未捕捉の例外を投げる。それが `release_command`（`prisma migrate deploy`）を巻き込んで、Flyは「マイグレーション失敗」と判断しました。

**監視の仕組みがアプリを落とす。** これを避けるためのコードがこれです。

```ts
await fetch(url, {
  signal: AbortSignal.timeout(10_000),   // Axiomが遅ければ諦める
}).catch(() => {})   // ← try/catch に「加えて」必要。undici は await の外で投げる
```

そして flush のフックは `beforeExit` ではなく **SIGTERM / SIGINT** に付けました。Fly.ioがマシンを止めるときに送るのはSIGTERMで、そこには猶予があります。

**2. 絶対にブロックしない。** 送信は待たずにキューに積んで、50件か2秒で一括送信。キューには上限（1,000件）を付けます。**上限のないキューは、Axiomが落ちた日にメモリリークになってマシンを殺します**——つまりログの仕組みでサービスが落ちる、また同じ失敗です。

**3. 絶対に個人情報を送らない。** キー名でマスクします（`email` / `token` / `name` / `title`…）。値を見て「これはメールアドレスっぽい」と判定するのは脆く、**偽陰性はユーザーのメールを第三者に送ることを意味します。**

そしてもう一つ、地味にいちばん時間を溶かしたのがこれです。

```ts
// ESC は \u001b と書く。制御文字をソースに直接置くと、コピペや整形で壊れる
const ANSI = /\u001b\[[0-9;]*m/g   // ← これが無いと検索できない
```

consolaやHonoのロガーはステータスコードをANSIで色付けします。それがそのままAxiomに入ると、`200` の前後に色コードが付いた文字列になり、**`200` で検索しても何もヒットしません。** 障害のときにいちばん検索したい文字列が、色コードに埋もれていました。

### いちばん効いたアラートは「エラーが出た」ではなかった

外に置いたログには、もう一つ使い道があります。**アラートです。**

だから最初に作ったアラートはこれです。

```
['fly-logs']
| where _time > ago(15m)
| summarize count()
// → 0 のとき発火
```

**「15分間ログが1行も来ていない」。** エラーが出ないほど静かに死ぬ落ち方が、いちばん怖いからです。

### 遅くなったことに気づくアラート

5xxもログ停止も、「遅くなった」は捉えません。実ルートの中央値を別に見ます。

```
['fly-logs']
| where _time > ago(12h)
| where message startswith '-->'
| extend ms = toint(extract(@' (\d+)ms$', 1, message)),
         ruta = extract(@'^--> \w+ (\S+)', 1, message)
| where isnotnull(ms) and not(ruta startswith '/api/health')
| summarize p50 = percentile(ms, 50), n = count()
| extend valor = iff(n >= 25, p50, 0.0)
| project valor
// → 250ms を超えたらメール
```

- **ヘルスチェックを除く。** `/api/health` は `SELECT 1` なので、アプリが遅くなっても速いままです。混ぜると薄まります
- **`n >= 25` を入れる。** 母数の少ない時間帯の中央値で誤発火させないため
- **ウィンドウは12時間。** 1日150リクエストだと3時間では母数が足りず、安定していても中央値は302〜663msで暴れました。**スライディングウィンドウは、検知にかかるのと同じだけ消えるのにも時間がかかります。** だから24時間にはしません。直した後もしばらく鳴り、開いている間は次の通知が来ません

### 製品分析とエラー追跡を、1つのツールに寄せる

PostHogを選んだ理由は、**ウェブとアプリで同じプロジェクトに入れられる**ことでした。ランディングページ（`posthog-js`）とReact Nativeアプリ（`posthog-react-native`）が別ツールだと、**「サイトに来た」と「アプリを開いた」の間で計測が切れます。** その断面がいちばん知りたい場所なのに。

エラー追跡も同じ場所に寄せました。Sentryではなく PostHog Error Tracking です。理由は無料枠の中身で、**Sentryの無料枠にはRelease Healthが付きません**（どのリリースからクラッシュが増えたか、が分からない）。

`posthog-js` は **231KB** あり、ランディングで最大のチャンクでした。動的importにして、`requestIdleCallback`（Safari向けに `setTimeout` のフォールバック付き）で**ページ描画が終わってから**読み込んでいます。分析ツールが分析対象の速度を落とすのは本末転倒なので。

### そして、人間に届ける最後の一手

管理画面のキューは静かに溜まります。ユーザーからの不具合報告、「イベントの時間が違う」という指摘、承認待ちの投稿。**全部データベースには存在していますが、誰かが見に行くまで存在しないのと同じです。**

だからキューに何か入った瞬間にメールを送ります。

```ts
export async function notifyAdmin({ kind, subject, details }: AdminAlertInput) {
  const to = process.env.ADMIN_ALERT_EMAIL?.trim()
  if (!to) return          // ← 環境変数が無ければ黙る。local と dev と CI はこれで静か

  try {
    await sendEmail({ to, subject: `[MyApp] ${subject}`, text, html })
  } catch (error) {
    logger.error('[admin-alert] failed to send', error)   // ← 絶対に投げない
  }
}
```

設計の要点は3つです。

- **絶対に投げない。** 呼び出し元はユーザーが送信した内容を保存している最中です。メール基盤が落ちていることが、ユーザーの投稿を失う理由になってはいけません
- **環境変数が無ければ何もしない。** これだけで local / dev / テストが静かになります。「通知先が存在する環境にだけ通知が存在する」
- **即時に送り、まとめない。** 1日1回のダイジェストは、ユーザーを24時間待たせるという意味です。まとめる価値が出るのは量が増えてからで、そのとき変えるのはこの1ファイルだけで済みます

**メールは、4つの層のうち唯一こちらから人間に届く経路**です。他の3つは、こちらが見に行かないと何も起きません。

### 結局、何がメールで届くのか

| 届くもの | 送り主 | 鳴る条件 | やること |
| --- | --- | --- | --- |
| 落ちた | Better Stack Uptime | `/api/health` が3分応答しない | 今すぐ復旧する |
| ランディングが壊れた | Better Stack Uptime | ページに製品名の文字列が無い | ホスティング側を見る（200は返っている） |
| 定期実行が止まった | Better Stack Uptime | ハートビートが24時間来ない | 走らなかった原因を探す（ログは無い） |
| ログが消えた | Axiom | 15分間ログが0行 | 生きているかを外から確かめる |
| 5xx | Axiom | 5分以内に1件でも | 直近のデプロイを疑う |
| エラーが増えた | PostHog | 週1回のダイジェスト（即時通知は無い） | 増えたエラーを直す |
| 待たされている人がいる | Axiom | 15分で1.5秒超が2件以上 | 刺さっているルートを特定する |
| DBが遅い | Axiom | `/api/health` のp95が10分で150ms超 | 接続とインスタンスを見る |
| 全体が遅くなった | Axiom | 実ルートの中央値が12時間で250ms超 | 性能を見直す（急がなくていい） |
| 人間待ちが溜まった | アプリ | 問い合わせ・報告・承認待ちが入った瞬間 | 管理画面を開く |

## 7. 全部を、AIから触れる状態にしておく

ここが、いま構成を選ぶなら足すべきだと思っている基準です。

インフラを組むのは**一度きり**の作業でした。全部で3時間。**運用は毎日です。** そして一人でやっていると、最初に消えるのが運用です。

AxiomにもPostHogにも**MCPサーバー**があります。つまりAIエージェントは、僕がダッシュボードのスクリーンショットを貼るのではなく、**データセットに直接クエリを投げられます。**

```bash
npx @posthog/wizard mcp add     # PostHog（HogQL、エラー、フラグ）
```

Axiom側はAPL（Axiom Processing Language）のクエリ、データセット一覧、モニタの作成・履歴まで触れます。実際に投げているのはこういう依頼です。

- 「直近24時間の5xxをルート別に出して。増えてるものがあれば、いつから増えたかも」
- 「レイテンシのP95が上がってる時間帯があるか見て。あればそのときのログを10件」
- 「このスパイク、ボットか人間か判断して。判断の根拠も」
- 「PostHogで、オンボーディングのどのステップの離脱がいちばん大きいか出して」

これは「見やすくなった」という話ではありません。**そもそも僕が毎日はやらない作業**が、実行されるようになったという話です。

実際、この構成で見つかった問題はほとんどそうやって出てきました。ANSIコードでログが検索できなくなっていたことも、デプロイを落としていた真犯人がログ送信そのものだったことも（画面上はマイグレーション失敗に見えていました）、**気づいたきっかけは両方ともログへのクエリ**です。ダッシュボードを眺めて見つかるものではありません。

### だから、選定基準に1つ足す

> **そのサービスの「状態」は、テキストで問い合わせられるか。**

きれいなダッシュボードは、人間には価値があります。**エージェントにとっては存在しないのと同じです。** 逆に、CLIとAPIとMCPで中身が引き出せるなら、それは毎日見てもらえるインフラになります。

第3章の比較表に「設定の持ち方」という列を入れたのは、そのためです。`fly.toml` がGitに入ること、`fly logs` がテキストを返すこと、AxiomにAPLで問い合わせられること——これらは同じ性質の話です。

「AIに管理させやすいか」がインフラ選定の基準に入るようになったのは、たぶんここ1〜2年のことです。でも一人で開発しているなら、**これは価格と同じくらい実務に効きます。**

### ただし、「何を聞くか」は向こうからは出てきません

正直に書いておきます。**エージェントがくれるのは情報と選択肢までです。**

この記事に出てくる判断は、ほとんどがAIの提案ではありませんでした。

- Proを払わずにサーバーへ移すと決めたこと。数字は両方出ていました。42%を「このプロダクトでは許容できない」と判断したのは、数字ではなくプロダクト側の話です
- **ユーザーが100人に満たない時点でボット対策を入れる**と決めたこと
- オートスケールに2という天井をつけると決めたこと
- 監視を初日から入れると決めたこと

2つ目がいちばん分かりやすい例です。**「まだ誰も使っていないのに、攻撃を心配すべきか？」という質問を、そもそも誰も思いつきません。** 統計的に見れば、この規模で身構えるのは過剰です。

僕がそれを入れたのは、会社で小さなスタートアップのアプリを何本も作って、**攻撃が実際に何度も起きたのを見ているから**です。これは検索して出てくる知識ではなく、**痛い目に遭った記憶**です。

エージェントは、投げた質問には的確に答えます。**投げられなかった質問には、何も答えません。**

> AIが速いのは「調べること」です。「何を調べるべきか」を決めているのは、まだ経験のほうです。

そして経験のいいところは、AIが速くなっても目減りしないことだと思っています。むしろ調べるのが速くなるほど、**正しい問いを持っている人の生産性だけが伸びていきます。**

## 8. この構成は、10倍・100倍でどうなるか

ここまでの構成は「今が小さいから」選んだものではありません。**大きくなったときに何を捨てることになるか**を数えたうえで選んでいます。その答えを書いておきます。

| 増えたもの | やること | 作り直しが必要か |
|---|---|---|
| トラフィック10倍 | `fly scale count 4` / `max_machines_running` を上げる | **不要**（同じ `fly.toml`） |
| 1台のCPU・メモリ不足 | `fly scale memory 2048` | **不要** |
| DBが詰まってきた | PlanetScaleのSKUを上げる（PS-5 → PS-10 → …） | **不要**（ただし再起動が入る） |
| ログが増えた | Axiomは従量。500GBを超えたら課金 | **不要** |
| イベントが増えた | PostHogも従量 | **不要** |
| チームが増えた | `fly.toml` はGitにあるのでレビューできる | **不要** |

**いまは、全部プランを上げるだけです。** ただし順番があって、**先に上げるのはアプリではなくDBのプラン**です——アプリを横に並べてもDBのvCPUは増えないので（第5章）。逆にすると、コネクションの奪い合いが起きてお金だけが増えます。

### 4つの層を合計すると

この記事で選んだ構成を、層ごとに並べるとこうなります。

| 層 | いま | **3年目**（1万人） | **選択で変わるか** |
|---|---|---|---|
| ホスティング（Fly.io） | $3.32 | **約$12** | **○** 他社なら最大$30（2.5倍） |
| データベース（PlanetScale） | $5 | **約$17** | **○** 他社なら$17〜$72（4倍） |
| ログ（Axiom） | $0 | **$0** | ✗ どこでも無料枠に収まる |
| 死活監視（Better Stack） | $0 | **$0** | ✗ 監視対象の数で決まる |
| **合計** | **約$8.3/月** | **約$29/月** | |

3年で1万人まで伸びて**月$29**。個人開発として払えない額ではないと思います。

そして右の列が、この記事でいちばん持ち帰ってほしいことです。

> **将来を見て決めるべきなのは、ホスティングとデータベースの2つだけ。** この2つで3年目の金額がほぼ決まります。逆に**ログと死活監視は、いま都合のいいものを選んでいい**——スケールしても値段が動かないので、後から選び直すコストのほうが高くつきます。

## 9. 移行そのものは3時間でした

当日にユーザーへ告知しているので、時刻が残っています。

![メンテナンスの告知](/images/x-maintenance-notice.png)
*8月22日 8:03。「本日中（遅くとも明日まで）」と予告しています*

![メンテナンス完了の報告](/images/x-maintenance-done.png)
*同じ日の 11:01。告知から2時間58分後です*

踏み切れた理由は勇気ではなく、**戻し方が用意されていたから**です。CloudflareのTTLを事前に60秒に下げてあったので、DNSをVercelに戻せば数十秒で元通りでした。**「失敗したらどうする」に秒単位で答えられるなら、それはもうリスクの高い作業ではありません。**

**最後にVercelのために公平に書いておきます。** 593ms/リクエストは42%のコールドスタートの結果であって、トラフィックが密になればインスタンスが再利用されてこの数字は大きく下がります。**Vercelはスケールすると良くなります。** この記事の結論は「Vercelが高い」ではなく、「**僕のトラフィックの形に合っていなかった**」です。

## 10. なぜ、速さが必要だったのか

最後に、この速さが何の役に立つのかを書いておきます。ここが抜けると、ただのベンチマーク自慢になるので。

**推しスキは、机の前で開くアプリではありません。** 現場で、ライブの合間に、片手で開きます。推しの出番が何時なのかを確認するために、もう片方の手にはペンライトを持って、電波の悪い会場で。

その状況で2秒待たされるのは「遅い」とは読まれません。**「壊れている」と読まれます。** そして画面を閉じる。

失われるのは1セッションではなく、**習慣**です。予定を管理するアプリは、現場に行く前に開いてもらえないと存在価値がありません。最初の3回もたついたら、4回目はない。

しかも42%というのは平均の遅さではなく、**ばらつき**です。あるときは一瞬で開き、あるときは2秒待つ。規則性がない。**予測できないアプリは、一貫して遅いアプリより体感が悪い**というのが、今回いちばん腹に落ちたことでした。

---

並べてみると、**この記事の結論はほとんどが直感と逆**です。

- **トラフィックが少ないのはサーバーレスに有利**だと思っていました。実際は不利でした。温まらないので
- **「サーバーにすれば解決する」と思っていました。** 無料プランの多くはゼロまで落ちて、復帰に1分かかります。名前ではなく、落ちるかどうかが軸でした
- **サーバーはユーザーの近くに置くもの**だと思っていました。実際はDBの隣でした。往復の回数が非対称なので
- **監視とは「エラーを検知すること」だと思っていました。** いちばん効いたのは「**ログが1行も来ていない**」でした
- **ダッシュボードを入れれば見る**と思っていました。見ませんでした。届いたのはメールだけです
- **インフラ選定は価格と機能で決まる**と思っていました。いまは「**AIから触れるか**」という列が増えています
- **無料プランは規模が小さいうちは安全**だと思っていました。無料枠が尽きたのは、ユーザーが増えたからではなく**サーバーを常時起動にしたから**でした
- **常時起動にすればプールは維持される**と思っていました。**コードがそうなっていませんでした。** そのために引っ越したのに

デフォルト値のままだった `iad1`（ワシントンDC）も、誰かが選んだわけではありません。**選ばなかっただけ**です。そして選ばなかった結果が、3週間後の96%でした。

---

**この判断に必要だったのは、知識ではなく3時間の計測でした。** 42.3%も、593msも、73msも、調べて出てきた数字ではありません。自分のプロダクトを測って出た数字です。

だから持ち帰ってほしいのは、移行先の名前ではありません。**コールドスタート率・1リクエストのCPU時間・1リクエストのDB往復回数**——この3つを測れば、答えは自分で出せます。そして出した答えは可逆です。トラフィックの形が変われば、Vercelに戻すことも十分あり得ます。
