「推しスキ」という推し活アプリを個人で作っています。App StoreとGoogle Playに出していて、**実際のユーザーが毎日使っています。**

本番に出して3週間が経ったころ、Vercelから「無料枠の75%を使いました」というメールが届きました。慌ててダッシュボードを開いたら、そこに出ていた数字は**96%** でした。

無料枠を使い切ると、Vercelはチーム内の**全プロジェクトを停止します**。ログインも、共有カタログも、写真のアップロードも止まる。**すでにユーザーがいるアプリが、その日に使えなくなる**ということです。

そして、月のリクエスト数は**約14,500回**でした。ほぼ無風です。

調べたら、無料枠は成功して尽きたのではありませんでした。**トラフィックが少なすぎるせいで尽きていました。**

原因を測って、バックエンドをVercelからFly.ioへ移すところまで、**メールが届いた当日のうちに終わりました。** 実測の結果がこれです。

| | 移行前（Vercel） | 移行後（Fly.io） |
|---|---|---|
| DBクエリ | 1,541ms | **35ms** |
| リクエスト全体 | 約1.9s | **約0.35s** |
| コールドスタート | 42.3% | **0** |
| コスト | Pro $20/月の下限 | **約$3.5/月** |
| ログ保持 | 1時間 | 30日 |

**約5倍速くなって、月額は下がりました。**

この記事は、その3時間で何を測って、何をどう判断したかを、**そのまま真似できる形**で置いておくものです。

- サーバーレスとサーバーを、**3つの数字**で決める
- **無料の常時起動は存在しない**という落とし穴
- 主要サービスの**料金と機能の比較**（Vercel / Cloudflare / Render / Railway / Fly.io / AWS）
- そのまま貼れる **`fly.toml`** と、サーバーを持つと戻ってくる4つの仕事

数字はすべて本番の実測か、公式の価格ページからの引用です。「Vercelが高い」という話ではないことは、最後に公平に書きます。

この構成の残り2つ——**リージョンをどう決めるか**と**監視をどう組むか**——は分量があるので別記事にしました。最後にリンクを置いています。

## 1. サーバーレスかサーバーかは、好みではなく3つの数字で決まる

この選択は思想の問題ではありません。**測れば決まります。** 必要なのは3つの数字だけです。

### ① コールドスタート率

いちばん効きます。僕の実測は **42.3%** でした。

サーバーレスが明確に勝つのは、**アクセスが同じ時間帯に集中しているとき**です。理由は2つあります。

- アクセスが密なのでインスタンスが温まったまま再利用され、コールドスタートがほぼ起きない
- 使っていない時間帯は課金されない。サーバーは24時間ぶん払います

B2Bの業務アプリのように「平日9時〜18時に一気に来て、夜は誰もいない」形なら、サーバーレスは速くて安い。これは疑いようがありません。

推しスキは逆でした。ユーザーは少なく、アクセスは1日中まばらに散っている。インスタンスは温まらず、42%が起動待ちになる。

> サーバーレスのデメリット（コールドスタート）を全部払って、メリット（密なアクセスでの効率）を一度も使えていなかった。

**トラフィックが少ないことは、サーバーレスにとって有利ではありません。不利です。** ここが直感と逆で、僕も測るまで分かっていませんでした。

**目安：コールドスタート率が20%を超えたら、サーバーを検討する。**

### ② 1リクエストあたりのCPU時間

実測は **Active CPU P75 = 593ms**。処理時間ではありません。ほとんどが **Next.js + Prisma + better-auth を起動し直している時間**です。

サーバーレスの課金はここに乗ります。**フレームワークの起動が重いほど、1リクエストが高くなる。** Next.js + ORM + 認証ライブラリは、起動が重い側の代表です。

逆に、依存が薄いAPI（Honoだけ、といった構成）ならこの数字は小さく、サーバーレスの不利は消えます。**選択はフレームワークにも依存します。**

**目安：起動込みのCPUが300msを超えるなら、常時起動のほうが安い。**

### ③ 1リクエストあたりのDB往復回数

これが次の章のリージョンの話に効きます。Prismaなら測り方はこれだけです。

```ts
const prisma = new PrismaClient({
  log: [{ emit: 'event', level: 'query' }],
})

let count = 0
prisma.$on('query', (e) => {
  count++
  console.log(`[q${count}] ${e.duration}ms  ${e.query.slice(0, 80)}`)
})
```

いちばん重い画面を1回開いて、`count` がいくつになるか見る。**サーバーレスはリクエストごとに起動するので、コネクションプールを持ち続けられません。** この数字が大きいほど、プールを維持できる常時起動が有利になります。

ここでN+1が見つかることもよくあります。**往復を減らすのは、引っ越しより先にできる最適化**です。

---

ついでに、測ったから分かったことをもう一つ。ルート別の内訳がこれでした。

```
/api/[[...rest]]   140回
/_not-found         38回   ← ボット
/                   27回
/robots.txt         10回   ← ボット
/admin               6回
/login               6回
```

**実行回数の約20%が、脆弱性を探して回っているボット**でした。トラフィックのないプロジェクトほど、ボットのノイズがコストに占める割合は大きくなります。無料枠の見積もりでは、ここを忘れないほうがいい。

## 2. 落とし穴：「サーバー」を選んでも、寝るサーバーなら同じことが起きる

比較記事であまり書かれない部分です。「じゃあサーバーにしよう」と無料プランを選ぶと、**サーバーレスより悪いコールドスタート**を踏みます。

Renderの公式ドキュメントにこうあります。

> Render **spins down** a Free web service that goes 15 minutes without receiving any inbound traffic.
> A Free web service spins back up whenever it next receives an HTTP request... **This process takes about one minute.**
> — [Render Docs, Free Instance Types](https://render.com/docs/free)

**15分で寝て、起きるのに約1分。** Vercelのコールドスタートが593msだったので、**100倍遅い**ことになります。まばらなアクセスのプロダクトなら、ほぼ全員が1分待つ計算です。

つまり、本当の軸は「サーバーレスかサーバーか」ではありません。

> 本当の軸は **scale-to-zero か always-on か**。ゼロまで落ちるものは、名前が何であれコールドスタートを持ちます。

| | ゼロまで落ちるか | 復帰時間 |
|---|---|---|
| Vercel Functions | 落ちる | 実測 P75 593ms（起動込みCPU） |
| Cloudflare Workers | 落ちる（ただし極小） | 数ms |
| Render Free | **15分で落ちる** | **約1分** |
| Render Starter 以上 | 落ちない | — |
| Railway | 落ちない（従量課金） | — |
| Fly.io（`min_machines_running = 1`） | **落ちない** | — |

**無料の常時起動は、基本的に存在しません。** 月$3〜5は、コールドスタートを買い取る金額だと考えたほうが正確です。

## 3. 料金と機能の比較

少トラフィックのプロダクトを常時起動で置く前提で並べます。数字はすべて公式の価格ページ、2026年8月時点です。

| | 最小の常時起動構成 | 月額 | 東京リージョン | 設定の持ち方 |
|---|---|---|---|---|
| **Vercel Hobby** | 不可（関数のみ） | $0（CPU 4時間まで） | ○ `hnd1` | ダッシュボード |
| **Vercel Pro** | 不可（関数のみ） | **$20**/人 | ○ `hnd1` | ダッシュボード |
| **Cloudflare Workers** | 不可（関数のみ） | $5〜 | 全世界 | `wrangler.toml` |
| **Render Free** | **✗ 15分で停止** | $0 | **✗ なし** | `render.yaml` |
| **Render Starter** | 0.5 CPU / 512MB | 〜$7（DB込み約$13） | **✗ なし** | `render.yaml` |
| **Railway Hobby** | 従量（常時起動可） | $5（$5クレジット込み） | ✗ なし | ダッシュボード |
| **Fly.io** | `shared-cpu-1x` 512MB | **$3.32** | **○ `nrt`** | **`fly.toml`** |
| **AWS ECS + ALB** | 可 | **ALBだけで約$16** | ○ | Terraform / CDK |

補足を数点。

- **Vercelは東京が最も高い。** Active CPUが `iad1` $0.128/時に対し、`hnd1` は **$0.202/時（+58%）**。日本向けに速くしようとすると58%高くなります
- **Cloudflare Workers** はコールドスタートが実質ないので、この表で唯一「サーバーレスのまま勝てる」選択肢です。ただし無料枠はCPU **10ms/リクエスト**。Next.js + Prisma + 認証を起動するには足りません。**軽いAPIなら最強、重いフレームワークでは選べない**
- **RenderもRailwayも日本リージョンがありません。** Renderは Oregon / Ohio / Virginia / Frankfurt / **Singapore** の5つだけ
- **AWS ECS + ALB** は、ALBの時間課金 $0.0225/時 だけで月**約$16**。トラフィックがゼロでも発生します

### なぜFly.ioが勝つのか

上の表で**常時起動・東京あり・月$5未満**を全部満たすのはFly.ioだけでした。ただ、$2や$3の差は本音を言えば決め手ではありません。決め手は最後の列です。

**設定が1つのTOMLにあって、操作が全部CLIで、出力がテキストで返ってくる。**

一人で開発していて、インフラはAIエージェントに任せています。GUIのコンソールを何画面もクリックして回る構成は、自分でやるぶんには問題なくても、エージェントに任せると破綻します。**「何を選んだか」がどこにも残らない**からです。`fly.toml` はGitに入ります。

**大きなクラウドを選ばない理由も、価格ではありません。** ECS + ALB + RDS + IAM + VPC を一人で見るのと、コンテナ1つを動かすのとでは、**障害が起きたときに原因までたどり着く時間**が違います。オーバーキルの本当のコストは金額ではなく複雑さです。

## 4. リージョンは、ユーザーではなくDBに合わせる（別記事）

`fly.toml` の `primary_region` を決めるとき、直感に反する結論になりました。**ユーザーは全員日本にいるのに、サーバーはシンガポールに置いています。**

理由は、Neonに日本リージョンが無いことと、**リクエストあたりの往復回数が、ユーザー側とDB側で非対称**だからです。ユーザーとの往復は1回で固定ですが、DBとの往復はクエリの数だけ増えます。DBの隣に置くと、その掛け算が消えます。

実測はDBクエリが **1,541ms → 35ms**。40倍です。Fly.ioが速いからではなく、クエリが太平洋を渡るのをやめたからでした。

計算の詳細は[こちらの記事](#)に書きました。

## 5. そのまま貼れる `fly.toml` と、サーバーを持つと戻ってくる4つの仕事

サーバーレスをやめるということは、**サーバーレスが肩代わりしてくれていた仕事が自分に返ってくる**ということです。4つあり、うち3つの手当てがこのファイルに入っています。

```toml
app = "my-app"
primary_region = "sin"   # ← DBの隣。ユーザーの隣ではない（第4章）

[deploy]
  # ② デプロイのたびに止まる、への対処
  strategy = "bluegreen"
  release_command = "sh -c 'cd /migrate && node node_modules/prisma/build/index.js migrate deploy'"

[http_service]
  internal_port = 3000
  force_https = true
  auto_stop_machines   = "stop"   # 余った台だけ止める
  auto_start_machines  = true
  min_machines_running = 1        # ← コールドスタートを消す1行
  max_machines_running = 2        # ① リソースの天井（ハードキャップ）

[http_service.concurrency]
  type = "requests"
  soft_limit = 80    # ここを超えたら2台目が起きる
  hard_limit = 120

[[http_service.checks]]
  path = "/api/health"   # SELECT 1 を打つ。DBに届かなければ503
  interval = "30s"
  timeout  = "10s"
  grace_period = "20s"

[[vm]]
  size   = "shared-cpu-1x"
  memory = "512mb"   # Vercelでの実測平均が294MBだったので
  cpus   = 1
```

`min_machines_running = 1` が問題を解いている1行です。`auto_stop_machines` を切るのではなく、**最低1台を保証する**のがポイント。余った台は止まって構わないので。

### ① リソースには天井がある

サーバーレスならCPUもメモリも勝手に増えます。サーバーは増えません。天井に当たった時点でユーザーはアプリを使えなくなります。

→ **オートスケール、ただし上限2台。** 上限なしにするとボットの波がそのまま請求額になります。弾力性より封じ込めを選ぶ、技術ではなくリスクの判断です。

ただ、理由はそれだけではありません。**そもそも台数を増やしても速くなりません。**

| | 値 |
|---|---|
| Neonコンピュート | 0.25 CU 固定（最小＝最大） |
| `max_connections` | 112（うち6はsuperuser予約） |

アプリを何台に増やしても、この0.25 CUは1ミリも増えません。しかも各インスタンスは自分のプールを持つので、台数×プールが増えない106本を取り合う。**キャパシティが上がる前に、コネクションの奪い合いが先に起きます。**

> 横に並べる前に、「一緒にスケールしてくれないのはどれか」を数える。たいていそれは、状態を持っている側です。

だから2台目は、速くするためではなく**止まらないための2台目**です。

### ② デプロイのたびに止まる

サーバーではデプロイ＝プロセスの再起動です。デフォルトの `rolling` は、マシンが1台だと「古いのを止めてから新しいのを起動する」——ただの再起動になります。

うまくいって30秒。ただし新しいほうが起動に失敗したら（マイグレーションがこけた、環境変数が1つ足りない）**古いほうはもう止めた後**です。しかも、いちばん失敗しやすい日といちばん止まると困る日は同じです。大きな変更を出す日なので。

→ **`strategy = "bluegreen"`。** 古いのを止める前に新しいのを隣に立て、ヘルスチェックが通ってから切り替える。通らなければ古いほうが働き続けます。2台目はデプロイ中しか存在しないので、費用は1デプロイ数セントです。

「正常」の定義も大事で、プロセスが起動しただけでは正常ではありません。`/api/health` は `SELECT 1` を打っていて、アプリが生きていてもDBに届かなければ503を返します。**アプリは生きているのにDBに届いていない、が実際の落ち方**なので。

### ③ 攻撃は、規模に関係なく来る

会社で小さなスタートアップのアプリを何本も作りましたが、攻撃は数え切れないほど起きました。有名である必要はありません。公開されたIPとポートがあれば十分です。

| | 攻撃を受けたとき |
|---|---|
| サーバーレス | 請求書が跳ね上がる |
| サーバー | 落ちる |

→ **CloudflareをプロキシモードにしてWAFをサーバーの前に置く。** 無料で、トラフィックが自分のサーバーに届く前に止まります。コスト側の蓋は①の上限2台が兼ねています。

### ④ 落ちても、誰も教えてくれない

サーバーレスなら、落ちているかどうかはプラットフォームの問題です。サーバーでは自分の問題になります。そして一人で開発していると、気づくのはユーザーからの連絡です。

これは設定1行では終わらないので、章を分けます。

## 6. 監視をどう組むか（別記事）

サーバーを持つと戻ってくる4つ目の仕事——「落ちても誰も教えてくれない」——は、設定1行では終わりません。ログ、製品分析、エラー追跡、そして**人間に届くメール通知**という性質の違う4層をどう組んで、それを全部AIエージェントから触れる状態にしておくか。[別の記事](#)にまとめました。

そこで書いている中で、この記事の判断に直結するものを1つだけ引いておきます。

> **そのサービスの「状態」は、テキストで問い合わせられるか。**

きれいなダッシュボードは人間には価値がありますが、**エージェントにとっては存在しないのと同じです。** 上の比較表に「設定の持ち方」という列を入れたのは、そのためです。

## 7. 結果と、公平に書いておくこと

冒頭の表がその結果です。数字そのものより大事なのは、そこに至るまでの時間でした。**調査からDNSの切り替えまで、メールが届いた当日の3時間**で終わっています。踏み切れた理由は勇気ではなく、**戻し方が用意されていたから**です。CloudflareのTTLを事前に60秒に下げ、DNSをVercelに戻せば数十秒で元通り。移行が確定するまでVercel側は生かしたまま。

**「失敗したらどうする」に秒単位で答えられるなら、それはもうリスクの高い作業ではありません。**

そして、この窓は閉じていきます。コンテナ1つ・DB 34MB・環境変数25個の今なら午前中で終わる作業が、1年後には四半期のプロジェクトになる。技術的な難易度は同じでも、**やり直しの許されなさ**が違うからです。だから、いちばん動きやすいのは**まだ急いでいないように見えるとき**です。

ちなみに、引っ越しの副産物として壊れていたものが3つ見つかりました。本番のオブジェクトストレージが動いていなかった（環境変数がPreviewにしか無く、画像プロキシが500を返していた）、ロゴのURLが死んだドメインを指していた、DBがコードより18日進んでいた。**引っ越しの価値の半分は、普段見ないところを全部見ることになる**ことだと思います。

### なぜ速さが必要だったのか

最後に、5倍が何の役に立つのかを書いておきます。ここが抜けると、ただのベンチマーク自慢になるので。

**推しスキは、机の前で開くアプリではありません。** 現場で、ライブの合間に、片手で開きます。推しの出番が何時なのかを確認するために、もう片方の手にはペンライトを持って、電波の悪い会場で。

その状況で2秒待たされるのは「遅い」とは読まれません。**「壊れている」と読まれます。** そして画面を閉じる。

失われるのは1セッションではなく、**習慣**です。予定を管理するアプリは、現場に行く前に開いてもらえないと存在価値がありません。最初の3回もたついたら、4回目はない。

しかも42%というのは平均の遅さではなく、**ばらつき**です。あるときは一瞬で開き、あるときは2秒待つ。規則性がない。**予測できないアプリは、一貫して遅いアプリより体感が悪い**というのが、今回いちばん腹に落ちたことでした。

---

**最後にVercelのために公平に書いておきます。** 593ms/リクエストは42%のコールドスタートの結果であって、トラフィックが密になればインスタンスが再利用されてこの数字は大きく下がります。**Vercelはスケールすると良くなります。** この記事の結論は「Vercelが高い」ではなく、「**僕のトラフィックの形に合っていなかった**」です。

だから持ち帰ってほしいのは、移行先の名前ではありません。最初の3つの数字です。

1. **コールドスタート率**
2. **1リクエストのCPU時間**
3. **1リクエストのDB往復回数**

**測れば、自分のプロダクトの答えは自分で出せます。** そしてこの判断は可逆です。トラフィックの形が変わったら、戻せばいい。
