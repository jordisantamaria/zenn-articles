「推しスキ」という推し活アプリを個人で作っています。App StoreとGoogle Playに出ていて、ユーザーは全員日本にいます。

そのバックエンドをVercelからFly.ioへ移したとき、いちばん意外だったのはリージョンの選び方でした。ユーザーが全員日本にいるなら、東京に置くのが当然に見えます。**でもシンガポールに置きました。**

結果、本番のDBクエリが **1,541ms → 35ms** になりました。40倍です。

Fly.ioが速いからではありません。**クエリが太平洋を渡るのをやめたからです。** 以下は、その判断に至るまでに数えたものと、実測した数字です。

## Neonに日本リージョンはない（そして後から変えられない）

まず前提から。使っているデータベースはNeon（サーバーレスPostgres）です。公式ドキュメントに載っているリージョンは、この記事を書いている時点でこれだけです。

| | リージョン |
|---|---|
| 米国 | N. Virginia / Ohio / Oregon |
| 欧州 | Frankfurt / London |
| アジア太平洋 | **Singapore** / Sydney |
| 南米 | São Paulo |

**日本はありません。** 東京も大阪もない。日本向けにNeonを使うなら、いちばん近いのはシンガポールです。（Azureリージョンもありましたが、現在は新規作成が廃止されています）

そして、もっと効いてくる仕様がこれです。

> You cannot change the region for an existing project.
> — [Neon Docs, Regions](https://neon.com/docs/introduction/regions)

**プロジェクトのリージョンは後から変更できません。** 変えたければ新しいプロジェクトを作ってデータを移すしかない。つまりこれは、あとで直せる設定ではなく、最初に決めきる項目です。

さらに、同じページにこう書いてあります。

> To minimize latency between your Neon database and application, we recommend choosing the region closest to your application server.

「**アプリケーションサーバーに近いリージョンを選べ**」。まったく正しいアドバイスですが、日本にサーバーを置きたい人にとっては実行不可能です。近いリージョンが存在しないので。

だから逆をやります。**DBを動かせないなら、サーバーのほうを動かす。**

## 移行前の構成は、地球を一周していた

| ピース | 場所 |
|---|---|
| ユーザー | 日本 |
| Vercel Functions | `iad1`（ワシントンDC）— **デフォルトのまま** |
| Neon | `ap-southeast-1`（シンガポール） |

日本のユーザーが叩いたリクエストが、ワシントンDCで処理され、クエリはそこからシンガポールへ飛んでいました。地球を一周しています。

そして `iad1` は、誰も選んだ覚えのないデフォルト値です。**リージョンを一度も意識しないと、この構成になります。** サーバーレスの「設定を書かなくていい」という美点の裏側がここで、書かなかった設定にもデフォルト値は入ります。

## ユーザーとの距離ではなく、往復の回数を数える

では、サーバーを東京に置くべきか、シンガポールに置くべきか。直感は「ユーザーの近く＝東京」です。

でも、リクエスト1回あたりの往復回数を数えると答えが変わります。

- ユーザー ↔ サーバー：**1往復**（リクエストにつき1回で固定）
- サーバー ↔ DB：**クエリの数だけ往復**

ここが非対称です。ユーザーとの往復は1回で固定ですが、DBとの往復は画面が投げるクエリの数だけ増えます。

アプリの1画面は、だいたい複数回クエリを投げます。推しスキの場合、開いた瞬間に「今日の現場」と「推しの出番時刻」を引くうえ、better-authが何よりも先にセッションを見にいくので、1クエリで済む画面はほぼありません。

日本からNeonシンガポールまでのRTTを測ったら **105ms** でした。この数字で計算します。

```
サーバーが東京：
  ユーザー ↔ 東京         5ms × 1        =   5ms
  東京 ↔ シンガポール   105ms × 3クエリ  = 315ms
                                    合計 ≈ 320ms

サーバーがシンガポール（DBの隣）：
  ユーザー ↔ シンガポール 105ms × 1      = 105ms
  シンガポール ↔ DB        ~1ms × 3クエリ =   3ms
                                    合計 ≈ 108ms
```

サーバーをDBの隣に置くと**掛け算が消えて**、太平洋を渡る往復がリクエストにつき1回だけ残ります。クエリが増えるほど差が開くので、**画面が重いほどこの選択が効きます。**

逆に言うと、東京に置くのが正しいのは **1リクエストあたりのクエリが1回以下のとき**です。キャッシュが効いていてDBにほとんど触らないAPIなら東京でいい。そうでないなら、数えてから決めるべきです。

## 自分のアプリの「往復回数」を数える

一般論で終わらせても仕方ないので、測り方を書いておきます。Prismaならクライアントにログを仕込むだけです。

```ts
const prisma = new PrismaClient({
  log: [{ emit: 'event', level: 'query' }],
})

let count = 0
prisma.$on('query', (e) => {
  count++
  console.log(`[q${count}] ${e.duration}ms  ${e.query.slice(0, 80)}`)
})
```

これでいちばん重い画面を1回開いて、`count` がいくつになるか見る。**その数が、そのままリージョン選択の掛け算の係数**です。

3を超えていたら、サーバーはDBの隣に置いたほうがまず勝ちます。1〜2で、しかもキャッシュが効くなら、ユーザーの近くに置く判断もあり得ます。

ついでに、ここでN+1が見つかることがよくあります。**往復回数を減らすのはリージョン選定より先にできる最適化**なので、40のクエリが出てきたら、引っ越しの前にそっちを直したほうがいい。

## 実測：1,541ms → 35ms

移行の前後、同じ本番環境で測った数字です。

| | 移行前（`iad1`） | 移行後（`sin`） |
|---|---|---|
| DBクエリ | **1,541ms** | **35ms** |
| リクエスト全体 | 約1.9s | 約0.35s |

1,541msには、もう一つ理由が混ざっています。**Neonのコンピュートが5分でサスペンドする**設定だったので、まばらなアクセスでは毎回起こしにいっていました。起動待ち＋太平洋往復＋関数のコールドスタートが重なって、`SELECT 1` に1.5秒かかっていたわけです。

移行後の35msは、シンガポール内の往復です。ここまで来るとDBは実質ローカルと同じ扱いになります。

そして皮肉なのは、**サーバーレスのままだとこの最適化ができない**ことです。リクエストごとに起動する以上、DBとの間にコネクションプールを持ち続けられません。常時起動のコンテナに移して初めてプールが生き続けて、35msという数字が意味を持ちます。

## 一般化：いちばん「おしゃべりな依存先」までの距離

この話は、Neonにも日本にも限りません。

> 重要なのはユーザーからサーバーまでの距離ではなく、サーバーから**いちばんおしゃべりな依存先**までの距離 × そのおしゃべりさ。

「おしゃべりさ」は1リクエストあたりの往復回数です。DBのこともあれば、認証プロバイダのことも、外部APIや検索エンジンのこともある。

リージョンを決める前にやることは2つだけです。

1. **1リクエストで外部に何往復しているか数える**（上のログで出ます）
2. **その依存先が、そもそもどこに置けるのか確認する。** 置けない場所を前提に設計しても意味がない

僕も最初は東京に置くつもりでした。この掛け算をリージョン選定の前に計算している人は、あまり多くないと思います。そして Neon のようにリージョンが**後から変えられない**サービスでは、この計算をサボったコストが一番長く残ります。
